Storage and stateful recovery

A replacement Pod is not a recovered database. Recovery requires accessible data, exactly the intended writers and an application-level correctness check.

By the end you can…

Locate a CSI failure stage, choose storage semantics, recover a lost node without split brain and measure data recovery objectives.

Scenario: a disappeared node still owns the volume

A database Pod loses contact with the API. Its replacement is Pending or reports multi-attach errors. The original node may be powered off, or merely partitioned while still writing. Force-deleting API objects does not prove the original process stopped. Creating two writers can turn an availability incident into data corruption.

Follow the volume lifecycle

PVC → StorageClass/provisioner → PV with topology
Pod scheduling → compatible node / volume binding
CSI controller attach (when required) → VolumeAttachment
CSI node stage/publish → mounted filesystem or block device → application

WaitForFirstConsumer lets provisioning account for scheduling topology. Immediate provisioning can create a volume in a zone the workload cannot use. A bound PVC proves neither attachment nor a successful filesystem mount. Some CSI drivers do not require a controller attach step, so absence of VolumeAttachment is not universally a failure.

Inspect the failed stage

kubectl --context "$CTX" describe pod database-0 -n marketplace
kubectl --context "$CTX" describe pvc data-database-0 -n marketplace
kubectl --context "$CTX" get pv,storageclass
kubectl --context "$CTX" get volumeattachments
kubectl --context "$CTX" get csinodes
kubectl --context "$CTX" get nodes -L topology.kubernetes.io/zone

Match Events to controller and node-plugin logs for the same volume handle and time. FailedScheduling with volume node affinity points at topology. FailedAttachVolume points at backend permissions, attachment limits, stale attachment or backend state. FailedMount points later in the path: node plugin, device, filesystem, permissions or secrets. A filesystem permissions error is not fixed by expanding IAM at the controller.

Runbook: lost node and suspected stale attachment

  1. Pause operator-driven failover if its next action could create an additional writer. Identify Pod, PVC, PV, backend volume and all possible writers.
  2. Determine physical/virtual node state through infrastructure control, not only Kubernetes NodeReady. Fence the old writer using the backend's supported method: confirmed power-off, storage-access revocation or equivalent.
  3. After fencing is proven, follow the distribution's non-graceful shutdown procedure. The out-of-service taint mechanism can help volume detach and Pod replacement where supported; it is not a substitute for fencing.
  4. Check destination-zone compatibility, attach limits, available capacity and encryption access. Escalate to the storage owner if backend state disagrees with Kubernetes; do not remove attachment finalizers as a generic repair.
  5. Start one intended writer, complete filesystem/database recovery and check durable application markers before restoring traffic.
  6. Remove temporary node state only after recovery and before returning a node to service. Record the fencing evidence and recovery times.

Stop condition: if you cannot prove the old writer is fenced, do not force a second writer. Preserve consistency and communicate the availability impact.

Backups, performance and restore objectives

A CSI snapshot is commonly crash-consistent and may share the storage system's failure domain. Application-consistent backup requires database coordination, transaction-log/WAL handling or a supported operator procedure. A useful backup has independent retention, encryption-key access and a tested restore destination. Kubernetes object backup, etcd recovery and application-data backup solve different problems.

Define RPO from the newest committed business record recoverable after failure; define RTO from incident start to verified useful service. Example: failure at 12:00, latest recovered commit 11:57, verified service at 12:24 means measured RPO 3 minutes and RTO 24 minutes. Snapshot completion time alone establishes neither.

Capacity planning includes queue depth, p99 IO latency, throughput, IOPS, volume count/attach limits and rebuild load. A disk size increase might change performance on one backend and not another. Expansion can involve controller and filesystem stages; verify allowVolumeExpansion, driver support and application-visible space. PVC shrinking is not a generic reverse operation.

Lab: persistence and restore

Run the storage lab: create a durable marker, recreate the consumer and verify persistence; then back up the toy file to the host, corrupt it, restore it and verify the checksum. This is a file-level learning exercise. The extended CSI/database drill requires a snapshot-capable driver and measures real RPO/RTO, consistency and recovery into a separate destination.

Choose the action

The old node is NotReady. Is that sufficient fencing evidence?

Answer

No. It might still run and write while unable to reach the API. Confirm power or storage-level fencing through the infrastructure/backend before forced detach and replacement.
