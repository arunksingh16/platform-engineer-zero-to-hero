Upgrades and fleet delivery

An upgrade is a sequence of compatibility transitions. “Rollback available” is meaningful only when you name which component and which persisted state can go backward.

By the end you can…

Build a compatibility matrix, detect removed API usage, stage fleet upgrades and distinguish configuration rollback from control-plane or data recovery.

Scenario: the canary passes, the first real tenant fails

A canary cluster contains only stateless test Pods. The production cohort also has a CSI driver, a conversion webhook and an operator using an old API. The canary never exercised them. Representativeness means coverage of the risky contracts, including stateful restore and admission, not merely a smaller node count.

Under current upstream policy, kubectl is supported within one minor of the API server. Modern kubelets may be up to three minors older but must not be newer than any API server they can contact; HA mixed versions narrow the intersection. Do not skip API-server minor versions. Providers and add-ons may impose stricter rules, so upstream skew is necessary but not sufficient.

Inventory API and storage contracts

kubectl --context "$CTX" version -o yaml
kubectl --context "$CTX" get nodes \
  -o custom-columns=NAME:.metadata.name,KUBELET:.status.nodeInfo.kubeletVersion,RUNTIME:.status.nodeInfo.containerRuntimeVersion
kubectl --context "$CTX" get crd \
  -o custom-columns=NAME:.metadata.name,STORED:.status.storedVersions
kubectl --context "$CTX" api-resources
kubectl --context "$CTX" get validatingwebhookconfigurations,mutatingwebhookconfigurations

Server-side dry-run on the current cluster does not prove compatibility with the target release. Validate rendered manifests on a target-version test cluster and inspect deprecated API request metrics/audit evidence over a representative business cycle. Rare monthly Jobs and recovery tools can escape a short observation window.

Changing a CRD's storage: true version does not rewrite all existing objects. Keep old served versions and conversion compatibility until data is migrated and clients are updated. Verify conversion round-trips before removing versions; do not patch status.storedVersions just to silence a migration error.

Upgrade waves and exit gates

  1. Capture baseline SLOs, API error/latency, capacity, backups and tested recovery. Inventory current versions and freeze unrelated platform changes.
  2. Upgrade a representative canary through the supported sequence. Exercise create/delete, policy rejection, DNS/egress, volume provisioning/restore and workload identity.
  3. Replace a limited node cohort with sufficient surge and IP/volume capacity. Check PDBs and topology before drains; never solve an unknown drain block by blindly bypassing eviction.
  4. Hold the wave through representative load and scheduled work. Proceed only when error budget, pending age, node health, controller lag and functional checks meet declared thresholds.
  5. Expand by independent failure domain. Keep a working previous cohort while supported and maintain a clear pause owner.
  6. Remove obsolete API clients, images and exceptions after the fleet converges. Record the final version matrix and renewal dates.

Runbook: failed upgrade wave

Pause orchestration and identify the failed layer. Restore a bad manifest or supported add-on release if its data/schema is backward-compatible. Replace faulty canary nodes with the previous approved image only where control-plane skew and provider lifecycle permit. An API-server downgrade or etcd restore is not equivalent to kubectl rollout undo; often the supported path is forward repair or migration to a prepared replacement cluster.

Coordinate live mitigation with GitOps ownership. Pause the relevant reconciliation scope, save the intended revision, apply the narrow repair, then update/revert Git before resuming. Otherwise GitOps can undo the fix or recreate the incident. Stop the wave if data integrity, policy enforcement or identity trust fails even if application error rate temporarily looks healthy.

Recovery is verified by functional probes and restored SLOs plus converged desired state. Record temporary drift, follow-up migrations and a next decision time. Do not leave the fleet indefinitely in a barely supported skew window.

Lab: broken release and evidence-led rollback

Run the rollout exercise. Set a nonexistent image on the lab Deployment, observe the stalled rollout and preserved old endpoints, then undo it and verify service. This validates application rollout mechanics, not a Kubernetes downgrade. The extended exercise creates a second target-version cluster and validates the same fixtures there.

Migration review

The new CRD storage version is configured and new writes succeed. May you delete the old version?

Answer

Not yet. Verify stored objects migrated, old clients retired and conversion remains correct. Served and storage version flags alone do not prove those conditions.
