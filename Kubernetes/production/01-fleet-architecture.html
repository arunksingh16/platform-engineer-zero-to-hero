Fleet architecture and failure domains

A cluster is both a scheduling pool and a shared failure boundary. The architecture question is how much customer impact one mistake is allowed to cause.

By the end you can…

Choose a cluster boundary, enumerate shared dependencies, calculate failover headroom and define a testable ownership contract.

Scenario: a fleet that shares more than it admits

Assume a marketplace with 120 services, three zones per region and two regions. A team proposes one large cluster per region to maximize utilization. Another proposes a cluster per team. Both miss the dominant incident: a shared admission service is deployed incorrectly across every cluster at once. Cluster count alone did not isolate change.

Draw three paths separately: customer requests, provisioning/reconciliation, and recovery. Existing traffic may survive an API outage while replacement Pods cannot start. A registry failure may be invisible until nodes churn. A central identity provider can block new access even when every node is healthy.

Choose boundaries from requirements

ModelGood fitCost and residual risk
Shared cluster, namespacesCooperating teams, common trust and release cadenceEfficient packing; shared API, admission, nodes and cluster-scoped APIs
Dedicated nodes, shared control planePerformance separation, specialized hardwareLess packing efficiency; API overload and privileged cluster administration still cross tenants
Separate clusters / cellsIndependent blast radius, upgrade waves, high-risk workloadsDuplicated add-ons, spare capacity and operational overhead; global dependencies remain
Separate accounts/projects and regionsAdministrative and regional failure separationMore networking, identity and data-replication complexity; requires independent recovery credentials

A cell is an intentionally bounded serving unit, not a Kubernetes API type. Route a stable customer or workload partition to it and bound its capacity. Cross-cell synchronous dependencies can erase the isolation. Choose the maximum cell size from acceptable impact and tested evacuation capacity, rather than an upstream maximum node count.

Capacity must survive the failure you claim

With evenly spread work across three identical zones, loss of one zone multiplies surviving load by 3 / 2. At 60% normal utilization, survivors reach 90% before retries or failover overhead. If the tested safe ceiling is 70%, normal utilization must be at most 70% × 2/3 = 46.7%. This model assumes fungible capacity, balanced placement, working routing and available data; topology-bound volumes and GPUs invalidate those assumptions.

Record capacity at the limiting resource: safe requests/second at a latency target, CPU, memory, storage throughput, IPs, or downstream database connections. A regional traffic shift that doubles API replicas but exhausts database connections is not recovery.

Investigation and recovery: one cell cannot schedule

kubectl --context "$CTX" get nodes -L topology.kubernetes.io/zone
kubectl --context "$CTX" get pods -n marketplace -o wide
kubectl --context "$CTX" get events -n marketplace --sort-by=.metadata.creationTimestamp
kubectl --context "$CTX" get --raw '/readyz?verbose'

Set CTX to the intended cluster. These inspections require read permissions, with separate access for non-resource health URLs. Compare a healthy cell: identical application errors with a single cell's failed scheduling suggest a local platform path; every cell failing after the same policy revision suggests a common change.

  1. Pause the implicated rollout and record affected cells, timestamps and revision. Separate serving health from change-plane health.
  2. Check surviving-cell measured capacity and data residency before shifting traffic. Shift a small cohort first; watch latency, error rate and downstream saturation.
  3. Stop the shift if the receiving cell exceeds its tested ceiling or data correctness becomes uncertain. Shed optional work rather than multiplying retries.
  4. Recover the failed cell's dependency, verify a new Pod can become Ready and serve a synthetic transaction, then gradually return traffic.
  5. Reconcile temporary routing and Git state; a green API endpoint alone is insufficient recovery evidence.

Lab: dependency-loss review

Use the fleet exercise. Inventory a lab cluster and build a dependency map for existing traffic, new Pods and emergency access. Remove one dependency on paper at a time. For each, predict which path fails and identify an observable signal. Do not claim region-failure tolerance from a laptop cluster.

Design review

Two cells share a database, registry and admission release pipeline. What do two cells actually buy?

Answer

They can isolate some node, API and local configuration failures. They do not independently survive shared database failure or correlated admission rollout. Separate release waves, bound data dependencies and test image-cold recovery before calling them independent.
