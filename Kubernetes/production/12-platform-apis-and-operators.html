Platform APIs and operators

An operator is a distributed system that happens to watch Kubernetes objects. API writes and external side effects do not become one transaction because they occur in the same reconcile function.

By the end you can…

Define a stable platform API, make external operations recoverable across crashes, operate finalizers and evolve controllers without fleet-wide storms.

Scenario: the database was created twice

A controller creates an external database and crashes before writing its ID to status. On restart, status is empty, so it creates another database. A Provisioning flag written before the call merely moves the crash window: now a crash can leave the flag set when no database exists. Status is evidence, not an atomic commit with the provider.

Design the API around intent and ownership

Expose domain intent such as service tier, region, backup objective and deletion policy. Keep provider credentials and incidental implementation details out of tenant-editable fields. Validate immutable transitions and define defaulting deliberately. Users own spec; the controller owns status, including conditions, external identifiers and the observed generation that the result corresponds to.

A Ready condition describing generation 4 cannot prove generation 5 has converged. Compare metadata.generation with the relevant observedGeneration. Give each field one owner; server-side apply field management helps coordinate ownership but cannot make conflicting desired states sensible. Separate spec updates from status updates to avoid reconciliation loops triggered by meaningless writes.

A crash-aware reconciliation outline

read current object; return if no longer present
if deletionTimestamp is set:
    find external resource by stable owner identity
    execute/reconcile the declared deletion or retention policy
    remove only our finalizer after the obligation is satisfied
    return
ensure our finalizer is persisted before creating external state
derive stable operation identity from UID + desired operation revision
discover external resource / operation by identity
if absent:
    start operation with provider idempotency key, when supported
observe actual external state; reconcile toward current intent
patch status using resourceVersion-aware conflict handling
requeue on a bounded schedule while asynchronous work remains

This is pseudocode, not an SDK implementation. The exact contract depends on the external API. A stable key should identify one logical operation: do not use a new random key per retry, and do not let unrelated spec edits accidentally create a new resource. If the provider cannot deduplicate requests, design discoverable ownership tags/names, uncertain-outcome handling and a compensation/manual-recovery procedure.

Concurrency, caches and load

MechanismWhat it solvesWhat it does not solve
Optimistic concurrency / resourceVersionDetects conflicting API writesDoes not deduplicate external calls already accepted
Leader electionCoordinates active controller leadershipDoes not guarantee exactly-once execution through partitions or restarts
Informer cacheReduces API traffic and supports watchesReads can lag; a write may not immediately appear in cache
Rate-limited work queueBounds retries and helps avoid hot loopsCannot fix an endlessly changing desired state or unbounded external latency

Make conflicts retryable through reread and recomputation, not blind overwrite. Bound reconcile concurrency against API and provider quotas. Add timeouts and jittered backoff. Track queue depth, oldest queued age, reconcile duration/errors, external operation age and writes per reconciliation. A controller that rewrites status on every pass can overload the API without changing useful state.

Deletion is a contract

A finalizer blocks object removal while cleanup obligations remain; it is not a backup mechanism. Record whether deleting the custom resource deletes, retains or orphans external data. OwnerReferences enable Kubernetes garbage collection within its scope rules but do not clean up an external cloud database automatically. Restore and namespace-deletion procedures must account for these relationships.

Runbook: stuck finalizer

  1. Identify the finalizer's owning controller and the resource's deletion policy. Capture deletion timestamp, conditions, generation and external ID without exposing credentials.
  2. Check controller availability, RBAC, external API connectivity and provider operation state. A deleting object with a live external database may be correctly waiting.
  3. Repair the controller/dependency and observe cleanup reconciliation. Stop if the proposed repair could delete retained data or affect another owner.
  4. If normal cleanup is impossible, have the resource owner explicitly resolve the external obligation and record retained/orphaned assets.
  5. Only then remove the specific finalizer through the supported recovery procedure. Verify external state and inventory agree; do not strip every finalizer from a namespace.

API evolution and testing

Version schemas, conversion and controller behavior together. Test old objects read by the new controller, new objects read during rollback, unknown-field handling and defaulting. CRD storage-version migration is separate from serving a new version; see fleet delivery.

Useful failure tests interrupt execution after an external API accepts the operation but before status persists; after finalizer persistence but before creation; during a 409 conflict; during provider timeout with uncertain outcome; and during deletion. Assertions should target no unintended duplicate resource, convergence on restart, bounded retries and honored retention. A test that merely compares a generated manifest cannot establish these properties.

Recovery design

The external request timed out. Should the controller immediately create a replacement with a new key?

Answer

No. Timeout leaves the outcome uncertain. Query by the stable operation/resource identity or retry with the same provider-supported idempotency key. A new identity can create a duplicate.
