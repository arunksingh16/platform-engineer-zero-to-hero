Security engineering

A hardened Pod is one layer. The complete system includes who built its image, who can replace it, which credentials it receives, what the host exposes and how you detect abuse.

By the end you can…

Build a layered threat model, apply a working restricted security context, rotate secrets with evidence and contain an incident without destroying its history.

Scenario: an application vulnerability becomes a cloud incident

An internet-facing service executes attacker-controlled input. Its container runs as root, mounts an unnecessary API token and can reach a node metadata endpoint. The critical question is not just whether the image scanner found a CVE: it is whether application compromise can become node, cluster or cloud-account compromise.

Image signing authenticates a supply-chain assertion; it does not prove absence of vulnerabilities. Scanning needs a remediation window, exploitability context and expiring exceptions. Pin production images by digest and retain the previous approved digest for recovery. The lab uses a version tag for accessibility; record its resolved digest before treating a result as reproducible.

A restricted workload that can actually start

The complete workload uses a non-root BusyBox process, an explicit writable emptyDir, no automatic API token and an HTTP readiness probe. Its security context includes:

securityContext:
  runAsNonRoot: true
  runAsUser: 1000
  runAsGroup: 1000
  fsGroup: 1000
  seccompProfile:
    type: RuntimeDefault
# Per-container securityContext:
#   allowPrivilegeEscalation: false
#   readOnlyRootFilesystem: true
#   capabilities:
#     drop: ["ALL"]

Pod-level identity and seccomp defaults differ from container-level capabilities and privilege-escalation controls. Test real application requirements: TLS caches, temporary files and log paths can fail under a read-only filesystem. Add narrowly scoped writable volumes instead of reverting to privileged mode. Sandboxed runtimes may strengthen workload separation but need compatible devices, performance measurements and operational support.

Secrets: storage, delivery and revocation

Kubernetes Secret base64 encoding is not encryption. Configure encryption at rest through the supported API-server/provider mechanism and protect KMS access independently. Verify key rotation includes rewriting existing objects when required; changing the write key does not automatically migrate every stored object. Keep the old decrypt capability until migration and restore testing prove it is safe to retire.

External secret delivery reduces copies only if the chosen integration actually avoids synchronization into Kubernetes Secrets. Mounted updates do not prove process reload. Record maximum credential age, file-refresh interval, application reload delay and downstream session lifetime. Never include Secret bodies or bearer tokens in audit exports; metadata-level evidence is usually enough for access investigations.

Runbook: suspected workload compromise

  1. Record Pod UID, image digest, node, ServiceAccount, deployment revision, first suspicious request and observable outbound destinations. Preserve existing logs and audit IDs in a restricted incident record.
  2. Contain at the smallest reliable boundary: remove the serving route and block malicious egress with the enforcing network layer. Cordon alone does not stop the running Pod or isolate its traffic.
  3. Determine whether host access or powerful credentials were available. If node compromise is plausible, isolate and replace that node through the incident procedure rather than trusting a container restart.
  4. Revoke affected grants/trust and rotate exposed credentials, accounting for already-issued tokens. Roll forward to a patched, verified image or restore the last known-safe compatible release.
  5. Stop automated redeployment of the vulnerable digest. Validate expected service behavior and verify the exploit path and out-of-scope credential action fail.
  6. Restore controlled traffic, retain evidence, close temporary exceptions and add a regression control for the failed transition.

Stop routine recovery if the scope expands from workload to node or signing/build infrastructure: the trust used to deploy the “fixed” workload may itself be compromised. Recovery ownership must include the affected identity or build system.

Lab: prove the runtime restrictions

Run the runtime lab. Verify non-root identity, a failed root-filesystem write, a successful write to the designated volume, absence of the automatic token and a Ready endpoint. Then test a privileged Pod with server-side dry-run: restricted PSA should reject it. A manifest review alone cannot show that your image tolerates the restrictions.

Rotation drill

A mounted credential file changes but the application keeps failing authentication. What remains unproven?

Answer

The application or SDK may cache the old credential or connection. Check reload behavior and active sessions, then observe a new authenticated request with the replacement identity. File freshness is only one stage.
