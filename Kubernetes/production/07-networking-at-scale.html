Networking at scale

“The network is down” is not a useful hypothesis. Name the source, destination, protocol, port, payload size and failing hop.

By the end you can…

Separate DNS, endpoint, policy and translation failures; identify exhaustion signals; and define rollback gates for network changes.

Scenario: small requests work, large responses stall

A new overlay path crosses a lower-MTU underlay. TCP connections establish and health probes pass, but larger responses retransmit until timeout. Restarting CoreDNS cannot fix a packet-size-dependent failure. The correct hypothesis starts with the new path, encapsulation overhead, path MTU discovery and ICMP handling.

Build the path before choosing a command

Pod resolver → cluster DNS / node-local DNS → upstream DNS
Pod network namespace → veth / CNI dataplane → Service translation or direct Pod route
→ network policy → node route / overlay → destination
External egress: optional node SNAT → NAT gateway/firewall → remote service
Ingress: edge LB → ingress/gateway → Service/endpoints → Pod

The exact order of NAT and policy can differ by implementation. A Service IP is a virtual destination implemented by the dataplane, not necessarily an address bound to an interface. In kube-proxy replacement modes, inspect the CNI's service maps rather than assuming iptables. Follow the CNI course for packet mechanics and the traffic course for L7 routing.

Capacity and policy

DNS demand scales with connection creation, search paths, retry behavior and TTLs, not just Pod count. Fix excessive lookups and connection churn before blindly increasing DNS replicas. Node-local DNS changes the path and policy allowances. For external connections, track NAT port allocation per actual gateway/node/destination contract; there is no universal “ports per Pod” budget.

Linux host evidence can include nf_conntrack_count versus nf_conntrack_max, conntrack insert failures, interface drops and retransmits. Increasing limits consumes memory and may only postpone the fault. Prefer connection reuse, bounded retries and sufficient translation capacity; changing timeouts without understanding flow lifetimes can break established sessions.

Standard NetworkPolicies combine allowed traffic additively. An empty default-deny egress policy blocks DNS unless another allowance exists. A policy object does nothing if the installed dataplane does not enforce it. Confirm both allowed and denied flows, including cross-node traffic and node-local DNS behavior. Namespace/pod selectors in the same peer are ANDed; separate peers are alternatives.

Runbook: network regression during rollout

  1. Freeze the network change and identify affected node cohort, source/destination pair and old/new versions. Compare an unchanged cohort.
  2. Test DNS, Service IP, endpoint IP, cross-node and external paths separately with bounded timeouts. Capture the first failing layer and relevant CNI/LB events.
  3. If selectors or ports are wrong, restore the known-good configuration. If the dataplane change is implicated, follow its supported rollback/replacement path; some CNI migrations require new nodes or clusters.
  4. Stop migration if service reachability, network isolation or control-plane connectivity fails. Do not clear every connection table as a generic repair.
  5. Verify ingress, egress, DNS, policy denials, large payloads and long-lived connection draining before expanding the cohort.

Certificate rotation and load-balancer draining also need end-to-end tests: clients may cache old trust or retain connections to terminating Pods. Align application termination grace, endpoint removal and gateway/LB drain behavior. Readiness alone is not a guarantee that all traffic has stopped.

Lab: prove policy enforcement

Run the network exercise with an enforcing CNI: record successful baseline traffic, apply default deny, observe failure and restore only the required DNS/HTTP flows. Default kind networking may not enforce policy; in that environment record the enforcement test as unsupported rather than “passed.”

Interpret the evidence

A NetworkPolicy exists and every test request still succeeds. Is that a valid isolation test?

Answer

No. Inspect selectors, other additive allowances and the enforcement implementation. A policy acceptance response proves API storage, not dataplane enforcement.
