Nodes and performance

NodeReady is a control-plane observation, not a latency guarantee. A Ready node can be throttling, reclaiming memory, exhausting inodes or placing a workload across costly NUMA boundaries.

By the end you can…

Separate application limits from host pressure, budget allocatable capacity, investigate runtime failures and evaluate dedicated CPU/topology placement.

Scenario: p99 latency increases but average CPU is low

A latency-sensitive service has a small CPU limit. It performs bursts of parallel work and exhausts its cgroup quota within the enforcement period. A one-minute average looks modest while requests wait for replenishment. More replicas may help, but the diagnosis must compare throttling, concurrency, traffic and p99 latency before changing the resource model.

The enforcement stack

Pod resources → admission defaults → scheduler accounting
→ kubelet → CRI runtime (for example containerd) → Linux cgroups/kernel
Node condition / eviction threshold → kubelet reclamation and Pod eviction
Kernel memory exhaustion → cgroup or host OOM handling

CPU requests generally influence placement and proportional scheduling weight under contention. CPU limits constrain runtime time allocation. Memory requests are not a private preallocated region. Memory limits constrain charged memory; cgroup OOM can occur while the host has free memory. A memory-backed emptyDir consumes memory rather than behaving like ordinary disk-backed ephemeral storage.

Inspect before restarting

kubectl --context "$CTX" describe node "$NODE"
kubectl --context "$CTX" get pod "$POD" -n marketplace -o yaml
kubectl --context "$CTX" logs "$POD" -n marketplace --previous --tail=100
kubectl --context "$CTX" top node "$NODE"
kubectl --context "$CTX" top pod -n marketplace --containers

Set NODE and POD from the affected workload. Metrics commands require metrics-server and show recent usage, not historical peaks or all kernel evidence. Previous logs exist only for a retained prior container instance. On a separately authorized host session, inspect journalctl -u kubelet, runtime logs, crictl ps -a, df -h, df -i and /proc/pressure/ where available. On cgroup v2, relevant files include cpu.stat, memory.events and memory.current; locate the correct container cgroup instead of assuming a fixed path.

Budget the host, not the SKU

Start from node allocatable after system and Kubernetes reservations and eviction headroom. Subtract DaemonSets, then account for workload requests, init-container behavior and Pod overhead. Also budget PID count, ephemeral storage, image storage, network state and volume attachments. An 8-core machine is not automatically eight cores available to tenants.

Do not use QoS as an absolute eviction order. For memory pressure, usage exceeding requests, Pod priority and relative usage affect ranking. Disk and PID pressure have different signals. A PDB does not prevent kubelet node-pressure eviction or a kernel OOM.

NUMA and exclusive CPUs

CPU Manager's static policy can allocate exclusive CPUs to eligible Guaranteed containers with integer CPU requests. Topology Manager coordinates placement hints from resource managers; a single-NUMA-node policy can reject admission when CPU, memory/device locality cannot be satisfied together. This trades packing flexibility for locality and predictability. Hugepages and device plugins add their own allocation constraints.

Configure these policies through the supported node-image/kubelet mechanism on a dedicated canary pool. Changing a manager policy can require draining and state handling; do not edit its checkpoint on a live production node. Measure throughput, tail latency, migrations and cost against the normal pool. More exclusive CPUs are not proof of lower end-to-end latency if the bottleneck is a remote database.

Runbook: pressure or performance regression

  1. Preserve termination reason, node conditions, runtime version and recent rollout. Identify whether one workload, one node image or all nodes are affected.
  2. Stop new placement on the affected cohort when justified, but account for remaining capacity before draining. Cordon does not reduce existing pressure.
  3. For a leaking workload, contain its demand and deploy a measured resource/application correction. For host disk/inodes, identify owner and retention; do not blindly remove runtime files.
  4. Canary one change: resource setting, concurrency limit or node image. Stop if throughput or p99 worsens, or another tenant's SLO regresses.
  5. Replace defective nodes through the supported lifecycle. Verify repeated load windows, pressure counters and service outcomes before returning capacity.

Lab: bounded memory failure

Run the OOM lab in a disposable cluster. The container has a small memory limit and writes beyond it to a memory-backed volume. Record the termination state and node condition separately. This teaches the distinction without deliberately exhausting the host.

Interpret a graph

CPU throttling exists, but latency is normal. Should you remove every CPU limit?

Answer

No. Throttling is evidence of enforcement, not automatically an SLO failure. Evaluate demand, latency, contention and tenant isolation, then canary a justified change.
