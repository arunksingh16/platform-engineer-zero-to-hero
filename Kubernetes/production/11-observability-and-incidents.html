Observability and incident command

A useful alert identifies customer or platform impact and the first decision to make. A wall of component alarms rarely tells you which dependency failed first.

By the end you can…

Define a platform SLI, distinguish symptom from cause, run a bounded investigation and close an incident with objective recovery evidence.

Scenario: deployments fail while customer traffic survives

The API's readiness probe is green and HTTP success is normal. New workloads cannot pull images because registry access expired. The platform is still failing its provisioning contract and cannot replace capacity. Separate user-request availability, workload readiness latency and platform change success; one green dashboard cannot represent all three.

Track workload demand and platform saturation together: pending age, scheduling latency, unavailable endpoints, API errors, webhook timeouts, etcd latency, node pressure, DNS errors, CNI drops and CSI operation failures. Attach cluster, region, component and owning team labels. Avoid unbounded request IDs, user IDs or Pod UIDs as long-lived metric labels; use logs/traces for high-cardinality evidence.

Worked error-budget signal

For a hypothetical 99.9% provisioning SLO, the allowed bad fraction is 0.001. A measured bad fraction of 0.01 burns budget at 0.01 / 0.001 = 10×. Use paired short/long windows to distinguish a transient spike from sustained budget consumption, and decide alert thresholds from the response time and budget policy.

If your instrumentation exports the following custom counters, this illustrative query computes a five-minute bad fraction. These are proposed metrics, not built-in Kubernetes metrics; define deadline handling, delayed completions and zero-traffic behavior before deploying an alert:

sum(rate(platform_provisioning_total{outcome="deadline_missed"}[5m]))
/
sum(rate(platform_provisioning_total[5m]))

Pair this with target/scrape availability and synthetic probes. Missing telemetry is not zero failures. See the observability course for counter semantics, histograms and burn-rate alert design.

The first ten minutes

  1. Declare impact: affected user journey, cluster/cell, first known bad time, affected proportion and data-risk status. Assign incident commander, investigator and communications owner as needed.
  2. Stabilize change: pause implicated rollouts and noisy automation. Preserve the exact revisions and timestamps.
  3. Build a short hypothesis table: hypothesis, supporting evidence, discriminating check and next decision. Prefer a healthy cohort comparison.
  4. Choose a reversible mitigation: narrow rollback, traffic shift within tested capacity, demand shedding or dependency repair. Assign one owner and an explicit stop condition.
  5. Verify: run the failed operation end to end, observe the relevant SLI and confirm no new failure domain is affected.

Bounded evidence collection

kubectl --context "$CTX" get pods -n marketplace -o wide
kubectl --context "$CTX" get events -n marketplace --sort-by=.metadata.creationTimestamp
kubectl --context "$CTX" describe pod "$POD" -n marketplace
kubectl --context "$CTX" logs "$POD" -n marketplace --since=10m --tail=200
kubectl --context "$CTX" get endpointslices -n marketplace

These are starting points, not a command to run repeatedly across every namespace. Events are transient and logs may contain sensitive application data; scope exports and retention. Save request/audit correlation IDs when possible. Avoid dumping Secrets, environment credentials or entire cluster objects into a public incident channel.

Runbook: cascading component alarms

Order failures by time and dependency. If ingress, autoscaling and workloads all fail after DNS degradation, investigate name-resolution dependencies before restarting every component. If API writes fail but existing traffic works, follow admission/control-plane evidence. If new Pods fail only on one node image, compare runtime/CNI state there.

Stop the current mitigation if errors spread to a healthy cohort, downstream saturation rises or evidence contradicts the hypothesis. Escalate to the dependency owner with exact scope, operation, timestamp and evidence, rather than “Kubernetes is broken.” Keep a next-update time even while the technical cause is unknown.

Close only after sustained recovery through the relevant load window, successful replacement/provisioning and removal of temporary drift. The postmortem records trigger, enabling conditions, amplification, detection delay, mitigation effect and prevention owners. “Human error” does not explain why a bad change crossed every cell without a stop gate.

Lab: diagnose an injected failure

Run the incident exercise with the failed rollout or scheduling fixture. Complete the incident record without assuming the injected cause. Grade the investigation on evidence, scope and recovery verification rather than on how many commands were executed.

Choose a signal

Every node is Ready but no new Pod can become Ready. Which platform contract should alert?

Answer

Workload provisioning/readiness deadline success, supported by image-pull, admission, scheduling and dependency evidence. NodeReady alone does not measure that outcome.
