Kubernetes: production engineering

Own the failure boundary. Trace an identity across systems, recover a stateful workload without two writers, survive an admission outage, and upgrade a fleet with evidence rather than optimism.

Who this is for

Engineers comfortable with Pods, Deployments, Services, scheduling and a shell. Complete the core course first if those are new. Each module combines a design decision, an investigation, a recovery procedure and an exercise; allow additional time for the labs.

The operating scenario

A fictional regional marketplace runs interactive APIs, asynchronous jobs and stateful dependencies across three zones. Teams share infrastructure but have different risk and latency budgets. Numerical examples are explicit hypothetical inputs, not measurements or claims about Uber's internal architecture.

Modules

    Lab and evidence pack

    Start with the lab guide. It contains runnable RBAC, admission, runtime, networking, storage, scheduling and rollout exercises, plus fleet and disaster-recovery drills. Use the incident record and production-readiness review to record results.

    Version and validation contract

    The lab API baseline is Kubernetes 1.30 or later: this is a feature floor, not a recommendation to run an unsupported release. Use a currently supported distribution and compatible kubectl. Linux is assumed for runtime exercises; CSI, snapshots, network enforcement and host access are named prerequisites where needed. Read validation status for what has actually been checked. Primary references were reviewed on 12 November 2026; current upstream pages can contain newer features than your cluster.

    Provider implementations

    Use AKS for Azure identity, networking and recovery contracts, and OpenShift for distribution-managed components and supported operations. The CNI and traffic courses explain the underlying packet and gateway models.
