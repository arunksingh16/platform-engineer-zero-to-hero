Control plane and etcd

Adding API-server replicas does not repair a slow disk, an unavailable webhook or a controller that continuously rewrites thousands of objects.

By the end you can…

Localize API latency, contain a reconciliation storm, explain quorum and plan an etcd restore that accounts for watches, encryption and external state.

Scenario: reads succeed, deployments time out

A policy rollout is followed by slow Pod creation, controller retries and rising API request volume. Existing workloads mostly serve normally. The initial hypothesis is etcd saturation. But reads remain fast and admission duration rises first: a webhook is waiting on an external service. The retry storm is an amplifier, not the initiating fault.

The logical write path includes authentication, authorization, flow control, admission/validation and persistence. Mutation occurs before final validating admission; not every read goes through admission or reaches etcd directly. Instrument stages rather than assuming all API latency is storage latency.

APF allocates concurrency using priority levels and flow schemas. It is not a substitute for client backoff, and a broad exemption can let one client starve the control plane. Avoid cluster-wide watch/list commands in a tight diagnostic loop during overload. Inspect audit metadata and existing metrics instead.

etcd: quorum, latency and state size

A voting cluster needs floor(N/2)+1 members for quorum. Three members tolerate one failure; five tolerate two. Four still tolerate only one. Extra members add replication work and do not linearly increase write throughput. Place members across intended failure domains while preserving the latency budget; a cross-region quorum is not a free disaster-recovery solution.

Track etcd_disk_wal_fsync_duration_seconds, etcd_disk_backend_commit_duration_seconds, pending proposals, leader changes and backend size relative to quota. Metric availability and labels depend on the etcd distribution. A large object count, frequent status writes and retained history consume different resources. Compaction removes historical revisions; defragmentation reclaims backend space and can block the target member. Use the distribution's maintenance procedure and retain quorum.

Recovery runbook: saturation without data loss

  1. Capture start time, changed component and request classes. Confirm whether the API is unhealthy or only particular operations fail.
  2. Pause the offending automation or reduce its concurrency at its source. Preserve essential controllers and emergency access.
  3. If admission is responsible, restore the last healthy narrow policy/webhook configuration using the documented emergency path. Broadly disabling admission changes security posture; record the exact temporary exception.
  4. If etcd is responsible, check health and alarms using provider tooling. Repair disk/network or replace a failed member through the supported procedure; do not restore an old snapshot merely to solve high latency.
  5. Resume clients in batches after write latency, queue depth and controller lag return to baseline. Verify create, update, watch and deletion on a disposable object.

Disaster recovery is a different procedure

For actual quorum/data loss, isolate the old cluster and stop competing writers before restoring. A recovery bundle includes a verified snapshot, member topology, compatible binaries, PKI and encryption/KMS configuration. Restoring encrypted Secrets without usable decryption keys does not recover the service. An etcd snapshot contains sensitive cluster state and needs independent access controls and off-cluster retention.

Use etcdctl snapshot save for a live authenticated snapshot and the matching etcdutl snapshot status for inspection. The version-specific restore procedure creates new member data directories and identities. For Kubernetes, plan a revision bump and mark-compacted restore where supported so old informer caches invalidate rather than silently retaining state from a newer revision. Restore commands depend on peer URLs, member names, paths and version; copy them from the matched distribution recovery procedure, not a generic one-line recipe.

After restore, reconcile cloud load balancers, volumes and other external side effects with restored Kubernetes state. Measure API recovery separately from application recovery. Require a create/watch/delete probe, healthy controllers, readable Secrets and an application transaction before reopening normal changes.

Lab: write-path probe and restore rehearsal

Run the bounded write-path exercise and record timings. The extended drill uses a separate recoverable environment and the provider's restore procedure. Exit when restored data matches a known marker and controllers converge; snapshot creation alone is not a pass.

Failure analysis

Five etcd members have two failed disks. Can you take a third member offline for defragmentation?

Answer

No. Three votes are required. Only three members remain, so taking another down loses quorum. Repair membership first and verify health before maintenance.
