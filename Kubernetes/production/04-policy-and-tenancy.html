Policy and multi-tenancy

A policy engine is on the production write path. Its correctness, latency, ownership and emergency recovery deserve the same attention as the API server it protects.

By the end you can…

Separate policy layers, choose an enforcement mechanism, stage a rollout and avoid turning one tenant's policy into a fleet outage.

Scenario: the guardrail blocks its own repair

A fail-closed webhook matches every Pod. Its only replica is unavailable, and replacement Pods also require that webhook. Now routine workloads and the repair workload are both blocked. Availability requires redundant healthy endpoints, narrow matching and a tested bootstrap/recovery path—not just setting failurePolicy: Fail.

Use object-count quotas for high-churn resources as well as resource quotas. Constrain who creates PriorityClasses and who may select critical classes. An adversarial tenant sharing a privileged kernel or cluster-admin is outside a namespace-only isolation model.

Choose the smallest mechanism that expresses the rule

Pod Security Admission covers standard Pod Security Standards. Pin enforce policy to a reviewed minor version and use audit/warn to preview stricter versions. ValidatingAdmissionPolicy evaluates CEL inside the API server and is stable from 1.30; it avoids an external webhook dependency for expressible validations. It does not mutate objects or perform arbitrary external API calls.

Kyverno or Gatekeeper can fit broader policy-library, reporting or organization-specific workflows. Evaluate required capabilities against the installed release, controller/webhook availability, latency and operational ownership. Do not deploy two engines enforcing the same rule without deciding whose error and exception semantics win. Rules requiring external data inherit that data source's freshness and availability problems.

A complete CEL rollout fixture

The policy fixture requires a team label on Pods only in the lab namespace. Its binding starts with Warn and Audit. In the lab, change it to Deny and confirm an unlabeled Pod is rejected while a labeled one is accepted.

# Inspection; cluster-scoped policy read rights required
kubectl --context "$CTX" get validatingadmissionpolicy pe-lab-team -o yaml
kubectl --context "$CTX" get validatingadmissionpolicybinding pe-lab-team -o yaml
kubectl --context "$CTX" get namespace pe-lab --show-labels
kubectl --context "$CTX" get resourcequota,limitrange -n pe-lab

Distinguish failurePolicy from validationActions: the former controls evaluation-error handling, while the binding controls false validation results and enforcement. Deny and Warn cannot be combined in the same binding. Audit output requires an audit pipeline to observe; a manifest does not create one.

Operate the policy lifecycle

  1. Define invariant, target resources, owner, exceptions and expiry. Test CREATE and UPDATE, missing fields, init containers and subresources as applicable.
  2. Run audit/warn in one namespace. Measure violations by owning team and estimate deployment impact, including controllers generating Pods.
  3. Fix workloads, then deny on a canary cohort. Track admission latency, rejected requests, timeouts and stalled rollouts.
  4. Expand by failure domain. Keep the policy engine's dependency and repair path independent from rules that could strand it.
  5. Record exceptions as scoped, reviewed resources/configuration with a removal date; avoid permanent catch-all exclusions.

Runbook: admission outage

First distinguish a legitimate policy rejection from a transport/TLS timeout or CEL evaluation error. Inspect the admission response, policy revision, endpoints and certificate expiry. Restore the previous working configuration or narrowly suspend the faulty binding via the platform-owned emergency identity. Capture the temporary enforcement gap; do not delete every webhook configuration.

Stop widening the workaround if failures involve unrelated policies or no longer match the initial diagnosis. Verify the repair path with both a compliant and deliberately noncompliant disposable Pod. Resume paused rollouts, restore the intended enforcement and confirm the exception is gone from Git and the live cluster.

Lab: audit to deny to recovery

Run the policy exercise, including the expected-denial check. Its namespace selector limits scope. Repeat with a renamed namespace to understand why label governance matters: tenants who can remove enforcement-selection labels can bypass a selector-based control.

Trade-off

Should every webhook fail open to preserve availability?

Answer

No universal setting is correct. Fail-open can admit forbidden changes; fail-closed can block recovery. Classify the invariant, narrow matching, design redundant endpoints and explicitly rehearse the emergency path.
