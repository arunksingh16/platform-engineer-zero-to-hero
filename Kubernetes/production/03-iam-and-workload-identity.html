IAM and workload identity

“The cluster has permission” is not an identity model. Name the caller, credential, verifier, requested action and authorization policy at every boundary.

By the end you can…

Design scoped access, recognize indirect privilege escalation, trace a federated workload identity and recover from failed credential rotation.

Scenario: Kubernetes works, object storage returns 403

A reconciliation service can list Pods but cannot upload a report. Its Kubernetes RoleBinding is healthy. The application changed ServiceAccount during a namespace migration; the external trust still names the old subject. Adding cluster-admin would expand risk while leaving the cloud token exchange broken.

Human: IdP credential → API authentication → groups → authorization → admission
Workload API call: projected SA token → API audience/issuer validation → RBAC
Cloud call: projected/federated credential → external token service → cloud principal
            → resource IAM + resource policy + network boundary
Image pull: kubelet/runtime registry credentials → registry

Authentication establishes identity; authorization answers whether that identity may perform the requested action; admission evaluates an otherwise authorized object change. Cloud control-plane access, Kubernetes object access and cloud data access are separate grants. A 403 is a clue, not proof of which grant failed: service firewalls can also return it.

RBAC design includes indirect powers

CapabilityOperational consequenceDesign response
Create Pods / DeploymentsMay run as ServiceAccounts and mount Secrets available in that namespaceSeparate trust domains; constrain workload creation and privileged identities
bind, escalate, impersonateCan bypass normal grant restrictions or act as another identity when scoped that wayReview explicitly; never hide inside wildcard verbs
Secret list/watch, exec, node proxy, CSR approvalCan expose credentials or reach powerful execution pathsSeparate operational roles and audit usage
Cluster-scoped policy, CRD or webhook administrationCan change behavior for unrelated tenantsPlatform ownership; namespace editors do not need these capabilities

Prefer group-based human access and namespace RoleBindings to reusable ClusterRoles when appropriate. Avoid wildcard resources: tomorrow's CRD silently becomes part of today's grant. A namespace is not a strong tenant boundary if the tenant can run privileged host workloads. Do not use system:masters for routine access; it bypasses authorization checks rather than behaving like an ordinary revocable RoleBinding.

A minimal runnable grant

The RBAC fixture creates a ServiceAccount and a Role with get/list/watch on Pods only. After applying it in the lab, inspect both an allowed and a denied action:

kubectl --context "$CTX" auth can-i list pods -n pe-lab \
  --as=system:serviceaccount:pe-lab:observer
kubectl --context "$CTX" auth can-i get secrets -n pe-lab \
  --as=system:serviceaccount:pe-lab:observer
kubectl --context "$CTX" get rolebinding -n pe-lab -o yaml

The operator running --as needs impersonation rights. These checks evaluate authorization; they do not test actual token authentication, admission or network reachability. The lab expects “yes” then “no”; a broader preexisting binding can change the result and should be investigated.

Federation and credential lifecycle

Use short-lived projected ServiceAccount tokens with the audience required by the receiver. An API token's audience is not automatically correct for a cloud exchange. Bind trust to the exact issuer and subject, typically including namespace and ServiceAccount, and verify signing-key discovery, token lifetime and clock synchronization. Disable automatic token mounts for workloads that do not use the API; mount an explicit audience-specific projection where a supported integration needs one.

Rotation succeeds only when the running SDK or process rereads renewed credentials. Environment-variable secrets generally need process replacement; mounted files need reload behavior. Test expiry and rotation under ongoing traffic, including transient token-service failure. Keep credential revocation, trust revocation and already-issued downstream token expiry as separate timelines.

For implementation detail, follow AKS direct federation or OpenShift identity. Providers differ in token audiences, agents, annotations and credential chains; do not transplant one provider's manifest into another.

Runbook: denied cloud request

  1. Record service error code and request ID, Pod UID, namespace, ServiceAccount and recent identity changes. Do not export raw tokens or Secrets as evidence.
  2. Determine whether the failure occurs during credential discovery, exchange or the resource call. A DNS timeout precedes IAM; fix that path first.
  3. Inspect the admitted Pod's projection/injection and SDK configuration. Verify issuer, subject and audience against the external trust without printing token contents.
  4. If exchange succeeds, inspect the actual cloud principal and its narrow action/resource grant, resource policy and network restrictions.
  5. Restore the previous tested identity binding or correct the exact trust. Recreate Pods only when injection/reload requires it. Stop if the proposed fix grants unrelated resources.
  6. Verify one allowed and one denied operation, observe rotation, then remove temporary bindings and obsolete trust.

Lab and access review

Run the IAM lab. Then produce an access matrix with principal, scope, verbs, resource, owner, reason and review date. Emergency access should have an independent recovery path, short-lived issuance where supported, explicit audit evidence and a tested revocation procedure.

Review question

A team cannot read Secrets but can create Pods using any ServiceAccount in its namespace. Are the credentials isolated?

Answer

No. Pod creation can expose mounted Secrets and powerful ServiceAccount identities. Model indirect execution rights, and separate privileged identities into an appropriately controlled boundary.
