Lesson 7

Node autoscaling and Karpenter

Lessons 5 and 6 create Pods. Lesson 4 showed what happens when there is nowhere to put them: Pending, indefinitely. Something has to notice and buy a machine — and the way that is done changed significantly with Karpenter.

By the end you can…

Explain what triggers node autoscaling, say how Karpenter differs from the Cluster Autoscaler and why, describe consolidation and the disruption controls, and anticipate what breaks when nodes come and go constantly.

The trigger is a Pending Pod

Node autoscalers do not watch CPU graphs. They watch for unschedulable Pods — the exact condition lesson 4 described, where filtering leaves no feasible node and the Pod remains unscheduled until the scheduler is able to place it.

Karpenter's own summary of its job is one sentence: Karpenter's job is to add nodes to handle unschedulable pods, schedule pods on those nodes, and remove the nodes when they are not needed.

Notice the chain this completes. An HPA scales replicas on a metric → new Pods have nowhere to go → they sit Pending → the node autoscaler sees them and provisions capacity → the scheduler places them. Four controllers, none aware of the others, communicating only through the API server. Lesson 1's architecture doing real work.

The older model: node groups

The Cluster Autoscaler, which came first and is still very widely used, works through node groups — a cloud provider's own scaling group, where every machine is identical and pre-configured.

To scale, it increases the group's desired count and waits for the provider to produce a machine. That works, and it has two structural costs:

  • You choose instance types in advance. A Pod needing 1 GPU and a Pod needing 2 vCPU require different groups, so teams end up maintaining many, each with its own configuration.
  • You scale a template, not a machine. The request goes to the group and the group creates the node, which adds a layer of indirection and latency.

What Karpenter changed

Karpenter removes the group. Its docs name two improvements over the older approach.

On flexibility: it has the ability to efficiently address the full range of instance types available through AWS, where the older solution wasn't designed for hundreds of options. Rather than you pre-deciding which shapes exist, Karpenter looks at the actual Pending Pods and picks something that fits them.

On speed: it manages each instance directly, without use of additional orchestration mechanisms like node groups. This enables it to retry in milliseconds instead of minutes.

The model is "look at the work that is waiting, then buy a machine shaped like it", instead of "pick from the shapes you declared months ago".

The objects

ResourcePurpose
NodePoolDefine how Karpenter manages unschedulable pods and configures nodes — the constraints it must respect and the disruption behaviour it may use.
NodeClassThe provider-specific settings for the machines themselves.
NodeClaimRepresents individual node requests created by Karpenter. One per machine it is asking for.

A NodePool says what is allowed — instance families, architectures, zones, capacity types, limits — not what to create. Karpenter picks within those bounds based on what is actually Pending. Constrain it loosely and it can bin-pack well; constrain it tightly and you are most of the way back to node groups.

Which half of this is portable

NodePool and NodeClaim are part of the vendor-neutral core, now developed as a Kubernetes SIG project with more than one provider implementation. NodeClass is not — on AWS it is an EC2NodeClass, carrying AMI selection, subnets, security groups and instance profiles.

That line is why this course stops here. The concepts above hold anywhere; the YAML that provisions a machine does not. Provider specifics belong in the per-platform courses alongside this one.

Removing nodes is the harder half

Adding capacity is comparatively easy — there are Pending Pods, so buy something. Removing it means deciding that running workloads can be moved, which risks disrupting them.

Karpenter calls this consolidation, and performs it to actively reduce cluster cost by identifying when nodes can be removed because empty, workloads will run elsewhere, or nodes can be replaced with cheaper variants.

Three distinct moves hide in that sentence, and the third surprises people:

  1. Empty — nothing is running. Remove it.
  2. Consolidatable — everything on it fits elsewhere. Move the Pods, remove the node.
  3. Replaceable — a cheaper machine would hold the same workloads. Launch that one, move everything, remove the old.

The third means nodes can be replaced while nothing is wrong, purely for cost. Combined with the other disruption triggers — expiration, drift detection, and interruption handling — node lifetimes get much shorter than teams expect.

TriggerFires when
ConsolidationA cheaper or tighter packing exists
DriftA node no longer matches its NodePool or NodeClass spec
ExpirationA node exceeds a configured maximum lifetime
InterruptionThe provider signals the machine is going away, as with a spot reclaim

Node churn is a feature, and it will find your bugs

A cluster that constantly replaces nodes to save money is also constantly evicting Pods. Everything below is normally invisible and becomes load-bearing:

PodDisruptionBudgets — without one, nothing stops all your replicas being evicted together. Karpenter respects a PDB; it cannot respect one you never wrote.
Graceful shutdown — your app must handle SIGTERM, stop accepting work and finish in flight requests. If it exits immediately, users see errors every time a node is consolidated.
DaemonSets — every new node pays for one Pod of each. On small nodes that overhead can dominate.
Long-running jobs — a 6-hour job on a consolidatable node may be killed at hour 5. Use karpenter.sh/do-not-disrupt on Pods that genuinely cannot move.

Pending does not always mean "buy a node"

A node autoscaler only helps when more capacity would actually help. These stay Pending forever regardless of how many machines you add, and recognising them saves both money and an afternoon:

CauseWhy a new node will not fix it
Required anti-affinity, replicas > nodesA new node may help — but only if the rule is on hostname, and the cost is a node per replica
A Pod requesting more CPU than any permitted instance typeNothing in the NodePool can ever satisfy it
A node selector for a label nothing carriesUsually a typo. Check before adding capacity
Volume zone conflictThe volume exists in one zone; the node must be in that zone
NodePool limits reachedKarpenter is deliberately refusing. This is the guardrail working

Always set limits on a NodePool. Without them, one runaway Deployment with a broken readiness probe can provision machines until someone notices the bill.

✍️ Do it by hand

A cluster of 3 nodes with 8 CPU each, each about 50% allocated. A Deployment scales from 10 to 25 replicas, each requesting cpu: 1.

  1. How much free capacity exists, and how many of the new Pods fit?
  2. What state are the rest in, and what does Karpenter do?
  3. Traffic drops and the Deployment returns to 10. What does Karpenter do, and when?
  4. One node runs a 6-hour report job. What is the risk?
  5. The Deployment has a broken readiness probe and the HPA keeps scaling. What stops this?
Show answer

1) 3 × 8 = 24 CPU total, about 12 allocated, so roughly 12 free — enough for 12 of the 15 new Pods, minus whatever DaemonSets take on each node.

2) The remaining 3 are Pending. Karpenter sees unschedulable Pods and provisions a node sized for the work that is actually waiting, rather than from a fixed template.

3) Nodes become empty or consolidatable, and Karpenter removes them — possibly also replacing remaining nodes with cheaper ones that still fit the load. Not instant: it respects PodDisruptionBudgets and graceful termination.

4) Consolidation may evict it before it finishes, since the node looks like a cost saving. Mark the Pod karpenter.sh/do-not-disrupt, or run such work somewhere it will not be interrupted.

5) Only two things: maxReplicas on the HPA, and limits on the NodePool. Without the second, the cluster will keep buying machines for Pods that will never become ready.
