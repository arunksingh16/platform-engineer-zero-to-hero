Lesson 8

Operators and custom resources

Everything so far has been lesson 1's loop, written by someone else. An operator is that loop written by you, over an object you invented — and the two courses you have already done turn out to be most of the preparation.

By the end you can…

Explain what a CRD adds to the API, describe the operator pattern and why it is a control loop, say what idempotent and level-triggered mean for your reconcile function, and judge when writing one is a mistake.

Teaching the API server a new noun

A CustomResourceDefinition registers a new kind of object. Apply one and the API server starts serving a new endpoint — with validation, RBAC, kubectl support and watches, exactly like a built-in type:

kubectl get postgresclusters
kubectl describe postgrescluster orders-db

A CRD on its own does nothing. It gives you somewhere to write a spec, and the API server will dutifully store it. No database appears. You have a well-typed record in etcd and nothing watching it.

The thing that makes it real is a controller, and the two together are the pattern.

The operator pattern

From the documentation: Operators are software extensions to Kubernetes that make use of custom resources to manage applications and their components. Operators follow Kubernetes principles, notably the control loop.

And more precisely on the mechanism: the pattern lets you extend the cluster's behaviour without modifying the code of Kubernetes itself by linking controllers to one or more custom resources. Operators are clients of the Kubernetes API that act as controllers for a Custom Resource.

CRD          a new type the API server understands
   +
controller   a program that watches objects of that type and acts
   =
operator     automated operational knowledge for one application

The word "operator" is the point. It is the job a human operator used to do — provision, back up, fail over, upgrade — written down as code that runs continuously. The docs list exactly that: deploying an application on demand, taking and restoring backups of that application's state, handling upgrades of the application code alongside related changes such as database schemas, and choosing a leader for a distributed application without an internal member election process.

Note that an operator is a client of the Kubernetes API. It is an ordinary program, usually a Deployment in your cluster, holding credentials and a watch. There is no privileged plugin mechanism. KEDA is one of these. So is Karpenter.

Writing the loop correctly

A controller is one function: given the name of an object, make the world match it. Two properties make the difference between one that works and one that corrupts things at 3am.

Idempotent

Reconcile will be called many more times than things actually change — on a resync timer, on unrelated edits, on restart. It must be safe to run when there is nothing to do. So the body is never "create the StatefulSet"; it is "ensure a StatefulSet matching this spec exists", which on most calls does nothing at all.

Level-triggered, not edge-triggered

A natural instinct is to react to events: "on update, do X". That is edge-triggered, and it breaks the moment an event is missed — which happens, because controllers restart and watches drop.

Instead, reconcile reads the current desired state and the current actual state and closes the gap. It does not need to know what changed, or how many times. If your operator crashes during an upgrade and restarts, it re-reads both sides and carries on. This is the thermostat from lesson 1: it never asks why the room got cold.

Both courses prepared you for this

Lesson 1 gave you the loop. Code analysis lesson 2 gave you convergence — sweeping repeatedly until a pass changes nothing, which is what "idempotent" buys you here.

And an operator is IO all the way down, in the precise sense of that course: every reconcile reads cluster state and writes to the API server. It can never be a pure function, which is exactly why it must be safe to re-run.

Status is how it talks back

Enable the status subresource in your CRD and give the controller separate permission to update it. Status is a durable API for users and other controllers; Events, logs and metrics add operational evidence:

status:
  phase: Ready
  readyReplicas: 3
  conditions:
    - type: Available
      status: "True"
      reason: AllReplicasReady
      lastTransitionTime: "2026-11-05T09:14:22Z"

Use conditions rather than inventing a phase enum. It is the convention built-in types follow, tooling understands it, and conditions compose where a single phase field forces you to collapse independent facts into one value.

When not to write one

Operators are the most over-applied pattern in the ecosystem. The honest test is whether your application needs ongoing operational judgement that cannot be expressed as static configuration.

NeedReach for
Install an app with some values filled inHelm or Kustomize. No operator.
Keep the cluster matching gitGitOps — Argo CD or Flux.
Run a stateful app needing ordered failover, backups and version-aware upgradesAn operator — very likely one that already exists.
Expose an internal platform API to your own developersA CRD plus a controller, which is a genuinely good use.

Two cautions from practice. First, check whether one exists — databases, message brokers and certificate management are thoroughly covered, and a maintained operator encodes failure modes you have not met yet. Second, an operator is production software: scope its credentials to its actual responsibilities, and give it tests, upgrades and an on-call owner. Cluster-wide credentials are not intrinsic to the pattern. A half-maintained operator is worse than a runbook, because it acts on its own at three in the morning.

✍️ Do it by hand

You are writing a CertificateRotator operator that renews TLS certificates 30 days before expiry.

  1. Your reconcile function issues a new certificate every time it runs. What goes wrong?
  2. You restructure it as "on update event, renew". Why is that still wrong?
  3. What should the function actually do?
  4. Renewal takes 10 minutes and reconcile is called again after 30 seconds. How do you avoid a second renewal?
  5. The CA is unreachable. What do you do?
Show answer

1) It is not idempotent. Reconcile runs on resyncs and restarts, not only on changes, so you would issue certificates continuously — exhausting rate limits and churning secrets.

2) It is edge-triggered. Miss the event — controller restart, dropped watch — and the certificate silently expires. Nothing re-checks, because nothing is comparing state.

3) Read the current certificate's expiry, compare against the 30-day threshold, and renew only if needed. On the vast majority of calls it does nothing. That is a healthy reconcile function.

4) Use a stable external operation/idempotency key derived from the object's UID and renewal intent. Reconcile the CA's operation state before starting another renewal. Record the operation ID and a Renewing condition in status, using optimistic concurrency. A status flag alone cannot close the crash window between the CA accepting a request and Kubernetes recording it; it can also get stuck forever after a crash. If the CA has no idempotency support, implement discoverable external identity and explicit duplicate-recovery semantics. See production controller design.

5) Return an error so the controller retries with backoff, and set a condition explaining why. Do not crash and do not pretend it succeeded: a wrong status is worse than a visibly failing one, because everything downstream trusts it.
