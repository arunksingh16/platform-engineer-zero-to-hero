Lesson 5

Horizontal Pod Autoscaling

The HPA is lesson 1's control loop with one new trick: instead of you writing the replica count, it computes one from a metric. The formula is a single line, and knowing it exactly is the difference between trusting the autoscaler and fighting it.

By the end you can…

Apply the HPA formula by hand, explain the tolerance and the stabilization window, say why a request value from lesson 3 changes autoscaling behaviour, and choose a better signal than CPU.

The formula

This is the whole algorithm, quoted from the documentation:

desiredReplicas = ceil[ currentReplicas × ( currentMetricValue / desiredMetricValue ) ]

A ratio, scaled by the current count, rounded up. Work one through: 4 replicas averaging 80% CPU, target 50%.

ceil[ 4 × (80 / 50) ] = ceil[ 6.4 ] = 7 replicas

Note what is not in there. No PID controller, no history, no prediction, no learning. It is proportional control: the loop runs again shortly and recomputes from scratch. If 7 replicas bring the average to 46%, the next pass computes ceil[7 × (46/50)] = 7 and stops.

The target is a percentage of the request, not of the node

With averageUtilization: 50 and cpu: requests: 200m, the target is 100m per Pod — half of what the Pod asked for. The node's actual size never enters the calculation.

So changing a CPU request silently rewrites your autoscaling behaviour. Halve the request and every Pod's utilisation percentage doubles, so the HPA scales out roughly twice as far on identical traffic. Lesson 3 and this lesson are the same dial seen from two ends.

Three things that stop it oscillating

A naive proportional loop on noisy data would thrash. Three dampers prevent that, and all three are why "the HPA is slow" is usually "the HPA is working".

Tolerance: 10%

The HPA uses a tolerance of 10% (0.1) and takes no action while the metric sits within that band of the target. With a 50% target, anything from 45% to 55% is left alone. Without it, every passing fluctuation would produce a scaling event.

Sync period: 15 seconds

The controller re-evaluates on an interval — --horizontal-pod-autoscaler-sync-period, default 15 seconds. Nothing happens between passes, so the fastest possible reaction is one interval plus however long your metrics pipeline lags.

Stabilization: 5 minutes down, none up

The default scale-down stabilization window is 300 seconds. The controller looks at its recommendations over that window and picks the highest, so a brief dip in traffic cannot immediately remove Pods.

Scaling up has no such delay by default. That asymmetry is deliberate: being slow to add capacity costs you an outage, while being slow to remove it costs you a few minutes of compute. You can tune both under behavior:

behavior:
  scaleDown:
    stabilizationWindowSeconds: 300    # the default
  scaleUp:
    stabilizationWindowSeconds: 0      # the default: react at once

Where the metrics come from

The HPA computes nothing itself; it reads one of three APIs.

APIServesProvided by
metrics.k8s.ioCPU and memory per Podmetrics-server — not installed by default on most clusters
custom.metrics.k8s.ioAny metric attached to a Kubernetes objectAn adapter, commonly the Prometheus Adapter
external.metrics.k8s.ioMetrics from outside the cluster entirelyAn adapter — this is the door KEDA uses in lesson 6

If kubectl top pods does not work, neither will a CPU-based HPA; both need metrics-server. The HPA will report unknown for the metric and do nothing.

The metrics pipeline is the one from the other course

Custom metrics usually mean Prometheus plus an adapter, which is the stack in the Observability course. Scaling on request rate means a rate() query over a counter; "requests in flight" is a gauge.

The SLO lesson transfers directly too. Choosing a scaling signal is the same skill as choosing an SLI: pick something that tracks user-visible pain, and be careful what you divide by.

Why CPU is usually the wrong signal

CPU is the default because it is the metric that is always available, not because it is a good proxy for load. It fails in a specific, common way: for an IO-bound service, CPU barely moves while latency climbs. A Pod waiting on a slow database is not busy — it is blocked, using almost no CPU, and serving users terribly.

Scale on CPU and nothing happens, because by CPU there is no problem.

A second trap: an HPA on a memory target rarely does what people hope. Many runtimes hold memory after they stop needing it, so usage goes up and stays up, and the HPA scales out and never back in.

Scaling to zero

Ordinarily minReplicas must be at least 1 — the HPA holds a floor. Zero is governed by the HPAScaleToZero feature gate, which ran as alpha and off by default from v1.16, and became beta and on by default in v1.37.

So on a cluster older than that, HPA alone will not idle a workload down to nothing. That gap is a large part of why the next lesson exists.

✍️ Do it by hand

An HPA targets averageUtilization: 60 on CPU. Pods request cpu: 500m. Currently 3 replicas, minReplicas: 2, maxReplicas: 12.

  1. What CPU figure, in millicores per Pod, is the HPA aiming for?
  2. Pods average 540m. How many replicas does the formula ask for?
  3. Pods average 320m. What does the HPA do?
  4. Traffic collapses and the metric hits 10%. How long before replicas actually drop, and why?
  5. Someone lowers the request to 250m, changing nothing else. What happens on identical traffic?
Show answer

1) 60% of the 500m request = 300m per Pod. The node's size is irrelevant.

2) 540m against a 300m target is 180% — outside the 10% tolerance. ceil[3 × (540/300)] = ceil[5.4] = 6.

3) Nothing. 320/300 = 1.067, inside the ±10% tolerance band (270m–330m), so the controller takes no action even though usage is above target. This is the behaviour people report as "the HPA is stuck".

4) At least 5 minutes, the default scale-down stabilization window — the controller takes the highest recommendation across that window. Scale-up has no such delay.

5) The target becomes 60% of 250m = 150m. The same real usage now reads as double the utilisation, so the HPA scales to roughly twice as many replicas. A change to a resource request quietly re-tuned the autoscaler.
