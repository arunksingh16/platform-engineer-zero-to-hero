AKS / Lesson 3

Identity without shared secrets

“The cluster identity has access” is usually an incomplete diagnosis. An operator, the control plane, the kubelet and an application are four different callers. Trace the principal before changing a role.

By the end you can…

Identify the caller at each boundary, explain direct workload federation, and separate authentication, authorization and network failures.

Four identity paths

CallerPurposeCommon confusion
Human / deployment automationAuthenticate to the Kubernetes API through the configured Entra integrationPermission to fetch kubeconfig is not permission to read Secrets
AKS cluster identityManage supported Azure infrastructure, such as network resourcesIts Azure role is not the application's role
Kubelet identityNode-side Azure operations such as authorized ACR pullsImage pull authentication is not application authentication
Workload identityLet a specific ServiceAccount obtain a token for an Azure resourceCreating a ServiceAccount does not itself grant Azure data access

For API access, distinguish Entra authentication from authorization. The cluster may use Kubernetes RBAC or Azure RBAC for Kubernetes authorization, according to its configuration. An Azure management-plane role and a Kubernetes data-plane role solve different problems. Use namespace-scoped grants and managed group membership; treat cluster-admin as controlled break-glass access, not an onboarding default.

The direct federation chain

Pod using a named ServiceAccount
  → projected, short-lived Kubernetes token
  → Entra validates issuer + subject + audience against federated credential
  → Entra access token for the Azure service
  → service checks data-plane permissions + network access

For the direct-federation model, enable OIDC issuer and workload identity on the cluster as required by its service mode. Configure the federated credential on the intended identity with the exact issuer URL, subject system:serviceaccount:payments:reader and audience api://AzureADTokenExchange. Grant that identity the narrow data-plane role needed at the target resource. Use a supported Azure Identity SDK credential flow. Identity-binding features have a different contract; do not mix their token audiences with this model.

This review fragment shows the ServiceAccount annotation and the Pod template label. It intentionally omits the application container, identity creation and role grants; it is not a complete Deployment.

apiVersion: v1
kind: ServiceAccount
metadata:
  name: reader
  namespace: payments
  annotations:
    azure.workload.identity/client-id: "<managed-identity-client-id>"
---
# Fragment of the application's Deployment:
spec:
  template:
    metadata:
      labels:
        azure.workload.identity/use: "true"
    spec:
      serviceAccountName: reader

The workload identity webhook mutates labeled Pods to supply token projection and environment configuration. A label on only the Deployment's top-level metadata is not the Pod label. After a ServiceAccount annotation change, existing Pods need recreation to pick up the changed injection. Do not print projected tokens into logs while debugging.

Debug the boundary, not the symptom

az aks show -g example-rg -n example-aks \
  --query '{clusterIdentity:identity,kubelet:identityProfile,oidc:oidcIssuerProfile,security:securityProfile}' -o yaml
kubectl auth can-i get pods -n payments
kubectl get serviceaccount reader -n payments -o yaml
kubectl describe pod example-pod -n payments

Token exchange errors suggest issuer, subject, audience, tenant or credential propagation problems. A resource's 403 can indicate missing data-plane permission, but some firewalls also return 403: read the service error code and request ID. DNS failure or timeout points to connectivity, not a missing role. ImagePullBackOff starts with image reference, registry network access and the kubelet's pull permissions, not the application's Key Vault role.

Defense beyond identity

Enforce appropriate Pod Security Admission or supported policy controls, non-root images, minimal capabilities, restricted host access and resource quotas. Apply default-deny network policy with explicit DNS and dependency allowances on a supported enforcing dataplane. Workload identity reduces secret distribution; it does not isolate a privileged container or protect an over-permissioned ServiceAccount. Evaluate Key Vault CSI rotation and application reload behavior separately; mounting a refreshed secret does not ensure the process rereads it.

Do it by hand: a namespace migration

The app moves from payments to payments-v2. Client ID and role assignment are unchanged. Token exchange now fails. Why?

Trace the subject

The ServiceAccount subject includes the namespace. The old federated credential trusts system:serviceaccount:payments:reader, not system:serviceaccount:payments-v2:reader. Add the reviewed trust for the new subject, verify issuer and audience and retire the old trust when migration completes. Granting a broader Azure role does not fix a failed token exchange.
