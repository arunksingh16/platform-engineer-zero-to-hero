AKS / Lesson 2

Node pools and failure domains

A node pool is a lifecycle and placement boundary. Design it around what must fail, scale and upgrade together, not merely around a VM size.

By the end you can…

Separate platform capacity from tenant capacity, calculate failure headroom and explain why three replicas can still be one failure away from an outage.

System is a mode, not complete isolation

AKS requires a system pool to host critical platform Pods. User pools host application workloads. A system pool label expresses a platform role, but is not by itself a fence that prevents applications landing there. Where appropriate, use the supported CriticalAddonsOnly=true:NoSchedule taint on dedicated system capacity, and confirm the necessary system Pods tolerate it. Do not spread broad tolerations across tenant charts to silence Pending alerts.

Keep platform capacity resilient and appropriately sized; a single fragile system node can make DNS and metrics unreliable even when application nodes are idle. Check current system-pool VM, OS and count constraints in the source documentation rather than assuming any SKU is supported.

Count allocatable, not advertised cores

Kubelet and OS reservations, DaemonSets and eviction thresholds reduce usable capacity. The scheduler accounts for requests and placement constraints; kubectl top reports observed usage and cannot tell you whether another Pod fits. Include DaemonSet overhead on each new node when estimating capacity.

Zones do not place application replicas for you

Choose zones and pool topology deliberately, then use topology spread constraints or anti-affinity to distribute replicas. Node diversity is not Pod diversity. A multi-zone pool does not guarantee that the scheduler places every Deployment across zones, nor that replacement capacity will exist in the required zone during an incident.

A zonal persistent disk can constrain a Pod to the disk's zone. A hard spread rule can prevent scheduling when a zone has no capacity. Understand both availability goals and degraded-mode behavior: should the service run fewer replicas, relax spread under an approved policy, or fail closed? Test the actual rules, not a diagram.

Upgrade capacity is production capacity

During a drain, requests must fit somewhere else. A toleration only permits placement; it does not select a pool or reserve room. Use affinity/selectors when placement is required, and budget spare capacity in the same eligible failure domain. Too many tiny pools can strand capacity and complicate every upgrade.

Do it by hand: can this pool lose a node?

Four nodes each provide 6 allocatable CPU after reservations. DaemonSets request 1 CPU per node. Applications request 18 CPU in total. Assume memory, Pod slots and placement rules are not limiting. Can all application Pods fit after one node is lost?

Calculate the headroom

No. Four nodes provide 4 × (6 − 1) = 20 CPU for applications. Three provide 15 CPU, less than the requested 18. Low observed CPU does not change scheduler accounting. Reduce justified requests, add capacity or change the availability design before draining. Then repeat the calculation for memory, Pod slots and eligible zones; aggregate CPU alone is not proof of fit.
