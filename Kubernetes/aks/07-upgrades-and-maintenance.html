AKS / Lesson 7

Upgrades as a reliability exercise

An upgrade is a controlled failure test: nodes disappear, Pods move, IPs are allocated and old API assumptions are exercised. Passing it requires spare capacity and correct application behavior, not just a scheduled maintenance window.

By the end you can…

Build a preflight checklist, calculate surge, diagnose blocked drains and describe recovery without inventing an unsupported downgrade.

There is more than one lifecycle

Track Kubernetes control-plane and pool versions, node image versions, OS distribution support, CSI/networking components and ingress/add-on lifecycles separately. A supported Kubernetes minor does not make an end-of-life node OS safe. Read the current AKS release tracker and OS retirement notices; do not pin a production plan to a tutorial's version.

Query the actual upgrade path. Standard non-LTS upgrades normally proceed by consecutive minor versions; LTS has its own supported paths. Control-plane/pool version skew is constrained by AKS support policy. Manual staged control-plane/pool upgrades and cluster autoupgrade have different constraints; choose a supported workflow rather than combining recipes.

A safe sequence

  1. Compatibility: inspect removed API use in manifests, live clients and admission webhooks. Validate charts, CRDs, CSI, policy and ingress against the target release.
  2. Recovery: prove data backups and a rebuild or alternate-cluster path. A manifest backup alone is not data recovery.
  3. Capacity: reserve quota, regional SKU capacity where applicable, subnet IPs, overlay Pod blocks and eligible scheduling headroom for surge.
  4. Disruption: inspect PDB allowance, replica distribution, termination grace periods, readiness, shutdown behavior and startup time under load.
  5. Canary: rehearse in a representative non-production environment, then stage supported pool updates. A new canary pool tests scheduling/runtime compatibility, but does not reproduce every in-place drain behavior.
  6. Observe and gate: compare application error rate, latency, restarts, DNS and dependency health against explicit stop criteria before expanding rollout.

Surge and PDBs solve different problems

Surge adds temporary nodes during a rolling pool upgrade. For a percentage, fractional nodes round up: 33% of 10 nodes requires 4 surge nodes. Those nodes need both compute and network headroom. Extra nodes do not make a single-replica workload with a strict PDB evictable.

A PDB limits voluntary disruptions through the eviction API. Three healthy replicas with minAvailable: 2 permit one disruption; if one replica is already unhealthy, allowance can fall to zero. A PDB is not a replica controller and does not protect against every involuntary failure. Read disruptionsAllowed and the exact blocking event before changing anything.

Do not “fix” the upgrade by deleting every PDB

Restore healthy replicas, correct a mistaken budget through the application owner, or use a reviewed maintenance plan. A forceful bypass can convert a blocked change into a customer outage. Drain timeout and soak settings are safeguards, not proof the application can tolerate eviction.

Windows and recovery are explicit policies

Cluster Kubernetes autoupgrade and node OS/image update policies are distinct. Planned maintenance configurations determine allowed scheduling windows for their relevant operations; they are not a guarantee that every operation completes within that window or that no exceptional service maintenance occurs outside it. Check the current contract and monitor actual execution.

AKS does not provide a general “downgrade the cluster” rollback. Recovery may mean rolling back application configuration, moving workloads to a compatible pool where supported, rebuilding a cluster or failing over to a tested alternate environment. Each depends on data compatibility, DNS and available capacity. Decide the recovery path before starting.

Explain the contract

Evicting the only replica would violate the budget. Add and verify another replica if the application supports it, or coordinate an accepted maintenance interruption and a reviewed budget change. A larger VM does not create another application replica; the PDB is correctly exposing a design decision.
