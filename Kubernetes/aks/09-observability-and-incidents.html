AKS / Lesson 9

Observe, triage, improve

The senior operator's advantage is not remembering more commands. It is reducing uncertainty quickly without increasing the blast radius. Start with customer impact, localize the failed boundary and preserve evidence before changing the system.

By the end you can…

Build a layered signal map, run a bounded incident investigation and challenge a production-readiness claim with evidence.

Azure Monitor managed service for Prometheus, managed Grafana and Container Insights solve related but distinct needs. Prometheus stores time-series metrics; logs and inventory depend on configured collection and workspaces. A Grafana workspace does not itself create scrape coverage. Control-plane diagnostic categories must be enabled and routed to a destination; audit logging is not the same as the Azure Activity Log.

Choose retention, cardinality budgets, sampling and access controls before enabling every category. Audit logs and container output can contain sensitive data. Filter deliberately, restrict access and do not put tokens, raw customer payloads or unbounded request IDs into metric labels. Monitor the monitoring pipeline: missing telemetry is not a zero error rate.

A useful first ten minutes

  1. Establish impact: affected service, users, regions, error and latency SLIs, onset time and current error-budget burn. Assign incident coordination and a change log.
  2. Bound scope: one namespace, node, pool, zone, cluster or shared external dependency? Compare healthy and failing paths.
  3. Correlate changes: release, pool operation, policy, identity, route, DNS, certificate or quota changes. Correlation is a hypothesis, not proof.
  4. Collect narrow evidence: events, Pod status, controller conditions, Azure operation error and the relevant dependency's signal. Record timestamps and request IDs without secrets.
  5. Mitigate with an owner: roll back the evidenced change, add eligible capacity or shift traffic using a tested procedure. Define an observation window and stop condition.
  6. Verify the outcome: customer SLIs and consistency, not only green Pods. Preserve the timeline for follow-up.

Logs, events and object listings need different permissions and retention. “No events” after the retention window is not proof nothing failed. Capture relevant evidence early and redact it before sharing outside the approved incident channel.

Production-readiness review

  • Ownership: named owners for cluster, applications, network, identity and data, with an escalation/support path.
  • Resilience: measured failure headroom, eligible zone capacity, application placement and dependency failure domains.
  • Identity: least-privilege roles, tested break-glass, workload federation and approved policy enforcement.
  • Network: maximum/surge address budget, private DNS path, supported ingress, egress dependencies and connection capacity.
  • Lifecycle: supported Kubernetes/OS/add-ons, upgrade rehearsal, drain-safe workloads and recovery gates.
  • Recovery: recent isolated restore drill with measured RPO/RTO, key access and data validation.
  • Operations: SLO-based alerts, telemetry coverage, cost ownership and runbooks exercised by someone other than their author.

Capstone: the burst during maintenance

A pool upgrade begins. Queue age rises, HPA grows replicas and new Pods stay Pending. One node is draining; a strict PDB blocks another. The subnet has no room for more surge nodes. Write a mitigation order.

A defensible response

Establish customer impact and processing backlog, record the maintenance operation and pause further rollout through the supported workflow where possible. Do not launch conflicting AKS writes or delete PDBs. Read Pending and drain events; distinguish replica health from address capacity. Reduce incoming work or route it to a tested healthy path if possible. Restore eligible compute/IP headroom through the network and platform owners, or execute the approved alternate-capacity plan. Validate consumers and downstream capacity before increasing concurrency. Resume maintenance only after the pool and queue SLIs recover. Follow up with peak-IP budgeting, maintenance load tests and a reviewed disruption design.
