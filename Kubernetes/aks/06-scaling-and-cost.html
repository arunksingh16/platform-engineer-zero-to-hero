AKS / Lesson 6

Scaling without wishful thinking

Autoscaling is a chain of delayed control loops. A demand signal can request more Pods immediately while quota, IP capacity or a placement rule prevents new compute from ever arriving.

By the end you can…

Distinguish Pod and node scaling, diagnose a blocked scale-up and include lead time and interruption risk in the cost model.

Keep each controller's job separate

ControllerDecisionNot its job
HPADesired replicas from configured resource/custom/external metricsCreate Azure nodes or fix an unsuitable metric
KEDAEvent-driven activation and HPA integration for a targetGuarantee downstream throughput or provision VM capacity
Cluster AutoscalerGrow/shrink eligible existing pools within configured boundsIgnore scheduling rules or scale merely because a node has high observed CPU
Node autoprovisioningSelect/provision capacity under its supported node-pool constraintsRemove Azure quota, IP limits or SKU shortages

AKS node autoprovisioning uses Karpenter-based concepts, but the Azure-specific provider objects and service constraints differ from EKS examples. Do not copy an EC2NodeClass. Check supported combinations, migration requirements and ownership before enabling it. Do not let Cluster Autoscaler, a separate VMSS autoscaler and another capacity controller compete over the same resources.

Start with the exact scheduling failure: insufficient memory, an untolerated taint, affinity mismatch, topology constraint, Pod slots or volume topology. Then ask whether any eligible pool can produce a node that solves it. Increasing the maximum of a general pool does not help a GPU-only Pod. A 20 GiB request will not fit a node with 16 GiB allocatable memory, even when its observed usage is near zero.

The Cluster Autoscaler profile is a cluster-level tuning surface. Scan intervals, scale-down delays and utilization thresholds trade response speed against churn and disruption. Do not reduce every delay to “make it faster.” First establish the service's latency budget, normal burst duration and node provisioning lead time. Inspect the currently supported profile values in the reference.

Lead time is part of reliability

Consider a burst that must be served within 30 seconds. Metrics collection, HPA reconciliation, unschedulable detection, Azure allocation, node bootstrap, image pull and application warmup may take longer. Minimum replicas and warm node capacity buy response time. Scale-to-zero is useful for suitable asynchronous work, not a free answer to a synchronous tail-latency SLO.

For queue consumers, estimate sustainable processing rate and oldest-message age, not just queue length. Add consumers only if the downstream database or API can accept the concurrency. Multiple controllers must not independently own replica count for the same target; KEDA creates/manages the HPA it uses.

Cheapest node is not cheapest reliable service

Spot capacity fits interruptible workloads with retries, checkpoints and duplicate-safe processing. Keep a deliberate non-Spot baseline where required. PDBs do not guarantee protection from involuntary infrastructure loss. Include stranded pool capacity, disks, load balancers, NAT, telemetry ingestion and network transfer in cost review. Measure cost per useful request or completed job alongside the error budget.

Do it by hand: why did twelve replicas not help?

HPA grows from 4 to 12 replicas. Eight are Pending. The pool is at its maximum and all eligible nodes lack requested memory. Current CPU is only 30%. What should you change first?

Separate the loops

Confirm the memory requests and pool limits, then check quota, SKU and IP headroom for an approved capacity increase. If requests are inflated, right-size them using evidence rather than deleting them. CPU is irrelevant to the memory fit. Do not tune the HPA interval or keep raising its maximum: the replica decision already happened. Validate both scheduling and end-to-end service performance after mitigation.
