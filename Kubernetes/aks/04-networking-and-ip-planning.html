Azure CNI and IP planning

An IP shortage can look like a compute shortage. Adding quota will not fix an exhausted subnet, and adding a larger subnet will not fix a hard placement constraint. Budget each resource independently.

By the end you can…

Compare overlay and flat address consumption, calculate a bounded capacity model and distinguish IP allocation from policy enforcement.

Three designs with different budgets

DesignPod addressesPlanning consequence
Azure CNI OverlaySeparate Pod CIDR, not VNet Pod addressesNode subnet needs node IPs; overlay CIDR allocates a /24 block per node, including surge nodes
Azure CNI node-subnet / traditional flatFrom the node subnetBudget node plus configured Pod IP allocation for all maximum and surge nodes
Azure CNI Pod SubnetFrom a distinct VNet Pod subnetSize node and Pod subnets separately; dynamic and static-block allocation have different rules

With Overlay, traffic leaving the cluster is translated to node addresses; an external client cannot simply route to an overlay Pod IP as if it were a VNet NIC. Expose a Service through an appropriate frontend. Choose non-overlapping node, Pod, Service, peered and on-premises ranges; address overlap can cause traffic to take the wrong path even if creation succeeds.

Cilium is not an address-plan alternative. Azure CNI powered by Cilium changes the dataplane and policy implementation. Overlay versus flat describes address allocation and connectivity. Inspect both settings. A NetworkPolicy object does nothing without a compatible enforcing implementation, and enforcement details depend on the configured dataplane.

Play: peak node count, not today's count

This model assumes one IPv4 pool with a surge count expressed as an integer, and a /24 overlay block per node. Enter the planned autoscaler maximum, not merely the current node count. It compares minimum demand before shared infrastructure, Azure-reserved subnet addresses, other pools or allocation slack. It is not a subnet recommendation or a model of Pod Subnet dynamic allocation.

Upgrade IP budget

Peak nodes = maximum regular nodes + additional surge nodes
Traditional flat demand = peak nodes × (1 + maxPods)
Overlay node-subnet demand = peak nodes
Overlay Pod CIDR allocation = peak nodes × 256 addresses

For 20 + 5 nodes and maxPods 30, the traditional flat model needs 775 addresses before other consumers. Overlay needs 25 node addresses plus 25 /24 Pod blocks (6,400 Pod-range addresses). Reducing maxPods does not shrink Overlay's per-node /24 allocation. An overlay /20 contains only 16 /24 blocks, so it cannot support that 25-node peak.

Provisioning is a conjunction

A node needs VM-family quota, regional SKU availability, subnet capacity and, for Overlay, a Pod block. Check all of them before changing the pool maximum. Include concurrent pool upgrades and blue/green migration overlap in the real design. Network-mode migrations have documented prerequisites and disruptive steps; they are not an emergency toggle.

Do it by hand: failed surge

A traditional flat pool has 10 nodes, maxPods 30 and maxSurge 3. The shared subnet has 80 free addresses. Ignoring every other consumer, can all three surge nodes be allocated?

Calculate the extra demand

No. Three nodes need 3 × (1 + 30) = 93 additional addresses under this model. Eighty is insufficient before any additional reserve. Lowering surge may reduce peak demand but lengthens maintenance and still requires safe workload eviction. Rework the capacity plan rather than deleting unrelated resources for emergency IPs.
