Traffic, egress and private DNS

“Networking is broken” is not a hypothesis. Name the source, destination, protocol, port, resolved address and failed hop. Then test the narrowest boundary that can explain the symptom.

By the end you can…

Trace inbound and outbound traffic, separate private API access from workload exposure and identify a SNAT-capacity incident.

Inbound: follow the actual architecture

Client DNS → chosen frontend / WAF / load balancer
  → ingress or gateway implementation, if present
  → Service backend selection → ready endpoint → application
  → downstream dependency

A Kubernetes Service of type LoadBalancer is not automatically an HTTP router, a WAF or a TLS certificate manager. L4 load balancing and L7 ingress/gateway routing have different owners. Application Gateway-based designs may place backends differently from an in-cluster proxy design; inspect your selected controller rather than forcing every packet into this simplified diagram.

For each hop, write down who terminates TLS, which hostname the certificate covers, where health probes land and whether traffic is public or internal. If TLS terminates at the frontend, decide whether the backend also needs TLS and how trust is validated. An internal load balancer is not authentication. Choose a currently supported ingress/gateway implementation and check its lifecycle; an old tutorial is not a support statement.

Private control plane is not private everything

A private AKS API changes how operators and deployment agents reach the Kubernetes API. They need a valid network path and DNS resolution for that endpoint. It does not by itself make every application frontend internal, and it does not make outbound traffic private. Keep API exposure, workload ingress and workload egress as three separate decisions.

Private endpoints for services such as Key Vault also require the correct private DNS zone links and forwarding paths. From the actual calling environment, inspect the resolved address and compare it with the intended endpoint. A valid token does not route packets. A reachable public address does not prove that the private path works.

Outbound: routing plus translation plus authorization

AKS outbound behavior depends on its configured outbound type: managed load-balancer outbound rules, NAT Gateway or user-defined routing are not interchangeable. In a UDR design, verify the next hop, firewall policy, return path and the documented AKS outbound dependencies. Blocking required management endpoints can affect image pulls, bootstrap and upgrades, not just application HTTP calls.

SNAT maps many outbound flows onto a finite set of source ports and public addresses. High connection churn, slow downstreams and poor pooling can exhaust usable translation capacity. More replicas may make this worse. Correlate failure rate with connection counts, outbound metrics and the shared egress device before increasing Pod count. Connection reuse, bounded concurrency and appropriate NAT capacity address different parts of the problem.

EndpointSlice readiness narrows a missing-backend fault; it does not prove that network policy allows traffic or that the process is healthy beyond its readiness probe. Use approved diagnostic tooling in the source namespace to check DNS, TCP and TLS separately. Avoid installing privileged debugging containers or weakening policy as the first response.

Do it by hand: 504 after a database slowdown

The frontend returns 504 after exactly its configured timeout. The application is Ready, and database latency rose first. Should you just double the frontend timeout?

Trace the budget

No. A longer timeout can accumulate more in-flight work and deepen saturation. Compare request traces, database latency, pool wait time and connection limits. Mitigate the slow dependency or shed load safely; align application and proxy timeout/retry budgets. Readiness is not a guarantee of fast dependencies. Confirm improvement with end-to-end latency and error SLIs, not only disappearance of the 504 code.
