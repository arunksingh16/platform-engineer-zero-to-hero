The managed-service contract

A managed control plane removes machines from your pager. It does not remove dependencies from your service. Separate “Azure accepted the change” from “Kubernetes converged” and “customers can use the application.”

By the end you can…

Map a failure to its owner, distinguish the two control surfaces, and explain why changing an AKS-managed VM directly is not a durable fix.

Two APIs, three kinds of health

Azure Resource Manager → AKS resource and node pool lifecycle
Kubernetes API         → workload desired state and reconciliation
Customer request       → DNS + network + workload + dependencies

A successful ARM operation means the resource operation succeeded. A Deployment can still have zero ready replicas. Conversely, an Azure operation can fail while existing Pods keep serving traffic. Keep provisioning state, Kubernetes health and application SLIs separate in dashboards and incident reports.

The node resource group is not your playground

AKS uses a separate node resource group for infrastructure such as VM scale sets, load balancers and disks. Its name is often generated, but can be customized. Discover it instead of constructing a name. Resources there are AKS-managed; do not resize a scale set, delete a load balancer rule or install a hand-maintained node fix as your desired-state system. AKS operations can overwrite unsupported changes.

Read the effective configuration, not the creation command someone remembers. Record subscription, region, resource ID, service mode, control-plane access path, network mode, identities and pool ownership in the runbook. Do not copy tokens or kubeconfig credentials into tickets.

Standard versus Automatic

Standard exposes more explicit choices for pools, networking, scaling and lifecycle. Automatic supplies opinionated configuration and more managed operations. That changes which settings you can tune, not whether you must validate workload readiness and recovery. Do not copy a Standard surge or node-pool recipe into Automatic without checking its contract. Similarly, a pricing/SLA tier is not the same concept as the service mode.

Availability is a chain

An API-server SLA is not an application SLA. One replica, a zone-bound database, an expired certificate or a blocked egress path can each break your service while the managed API remains healthy. Model those dependencies before buying a higher tier as the “fix.”

Do it by hand: green cluster, failed checkout

The AKS resource says Succeeded. All nodes are Ready. Checkout fails after a firewall change. What evidence separates a platform incident from an application incident?

Work through it

Measure checkout errors and dependency latency first. Compare the change timestamp with Pod readiness, restarts and scheduling events. Trace application DNS and outbound connectivity to the payment dependency; inspect firewall denies, routes and SNAT capacity. Involve the network owner with the destination, timestamp and correlation ID. Neither Ready nodes nor a green ARM operation proves that path works. Prefer reverting the correlated firewall change through its owner over restarting every Pod.
