Lesson 1

Desired state and the control loop

Kubernetes has a reputation for being enormous. It is — but almost all of it is one idea repeated. Learn the idea properly now and the other eight lessons are variations on it, including the ones about autoscaling and operators.

By the end you can…

Explain the difference between spec and status, describe what a controller does, say why Kubernetes is declarative rather than imperative, and predict what happens when something in the cluster breaks.

You describe the destination, not the journey

Most tools you have used are imperative: you issue commands and they run. ssh web01 && systemctl restart nginx does a thing, once. If the process dies an hour later, nothing brings it back, because nothing recorded that you wanted it running.

Kubernetes is declarative. You do not say "start three copies". You write down "three copies should exist" and leave it written down. Something else makes it true, and keeps making it true.

Every object in Kubernetes has two halves, and the whole system is the gap between them:

FieldWho writes itMeans
specYouWhat should be true
statusThe clusterWhat is actually true right now
spec:
  replicas: 3          # you wrote this: what you want
status:
  replicas: 2          # the cluster wrote this: what there is
  readyReplicas: 2

That mismatch is not an error state. It is the normal, expected condition of a running system, and it is the thing that makes work happen.

The control loop

A controller is the thing that closes that gap. The Kubernetes documentation describes controllers as control loops that watch the state of your cluster, then make or request changes where needed, where each one tries to move the current cluster state closer to the desired state.

It borrows the term from engineering: In robotics and automation, a control loop is a non-terminating loop that regulates the state of a system. The docs reach for a thermostat, and it is worth taking the analogy seriously:

The thermostat

When you set the temperature, that's telling the thermostat about your desired state. The actual room temperature is the current state. The thermostat acts to bring the current state closer to the desired state, by turning equipment on or off.

Note what the thermostat does not do. It does not compute a heating schedule in advance. It does not care how the room got cold — open window, failed boiler, winter. It observes, compares, acts, and then does it again. That indifference to history is the source of Kubernetes' self-healing, and also of its most confusing behaviour.

Written out, every controller in the system does this:

loop forever:
    observe   current state
    compare   against spec
    act       to reduce the difference

That is the whole pattern. The Deployment controller runs it over ReplicaSets. The ReplicaSet controller runs it over Pods. The HorizontalPodAutoscaler in lesson 5 runs it over replica counts. Karpenter in lesson 7 runs it over nodes. An operator you write in lesson 8 runs it over whatever you invent.

You have met this loop in another course

In Code analysis lesson 2 you propagated IO marks through a call graph by sweeping repeatedly until a sweep changed nothing. Same shape: observe, act, repeat, converge. The difference is that a call graph is finite and stops, while a cluster never does — nodes fail, traffic shifts, so the loop is deliberately non-terminating.

Where the state lives

Controllers do not talk to each other. They all talk to one place.

ComponentJob
API serverThe only way in. Validates and serves every object. Everything else is a client.
etcdThe database behind the API server. Where spec and status are actually stored.
Controller managerRuns the built-in controllers — Deployment, ReplicaSet, Job and dozens more.
SchedulerDecides which node each new Pod should run on (lesson 4).
kubeletOn every node. Starts the containers it has been assigned and reports back what they are doing.

This matters more than it looks. Because controllers only read and write objects through the API server, nothing has to know about anything else. The scheduler never calls the kubelet. It writes a node name onto a Pod; the kubelet on that node notices a Pod assigned to it and acts. Components communicate by changing shared state, not by issuing commands.

That is why kubectl apply returns instantly. It did not deploy anything. It updated a record, and the loops took it from there.

Watch it converge

Change the desired count, or break something, and watch the loop respond. Nothing here is scripted — the controller only ever compares the two numbers and acts on the difference.

A ReplicaSet controller, slowed down

desired: 3

Steady. Current state matches spec, so the controller has nothing to do — it keeps checking anyway.

Three consequences worth internalising

Deleting things does not work the way you expect

kubectl delete pod web-xyz deletes the Pod. Seconds later there is a new one, with a different name. You did not fight Kubernetes and lose; you removed a Pod while leaving a written instruction saying three should exist. The loop did exactly its job. To actually reduce the count, change the spec.

Failure and change are the same event

A node dying and you editing replicas both show up identically: current state no longer matches desired state. The controller does not distinguish them, which is why you get self-healing for free rather than as a separate feature.

Nothing is instant, and that is on purpose

Loops have intervals. Controllers batch work, back off when they fail, and converge over seconds rather than immediately. When lesson 5's autoscaler appears slow, it is not broken — you are watching a loop with deliberate damping, for reasons that lesson will make painfully clear.

✍️ Do it by hand

A Deployment has spec.replicas: 5. Right now status.readyReplicas: 5.

  1. A node holding 2 of those Pods loses power. What does status show, and what does the controller do?
  2. You run kubectl delete pod on one healthy Pod. What happens, and why?
  3. You edit the Deployment to replicas: 2. Is this different in kind from case 1 or the same?
  4. Someone scales to 50 and every new Pod sits in Pending. Is the controller broken?
  5. Why does the API server not simply tell the kubelet to start a container?
Show answer

1) status drops towards 3. The gap is now 2, so the ReplicaSet controller creates 2 replacement Pods, which the scheduler places on surviving nodes. No human action required.

2) A replacement appears almost immediately. You changed current state, not desired state — and only the spec decides what should exist.

3) The same in kind, opposite direction. The controller sees current 5, desired 2, and deletes 3. It has no concept of "failure" versus "intent".

4) No. The controller's job is to create the Pod objects, and it did. Placing them is the scheduler's job, and Pending means it cannot find anywhere to put them — lesson 4, and the trigger for node autoscaling in lesson 7.

5) Because then the API server would need to know which kubelets exist, whether they are reachable, and what to do when one is not. Instead it stores a fact; each kubelet watches for facts about itself and acts. Components stay independent and restartable.
