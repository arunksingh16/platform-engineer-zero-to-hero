Lesson 14

Operations: etcd, monitoring, logging, debugging

This is the lesson you will reread at 3am. The control plane's health reduces to etcd, so start there; then the monitoring that tells you something is wrong, the logging that tells you why, and the toolkit that gets data off a node when the API itself is unreachable.

By the end you can…

Read etcd health and size, take and secure a backup, describe the restore procedure and when it is required, configure and route platform and user-workload alerts, forward logs sensibly, and collect evidence before changing anything.

etcd: the single point you must understand

Three members, Raft consensus, one on each control-plane node, managed by the cluster-etcd-operator. A write needs a majority: two of three. Lose one member and the cluster continues with no quorum risk but no slack; lose two and the API cannot accept writes. Running Pods continue to run — kubelets do not need etcd — but nothing new can be scheduled, scaled or healed.

Space and defragmentation. etcd keeps revisions and compacts them periodically; compaction frees logical space but not file size, which is returned by defragmentation, a blocking operation on the member. Recent releases defragment automatically when fragmentation crosses a threshold; if you defragment by hand, do it one member at a time, the leader last, never during an update. Growth is nearly always a symptom — a tenant creating objects without bound (lesson 13) — so fix the source, not just the file.

Backup and restore

The documented backup runs on one control-plane node and produces a snapshot plus the static-Pod resources needed to restore:

oc debug node/<control-plane-node> -- chroot /host \
  /usr/local/bin/cluster-backup.sh /home/core/assets/backup
# copy snapshot_*.db and static_kuberesources_*.tar.gz OFF the node, to storage outside the cluster
  • Take it before every update and on a schedule (a CronJob or your fleet tooling; recent releases add a declarative backup API). Keep several generations.
  • A backup is valid for restore on the same OpenShift version it was taken from. A backup from before an update restores a pre-update cluster.
  • It contains cluster state, including Secrets: encrypt and access-control it as you would a root credential.
  • It does not include your application data or PVC contents (lesson 12).

When to restore. Rarely. One lost member is not a restore: remove the bad member's Machine (or follow the replacement procedure), and the operator rebuilds it. A full restore, cluster-restore.sh on a chosen recovery node with the other control-plane static Pods stopped first, is for loss of quorum, data corruption, or recovery from a failed update. It rewinds the cluster to the backup moment: objects created after it vanish, so expect to reconcile workloads and then restart kubelets and operators in the documented order. Rehearse it on a non-production cluster at least yearly; the first time must not be the real one.

Monitoring: two Prometheus stacks

openshift-monitoring                   cluster/platform stack
  prometheus-k8s (2 replicas), alertmanager-main (3), thanos-querier,
  kube-state-metrics, node-exporter, prometheus-operator, telemeter-client
openshift-user-workload-monitoring     OPTIONAL, for your applications
  prometheus-user-workload, thanos-ruler, its own operator

Enable user-workload monitoring in the cluster-monitoring-config ConfigMap in openshift-monitoring (enableUserWorkload: true). Platform and tenant metrics are deliberately separate so tenant cardinality cannot damage platform alerting. Configure the same ConfigMap for the parts you must tune:

data:
  config.yaml: |
    enableUserWorkload: true
    prometheusK8s:
      retention: 15d
      volumeClaimTemplate: {spec: {storageClassName: fast, resources: {requests: {storage: 200Gi}}}}
      nodeSelector: {node-role.kubernetes.io/infra: ""}
      remoteWrite: [{url: "https://mimir.example.com/api/v1/push"}]
    alertmanagerMain:
      volumeClaimTemplate: {spec: {resources: {requests: {storage: 10Gi}}}}
  • Persist Prometheus. The default is ephemeral; a restart loses history. Set a PVC, sized by retention and series count.
  • Remote write for the fleet. A cluster's Prometheus is not your fleet view; ship metrics to a central store (Thanos, Mimir, a managed service) for cross-cluster SLOs and long retention.
  • Alert routing. Alertmanager's config lives in the alertmanager-main Secret (or the console). Define receivers (PagerDuty, Slack, email) and routes by severity. A fresh cluster raises AlertmanagerReceiversNotConfigured until you do. Wire the always-firing Watchdog alert to a dead-man's-switch so you learn when alerting itself is broken.
  • Tenant rules. Tenants write PrometheusRule objects in their own namespace; set sample limits (enforcedSampleLimit) so one tenant's cardinality cannot overload the user-workload Prometheus.
  • Query across it. thanos-querier (exposed by a Route) fans out to both stacks and is the endpoint for Grafana and tooling.

Logging

The current logging stack (Red Hat OpenShift Logging 6.x) is collector-plus-store and is installed through operators: the Cluster Logging / Observability operator deploys a Vector collector DaemonSet configured by a ClusterLogForwarder (API observability.openshift.io/v1); the Loki Operator runs LokiStack as object-store-backed storage; the console plugin queries it. The older Elasticsearch and Fluentd paths are deprecated or removed in this generation.

  • Three input classes: application (Pod logs from tenant namespaces), infrastructure (openshift-*, kube-*, node journal), and audit (API server, node, OVN). Audit logs are sensitive and high volume; forward them straight to a SIEM.
  • Outputs: LokiStack, Splunk, Kafka, Elasticsearch, CloudWatch, Google Cloud Logging, syslog, OTLP. Forward to your central platform; cluster-local retention should be short.
  • The collector is a privileged consumer. It needs ServiceAccount permissions (collect-application-logs, collect-infrastructure-logs, collect-audit-logs ClusterRoles) bound explicitly — review them.
  • Mind the cost. Log volume and label cardinality dominate cost. Drop noisy debug logs at the collector, and use structured logs with a small label set.

Evidence before action

In an incident the pull to "restart something" is strong and often destroys the evidence. Before you change anything: oc adm must-gather --dest-dir=... (it works while the API is up), capture oc get co,mcp,nodes,csr -o yaml, and note the exact time. If the API is down, collect crictl logs from the etcd and kube-apiserver containers and journalctl from the nodes. Then mitigate. A fix that cannot be explained afterwards is a fix that will recur.

✍️ Do it by hand

At 03:00 etcdHighFsyncDurations fires, then KubeAPIErrorBudgetBurn. oc get co shows several operators Progressing. A teammate proposes restoring the last etcd backup "to get back to a good state". Metrics show etcd leader changes every few minutes and DB size is 2.1 GiB of an 8 GiB quota. A node-level graph shows one control-plane node's disk latency spiking when a nightly backup job runs on that node.

  1. Should you restore?
  2. What does the evidence point to?
  3. What do you do now and what changes permanently?
  4. Where was the backup job a mistake?
Show answer

1) No. Quorum is intact and the data is healthy: 2.1 GiB of 8 GiB, members available. A restore rewinds the cluster and is for quorum loss or corruption, not instability.

2) Disk latency on one control-plane node is starving etcd's fsync, which produces leader elections, which slow the API, which makes operators look unhealthy. The operators are the symptom.

3) Stop the competing I/O now. If the leader is on that node, a controlled leader move can help. Verify fsync p99 recovers. Permanently: move backup copy work off the control-plane disk or throttle it, give etcd a dedicated fast device, and alert on fsync p99 and leader changes.

4) A heavy job — writing a snapshot and copying it — ran on a control-plane node's disk without regard for etcd latency. Backups should be scheduled to off-peak, rate-limited, and transferred from a different disk or by streaming off-node; just never on the same device as the WAL during peak writes.
