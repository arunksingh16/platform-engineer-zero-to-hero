Lesson 6

Updates, channels and lifecycle

An OpenShift update is one command and several hours of coordinated reconciliation across the control plane, the operating system and every operator. The command is easy. The skill is the preparation before it and the judgement about what to do when one phase stalls.

By the end you can…

Choose a channel, read the update graph including conditional risks, run a pre-update checklist, explain the order the platform updates in, plan an EUS-to-EUS update with paused pools, mirror content for a disconnected cluster, and describe the real recovery options.

Channels and the graph

A cluster subscribes to a channel, set in ClusterVersion.spec.channel. The CVO polls the Red Hat Cincinnati update service for the set of releases that are valid next steps from your current version. That graph is curated: Red Hat adds and removes edges as problems are found.

ChannelWhat lands in itUsed for
candidate-4.xRelease candidates, before general availabilityTest and lab clusters
fast-4.xReleases as soon as they are generally availableEarly production adopters, non-critical
stable-4.xReleases promoted after additional telemetry signalsMost production
eus-4.yOnly on even-numbered minor releases designated Extended Update SupportFleets that update once a year or so, EUS to EUS

Switching channels does not update anything; it changes which targets oc adm upgrade offers. Changing from stable-4.17 to stable-4.18 is the usual way to "unlock" the next minor version.

Some edges are conditional updates: the target is known to have a risk that affects only clusters matching a condition (a certain platform, a particular configuration). The graph evaluates the condition against your cluster; if you match, the update is shown as not recommended, with a link to the issue. You can still choose it with --include-not-recommended, and that is an informed risk acceptance, not a default.

The pre-update checklist

  1. Read the release notes for every minor you will cross — deprecations, removed APIs, behavioural changes.
  2. oc get clusterversion -o yaml — look for Upgradeable=False, and read its reason. Common ones: an unacknowledged API removal (the admin ack ConfigMap in openshift-config asks you to confirm), an operator that is not compatible with the next minor, or a pool that is paused.
  3. Removed APIs in use. The APIRemovedInNextReleaseInUse and APIRemovedInNextEUSReleaseInUse alerts and oc get apirequestcounts tell you which clients still call a deprecated API. Fix the callers; an update that removes an API they use will break them.
  4. All ClusterOperators healthy (Available=True Degraded=False) and all MachineConfigPools Updated. Starting on a Degraded cluster is how an update becomes an incident.
  5. Operators installed through OLM are compatible: many declare a maximum OpenShift version, and the update will be blocked or the operator will break. Upgrade them first where required (lesson 7).
  6. Capacity and PDBs. You are about to drain every node. Confirm headroom, and that no PDB allows zero disruptions on a workload that must not stop.
  7. An etcd backup, taken and copied off the cluster (lesson 14). This is your recovery path, not a formality.
  8. Certificates and CSRs in good order; no stuck pending requests.

What actually happens, in order

  1. You set the desired release (oc adm upgrade --to=4.18.9, or the console). The CVO pulls the release image and verifies its signature.
  2. The CVO applies manifests in run-level order. etcd and the kube-apiserver are updated first, each by its operator rolling a new revision across the control-plane nodes one at a time.
  3. The remaining operators update — network, ingress, authentication, console, monitoring, storage, and the rest — each reporting Progressing and then healthy before the CVO continues.
  4. The machine-config operator publishes a new rendered config that includes the new OS image. The control-plane pool rolls first (one node at a time, each drained and rebooted), then workers per pool settings.
  5. When every operator reports the new version and every pool is updated, ClusterVersion goes Progressing=False.

The time budget is dominated by node reboots, not by operators. A control-plane roll is usually sequential and short; worker time is nodes × per-node time ÷ maxUnavailable (lesson 5's calculator).

Within a minor release (z-stream, 4.18.3 → 4.18.9) the same mechanics apply. Minor updates (4.17 → 4.18) must be taken one minor at a time, except for the documented EUS-to-EUS path.

EUS-to-EUS: skipping a minor safely

Between two designated even-numbered releases (for example 4.16 → 4.18), you can update the control plane through the intermediate minor while workers stay on the old OS:

  1. Pause the worker (and any custom) MachineConfigPools.
  2. Update the control plane 4.16 → 4.17 → 4.18 through the CVO. Workers are not rebooted for each step.
  3. Unpause the pools; the workers roll once to the 4.18 OS.

Result: one worker reboot cycle instead of two, which for a large bare-metal fleet is days saved. The constraints are real: the version skew between control plane and kubelets must stay within Kubernetes' supported skew, pools can only be paused for a limited time, and every workload still has to tolerate the intermediate API surface. Follow the documented procedure for your exact pair.

Canary and fleet strategy

At fleet scale, do not update everything on the same day. A defensible pattern: a lab cluster on candidate, a canary production cluster that takes releases first on fast, then the main fleet on stable after the canary has soaked. Inside a cluster, a canary MachineConfigPool lets you validate the new OS on a few nodes before the rest. Track a release's soak time in telemetry from your own environment — not just Red Hat's.

Disconnected clusters

A cluster with no internet cannot reach Cincinnati or the release registry. You mirror content and provide a local update service:

  • oc-mirror mirrors a declared set of releases, operator catalogs and additional images into your registry from an ImageSetConfiguration.
  • Cluster resources generated by it (ImageDigestMirrorSet, ImageTagMirrorSet, CatalogSource) redirect image pulls to the mirror. These replace the older ImageContentSourcePolicy.
  • The OpenShift Update Service (OSUS) operator runs a local Cincinnati so the cluster still sees an update graph.

Mirror catalogs and release content before the maintenance window, and mirror the complete upgrade path, including intermediate minors and any operator versions you will need.

There is no rollback button

For the general case, Red Hat does not support rolling a cluster back to a previous minor version. Your options are to update forward to a fixed release, or to restore the cluster from an etcd backup taken before the update — a control-plane disaster-recovery procedure with its own requirements (the backup must be from the same version, with a coherent set of control-plane nodes). Some narrow rollback paths have appeared in recent releases; do not plan on them without reading the current docs.

This is why the backup in the checklist is not optional, and why a canary cluster is your real rollback strategy: you learn about a bad release on a cluster you can afford to lose.

✍️ Do it by hand

You run 4.16 on 12 bare-metal clusters with 40 workers each and want 4.18 by the end of the quarter. Per-node reboot time is about 20 minutes, and you may lose 4 workers per cluster at once.

  1. Which path do you take, and what do you pause?
  2. How many worker reboot cycles does that save per cluster?
  3. Roughly how long is the worker roll per cluster?
  4. oc adm upgrade refuses the minor step with Upgradeable=False: AdminAckRequired. What is happening?
Show answer

1) EUS-to-EUS 4.16 → 4.18. Pause the worker pool (and any custom pools) before updating the control plane, and unpause it after the control plane reaches 4.18. Workers roll once.

2) One cycle saved: the normal path would reboot workers for 4.17 and again for 4.18; EUS-to-EUS reboots them once.

3) 40 nodes ÷ 4 per wave = 10 waves × 20 min ≈ 3.3 hours of worker roll, excluding the control-plane phase and drains that run slowly because of PDBs.

4) The release notes include a change that could affect your workloads (commonly an API removal). The platform requires an administrator to acknowledge it in the admin-acks ConfigMap in openshift-config after you have verified nothing depends on the removed behaviour. It is a deliberate gate; verify first, then ack.
