Lesson 5

The Machine Config Operator

Every change to a node — a kernel argument, a chrony file, a kubelet setting, an OS update — travels the same path: a MachineConfig is merged into a rendered config, a pool rolls it out one node at a time, and each node drains, writes, and (usually) reboots. If you do not know that path, a harmless-looking YAML will reboot your fleet.

By the end you can…

Describe the MCO's components and how a rendered config is made, predict how long a rollout takes and what stops it, choose when to pause or use a custom pool, and diagnose a Degraded or stuck pool.

The pieces

ComponentJob
MachineConfig (mc)A named fragment of desired node state: Ignition files and units, kernel arguments, extensions, FIPS, and a kernel type. You write these.
Machine Config ControllerMerges all MachineConfigs matching a pool, in lexical name order, into one rendered-<pool>-<hash> object. Also runs the pool's rollout and node selection.
MachineConfigPool (mcp)A set of nodes (by label) plus the MachineConfigs they share. Defaults: master and worker.
Machine Config Daemon (per node)Cordons and drains, writes files, applies OS updates via rpm-ostree, reboots, then validates on-disk state.
Machine Config ServerServes the current rendered Ignition to new machines during first boot.

The naming convention matters: MachineConfigs are merged in lexical order, and later wins on a conflict. Platform-owned ones are 00- to 99- prefixed; yours should sit near the end, 99-worker-chrony, and never collide with a file the platform owns.

One change, end to end

1. oc apply -f 99-worker-chrony.yaml          # a MachineConfig labelled for the worker pool
2. Controller renders rendered-worker-7f3a...  # new hash because content changed
3. Pool "worker" desired = new rendered; UPDATING
4. For each node, up to maxUnavailable at a time:
     MCD: cordon → drain (respects PDBs) → write files → rpm-ostree → reboot
     node returns → MCD validates → annotates state=Done → uncordon
5. Pool reports UPDATED when every node's current == desired

Look at the status you will actually watch:

$ oc get mcp
NAME     CONFIG                    UPDATED  UPDATING  DEGRADED  MACHINECOUNT  READY  UPDATED  UNAVAIL
master   rendered-master-1a2b      True     False     False     3             3      3        0
worker   rendered-worker-7f3a      False    True      False     30            27     27       1

Node annotations machineconfiguration.openshift.io/currentConfig, desiredConfig and state (Done, Working, Degraded) tell you exactly where each node is.

Does this reboot me?

By default, assume yes. The daemon is conservative because it cannot know whether a changed file matters at runtime. Several classes of change have long been special-cased to avoid a reboot — SSH key updates, pull-secret changes, and image mirror (ImageDigestMirrorSet / ImageTagMirrorSet) changes handled with a CRI-O reload, for example. Recent releases add node disruption policies in the MachineConfiguration API so you can declare which files or units need only a service reload or no action. Check your version before relying on it; and test on a canary pool.

The fleet-level consequence: any change to the worker pool is a rolling drain and reboot of every worker. Batch your changes. Ten separate MachineConfigs applied across a day is ten rollouts; ten applied together while paused is one.

Model the rollout

Rollout time and PDB blocking

At maxUnavailable: 1 a 100-node pool takes roughly a day. Raising it speeds things up and shrinks your capacity margin in exact proportion — set it from how many nodes' worth of headroom you can lose, not from impatience. It accepts a percentage, which scales as the pool grows.

Custom pools: separate schedules and blast radius

Create a pool that inherits worker configs and adds its own, with a label selector over a node role such as infra or canary:

apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfigPool
metadata: {name: canary}
spec:
  machineConfigSelector:
    matchExpressions:
      - {key: machineconfiguration.openshift.io/role, operator: In, values: [worker, canary]}
  nodeSelector:
    matchLabels: {node-role.kubernetes.io/canary: ""}
  maxUnavailable: 1

Two reasons to do this. Canary: new configuration reaches a few nodes first, while the main pool is untouched. Update control: you can pause the big pool and update only the control plane during a cluster upgrade, then let the pool roll at a time you choose. Pausing (spec.paused: true) holds the pool's rollout; it must be unpaused before you can complete a minor update, and certificates on a long-paused pool can expire — do not leave pools paused for weeks.

A node can belong to only one pool. If a node matches several selectors, the pool selection becomes ambiguous and the MCO refuses to proceed; keep selectors disjoint.

KubeletConfig and friends

You change kubelet behaviour through a KubeletConfig object whose machineConfigPoolSelector targets a pool by label on the pool itself. The MCO then generates a MachineConfig with the result. The same pattern gives you ContainerRuntimeConfig (CRI-O: PID limits, log size, default ulimits), and the Node Tuning Operator handles sysctls and tuned profiles without reboots where possible.

apiVersion: machineconfiguration.openshift.io/v1
kind: KubeletConfig
metadata: {name: worker-limits}
spec:
  machineConfigPoolSelector:
    matchLabels: {pools.operator.machineconfiguration.openshift.io/worker: ""}
  kubeletConfig:
    maxPods: 250
    podPidsLimit: 4096

Common mistake: a KubeletConfig whose selector matches nothing. It produces no error; the pool just never changes. Check oc get kubeletconfig -o yaml for status.conditions and check the generated 99-worker-generated-kubelet exists.

When a pool is stuck or Degraded

SymptomLikely causeFirst look
Pool UPDATING for hours, one node cordonedDrain blocked by a PDB or a Pod that will not terminateoc -n openshift-machine-config-operator logs <daemon> -c machine-config-daemon; oc get pdb -A
Pool Degraded, unexpected on-disk stateSomeone edited a managed file by handDaemon log names the file; revert it, or touch /run/machine-config-daemon-force as documented
Node NotReady after rebootBoot or network failure, or pending CSRs after long downtimeConsole; oc get csr
Pool rendering errorsInvalid Ignition or two MachineConfigs conflictingoc describe mcp, controller logs
Nothing happens at allPool is paused, or selector matches no nodesoc get mcp -o yaml | grep paused

The one habit that prevents most of this: drains block because of workload design, not platform fault. A PDB set to allow zero disruptions on a single-replica app is a promise the platform will not break, and it will wait forever. Fix the workload, not the pool.

✍️ Do it by hand

You must add a kernel argument to all 60 workers. Capacity analysis says you can lose 6 nodes. Each node takes about 15 minutes. A pager-sensitive team runs a database on 3 of the workers with a PDB of minAvailable: 3 on 3 replicas.

  1. With maxUnavailable: 6, what is the best-case duration?
  2. What will the PDB do to the rollout?
  3. How do you get the DB nodes through safely?
  4. What would you do before touching production at all?
Show answer

1) 60 / 6 = 10 waves × 15 min = ~2.5 hours best case.

2) minAvailable: 3 of 3 means no replica may be evicted, so the drain of any DB node never completes and the MCO waits. Because maxUnavailable counts cordoned nodes, one stuck DB node holds a slot for the rest of the rollout; the pool appears frozen.

3) Do not remove the PDB casually. Put the DB nodes in a dedicated pool and roll them separately, one at a time with an operator-driven switchover (fail over, update the node, fail back), or temporarily relax the PDB with a plan for the replica being unavailable. The rule is: the app owner decides how many replicas can go.

4) Apply the same MachineConfig to a small canary pool first, confirm the node returns Ready and the kernel argument is present (cat /proc/cmdline), then widen. Batch any other pending changes into the same rollout.
