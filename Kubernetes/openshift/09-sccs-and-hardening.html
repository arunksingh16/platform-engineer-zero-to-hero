Lesson 9

SecurityContextConstraints and hardening

Most "it works on Kubernetes but not on OpenShift" tickets are the same ticket: the image wants to run as root. SCCs are the reason, and they are also the best control you have against a compromised workload becoming a compromised node. This lesson is about reading them, not just granting anyuid until the error goes away.

By the end you can…

Explain how an SCC is selected for a Pod, read the UID range on a namespace, predict which SCC admits a workload, avoid the anyuid priority trap, relate SCCs to Pod Security Admission, and run through a hardening checklist.

What an SCC is

A SecurityContextConstraints object is a cluster-scoped policy describing what a Pod may ask for: which UIDs, which Linux capabilities, whether it may use the host network, host PID, host paths, privileged mode, which volume types, which SELinux context and seccomp profile. It is both a validator (reject Pods that exceed it) and a mutator (fill in defaults, such as a UID).

Authorisation to use an SCC is ordinary RBAC: the verb use on the resource securitycontextconstraints by name. You grant it to a ServiceAccount (or user or group) with oc adm policy add-scc-to-user — which creates the RBAC for you — or by writing the Role and RoleBinding yourself. The admission plugin considers the SCCs available to the Pod's ServiceAccount and to the requesting user.

UID ranges: why your image gets a random user

On namespace creation, OpenShift assigns three annotations:

$ oc get ns payments -o yaml | grep openshift.io/sa.scc
openshift.io/sa.scc.mcs: s0:c26,c10
openshift.io/sa.scc.supplemental-groups: 1000680000/10000
openshift.io/sa.scc.uid-range: 1000680000/10000

The range is a block of 10,000 UIDs unique to that namespace, and the MCS label is the SELinux category pair that isolates its containers from other namespaces' containers on the same node. With restricted-v2 and no runAsUser in the Pod, the first UID in that range is assigned. The process runs as an arbitrary non-root UID with GID 0 as an extra group.

What follows for image authors: files that the process must write need group-0 write permission (chgrp -R 0 /data && chmod -R g=u /data), the image cannot rely on /etc/passwd containing the running UID, and binding to ports below 1024 needs NET_BIND_SERVICE or — better — a high port. SELinux isolation between namespaces comes from the MCS pairs; disabling SELinux enforcement on a node removes it.

Which SCC admits this Pod?

The algorithm: gather the SCCs the Pod's ServiceAccount and requester may use, order them by priority (highest first), then by restrictiveness, and take the first that can validate the Pod, applying its mutations. Try it below — especially with anyuid granted.

The anyuid trap

Because anyuid has priority 10, once a ServiceAccount may use it, it is chosen before restricted-v2 for every Pod it can admit — including Pods that did not ask for anything unusual. Its UID strategy is RunAsAny, so a Pod with no runAsUser runs as whatever the image's USER says, which is often root. Granting anyuid to "fix" one image silently makes the whole ServiceAccount run root everywhere. Use a dedicated ServiceAccount per such workload, grant the narrowest SCC that works, and fix the image when you can.

SCCs and Pod Security Admission

Upstream Kubernetes' Pod Security Admission (PSA) enforces three profiles — privileged, baseline, restricted — through namespace labels. OpenShift runs both. SCCs remain the authoritative control; to keep PSA from fighting them, a label-sync controller sets each namespace's PSA labels to the strictest profile that matches the SCCs its ServiceAccounts can use. Namespaces whose names start with openshift-, and those you opt out of with security.openshift.io/scc.podSecurityLabelSync: "false", are not synced.

Two consequences. First, a workload may be admitted by SCC and still produce a PSA warning in oc apply output; read it, as it tells you the Pod is less restricted than the cluster would like. Second, if you manage PSA labels in Git for a namespace, turn off the sync for it or the two controllers will fight forever.

✍️ Do it by hand

A vendor image requires UID 1001 and writes to /var/lib/app. A developer grants anyuid to the default ServiceAccount in payments. A week later a security scan shows several unrelated Pods in that namespace running as root.

  1. Why are unrelated Pods now running as root?
  2. What is the smallest SCC that fits the vendor image?
  3. What does the filesystem need for it to work under a random UID?
  4. Where do you find out which SCC admitted a running Pod?
Show answer

1) anyuid has priority 10, so for any Pod using the default ServiceAccount it is evaluated first and chosen; its RunAsAny UID strategy leaves each image's USER alone, and many images default to root.

2) nonroot-v2 — it accepts any non-zero UID such as 1001 and keeps everything else restricted. Grant it to a dedicated ServiceAccount used only by that Deployment.

3) With the fixed UID under nonroot-v2, the directory must be writable by 1001 (or via a group in fsGroup through a PVC). If the app later runs under restricted-v2 with a random UID, the directory must be group-0 writable.

4) The Pod annotation openshift.io/scc names the SCC. oc get pod x -o jsonpath='{.metadata.annotations.openshift\.io/scc}'. Use oc adm policy scc-subject-review -f pod.yaml to predict it before deploy.
