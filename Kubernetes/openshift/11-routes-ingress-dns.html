Lesson 11

Networking II: Routes, routers and DNS

North-south traffic on OpenShift enters through the router: HAProxy Pods managed by the Ingress Operator. Routes are the native API; Ingress and Gateway API are layered over them. Most "the app is down" tickets are not the app — they are a timeout, an admission conflict, or a router that lost its endpoints.

By the end you can…

Describe the path of a request, size and shard routers, choose a route termination type, find which layer cut a long request, debug 503/502/504 in order, and explain how the API and ingress VIPs and cluster DNS work.

The path of a request

client ─► DNS  *.apps.cluster.example.com  ─► cloud LB / keepalived VIP
       ─► router Pod (HAProxy) on an infra/worker node
       ─► endpoint Pod IP directly (not the Service ClusterIP)
       ─► application container

Notice the router talks to Pod endpoints directly, read from EndpointSlices, so it bypasses Service load balancing and can do its own balancing, health tracking and session stickiness. It also means a Route with a Service whose endpoints are empty gives you the router's "Application is not available" 503 page, not a Kubernetes error.

IngressController: how the router is run

The router is declared by IngressController objects in openshift-ingress-operator. There is always a default, and you may add more for shards or different networks.

apiVersion: operator.openshift.io/v1
kind: IngressController
metadata: {name: internal, namespace: openshift-ingress-operator}
spec:
  domain: internal.apps.example.com
  replicas: 3
  endpointPublishingStrategy:
    type: LoadBalancerService
    loadBalancer: {scope: Internal}
  nodePlacement:
    nodeSelector: {matchLabels: {node-role.kubernetes.io/infra: ""}}
    tolerations: [{key: node-role.kubernetes.io/infra, operator: Exists}]
  routeSelector: {matchLabels: {exposure: internal}}
  namespaceSelector: {matchLabels: {tier: internal}}
  tuningOptions: {threadCount: 8, maxConnections: 50000, clientTimeout: 30s, serverTimeout: 30s}
  tlsSecurityProfile: {type: Intermediate}
  defaultCertificate: {name: internal-wildcard}
SettingWhat it decides
endpointPublishingStrategyLoadBalancerService (cloud LB, External or Internal), HostNetwork (router binds node ports 80/443; used on bare metal behind a VIP), NodePortService, Private
routeSelector / namespaceSelectorSharding: which Routes this router serves. Disjoint shards give blast-radius isolation: a noisy tenant cannot exhaust the router that serves payments.
nodePlacementRun routers on infra nodes; spread across failure domains with topology spread settings
tuningOptionsHAProxy threads, connection cap, client/server timeouts, reload interval
tlsSecurityProfile, defaultCertificateCipher/protocol floor and the wildcard cert presented for edge routes

Scaling the router is a real capacity decision: HAProxy reloads when routes change, and a cluster with thousands of routes and frequent changes reloads constantly. Shard by tenant or by traffic class when route count, connection count, or churn crosses what one router set can handle comfortably, and watch the router's own metrics (connections, reload duration, backend up/down) rather than node CPU alone.

Routes, Ingress, Gateway API

  • Route (route.openshift.io) — host, optional path, target Service and port, and a TLS termination block. Rich knobs through annotations (haproxy.router.openshift.io/*).
  • Ingress — standard. The Ingress Operator creates managed Routes from Ingress objects, so you can use portable manifests; advanced features still require Route annotations or Route objects.
  • Gateway API — the successor to Ingress. Recent OpenShift releases support it through the Ingress Operator and an Istio-based implementation. Adoption depends on your release and your need for features Routes lack, such as richer traffic splitting. Check support status before building on it.

Admission and host claims

The router admits a Route only if its host is allowed. By default, hosts are claimed per namespace: the first namespace to use shop.example.com/api owns that host, and with the default InterNamespaceAllowed policy another namespace may claim different paths on the same host, which lets tenants hijack each other's paths. Setting routeAdmission.namespaceOwnership: Strict restricts a host to one namespace. A Route that is rejected shows its reason in status.ingress[].conditions (Admitted: False), which is where to look first when a Route "does nothing".

Which layer cut the request?

A long request that dies has several candidate killers: the client, the cloud LB idle timeout, the router's timeout, and the application. The router's default server/response timeout is 30 seconds, overridable per Route with haproxy.router.openshift.io/timeout (and timeout-tunnel for upgraded connections like WebSockets). Whichever layer has the smallest limit fires first:

Timeout stack

Fix by raising the smallest limit that is wrong — or, better, by making a request that takes a minute asynchronous. Remember that every layer after the router, including a service mesh, can also have its own timeout.

The API VIP and the ingress VIP

On public clouds, the API (api.cluster.example.com, port 6443, and the internal api-int) and the router sit behind cloud load balancers the installer created. On bare metal IPI, there is no cloud LB: the platform runs keepalived on control-plane (API VIP) and router-hosting (ingress VIP) nodes with HAProxy, and the VIPs move with VRRP. On UPI you provide external load balancers yourself, and their health checks, TLS passthrough on 6443 and 22623, and api-int reachability for nodes become your responsibility.

The api-int endpoint matters: nodes and operators use it, and a mis-set LB that works for humans on api but not for api-int yields nodes that cannot join or update.

Cluster DNS

CoreDNS runs as a DaemonSet dns-default in openshift-dns, serving the Service IP (typically 172.30.0.10). The DNS Operator (operator.openshift.io/DNS) lets you forward specific zones to corporate resolvers, set upstream resolvers, and tune caching. Remember ndots:5 in Pod /etc/resolv.conf: a lookup like api.partner.com tries several search-suffix variations first, multiplying DNS load and latency; use fully qualified names with a trailing dot for hot paths, or lower ndots in the Pod's dnsConfig.

The *.apps wildcard is a record created by the Ingress Operator in the cloud DNS zone (via a DNSRecord), or by you on bare metal. A cluster that comes up with all operators healthy but whose console is unreachable usually has a missing or wrong wildcard record.

✍️ Do it by hand

A batch-export endpoint takes 70s. Users on the Route get a 504 at 30s. Raising the Route timeout to 120s fixes it for most — but a handful still drop at 60s from inside the corporate network, and a second tenant reports their Route "stopped working" after a teammate created a Route for the same hostname.

  1. Which layer produced the 504, and what is the fix?
  2. What is likely cutting the remaining requests at 60s?
  3. What is the better long-term design?
  4. What explains the second tenant's problem and how do you prevent it?
Show answer

1) The router's default 30s server timeout. Set haproxy.router.openshift.io/timeout: 120s on that Route only — a cluster-wide increase ties up router connections for every tenant.

2) A 60s idle timeout on a layer outside the cluster: the cloud load balancer in front of the router (a common default) or a corporate proxy. Raise it where it is set, or avoid the long idle connection.

3) Make the export asynchronous: return 202 with a job id, poll or notify, and download the result. Long synchronous requests tie up router and app connections and fail in many layers.

4) A host collision. With the default inter-namespace policy another namespace can claim a different path on a hostname, or if the router was not strict, conflicting Routes get arbitrated by age, so the older one wins. Set routeAdmission.namespaceOwnership: Strict on the IngressController and check status.ingress[].conditions on the rejected Route.
