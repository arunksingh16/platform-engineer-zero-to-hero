Lesson 8

Identity: OAuth, groups and RBAC

Kubernetes has no users; it trusts whatever authenticates a request. OpenShift ships the thing that authenticates: an OAuth server that federates your corporate identity provider and issues tokens. Understanding where a human's identity becomes a username, a group and a token is what lets you answer an access review — and shut down a leaked credential.

By the end you can…

Trace a login from identity provider to token, configure an IdP without locking yourself out, remove kubeadmin safely, sync groups, apply least-privilege RBAC patterns, and audit who can do what.

The login path

user ─► oc login / console
         │
         ▼
  oauth-openshift (authentication operator runs it, behind a Route)
         │   redirects to the configured identity provider
         ▼
  IdP (LDAP, OIDC, GitHub, HTPasswd, ...)  ──► authenticates
         │
         ▼
  OAuth server creates/updates:  Identity  →  User  (+ Group membership)
         │
         ▼
  OAuthAccessToken  (sha256~… token; opaque; revocable)

Three things to take from that. First, the token is opaque and stored in etcd as an OAuthAccessToken object; revoking access means deleting that object (oc delete oauthaccesstoken) or the user, not waiting for a JWT to expire. Second, the default maximum token age is 24 hours (spec.tokenConfig.accessTokenMaxAgeSeconds in the OAuth config), and inactivity timeouts are configurable; shorter is better for human users. Third, because authentication goes through a Route, a broken router breaks logins — recall lesson 3's dependency chain.

Identity providers

TypeNotes
OpenID ConnectPreferred for modern SSO. Map a claim to the username and groups. Sync of group claims is increasingly supported in newer releases.
LDAPBind-and-search. Groups are synced separately (below). Mind TLS and bind-account hygiene.
HTPasswdA Secret-backed local user file. Fine for break-glass, lab and bootstrap; not for a fleet.
GitHub / GitLab / Google / Keystone / Request headerEach has its own limits; request-header is for an authenticating proxy and is dangerous if the proxy is bypassable.
External OIDC (direct)Newer releases let the API server trust an external OIDC issuer directly and bypass the built-in OAuth server. Check your version and the trade-offs before adopting.
spec:
  tokenConfig: {accessTokenMaxAgeSeconds: 28800, accessTokenInactivityTimeout: 30m}
  identityProviders:
    - name: corp-sso
      mappingMethod: claim          # claim | lookup | add — see below
      type: OpenID
      openID:
        clientID: openshift
        clientSecret: {name: oidc-secret}
        issuer: https://sso.example.com
        claims:
          preferredUsername: [preferred_username]
          groups: [groups]

mappingMethod is a quiet security decision. claim (default) fails if a user with that name already exists from another provider — protects against takeover. add merges identities from several providers into one User — convenient, and a route to account confusion. lookup requires users to be pre-provisioned. Choose deliberately, and never use add when one provider's usernames are user-controlled.

Do not lock yourself out

The classic failure: you replace the only IdP with a mis-typed one, then cannot log in, and the cluster has no kubeadmin (removed) and no kubeconfig. Rules that prevent it: keep a break-glass path (the installer's kubeconfig with its client certificate stored in a vault), test the new IdP with a non-admin account while still holding an admin session, and add before you remove.

kubeadmin and the installer kubeconfig

The installer creates a temporary kubeadmin user (a password hash in the kubeadmin Secret in kube-system) and an admin kubeconfig with a client certificate. Once a real IdP and at least one real cluster-admin group exist, delete the kubeadmin Secret. The kubeconfig certificate remains valid and is the true emergency credential; protect it as the root credential it is. Rotating it means regenerating the signer, a documented but disruptive procedure.

Groups and sync

Identity is useless for authorization unless humans are grouped. OpenShift has a Group object (not just a claim) and can sync from LDAP with oc adm groups sync. A recurring problem is drift: someone removes a user from the directory, but the OpenShift group still lists them. Run the sync on a schedule (a CronJob or your GitOps tooling), prune stale groups, and reconcile cluster-admin membership against the directory often.

RBAC patterns that survive a review

  • Bind to groups, never users. A RoleBinding naming individuals is a time bomb for the next access review.
  • Prefer RoleBindings over ClusterRoleBindings. A ClusterRole bound with a RoleBinding limits it to one namespace — the easiest least-privilege win.
  • Know the built-in project roles: admin (manage a project and its RBAC), edit (modify most resources, no RBAC), view (read-only), and the dangerous cluster ones, cluster-admin and self-provisioner.
  • edit on a namespace is stronger than it looks. It lets a user create Pods and read Secrets, which on a namespace with a powerful ServiceAccount means they can run code as that account — the classic privilege-escalation path. Pair with SCCs (lesson 9) and admission policy.
  • Remove self-provisioner from system:authenticated:oauth if you do not want every user able to create projects (lesson 13).
  • Watch verbs that escalate: impersonate, bind, escalate, create on pods with any ServiceAccount, and use on a powerful SCC.
oc adm policy who-can get secrets -n payments           # who can read secrets here
oc adm policy who-can use scc privileged                 # who can run privileged Pods
oc auth can-i --as system:serviceaccount:ci:deployer create pods -n payments
oc get clusterrolebinding -o json | jq '.items[] | select(.roleRef.name=="cluster-admin") | .subjects'
oc adm policy scc-subject-review -f pod.yaml             # which SCC would admit this

ServiceAccounts and tokens

ServiceAccounts are how workloads authenticate. On current releases, tokens mounted into Pods are bound, time-limited and audience-scoped (projected volumes), not the old never-expiring Secrets. Long-lived token Secrets still exist and are a standing credential if you create one; avoid them, and prefer short-lived tokens or workload identity (cloud STS) for anything external. Audit for kubernetes.io/service-account-token Secrets as part of a periodic review.

Audit and encryption

The API server audit policy is a profile on config.openshift.io/APIServer: Default (metadata only), WriteRequestBodies, AllRequestBodies, or None — richer profiles produce more data and log volume, and capture Secret payloads at the higher levels. Pick by risk and ship the logs off-cluster. Etcd encryption (aescbc or aesgcm) is off by default; turn it on and watch the operators' Encrypted progress conditions. It protects data at rest in etcd, not against anyone with API access.

✍️ Do it by hand

A contractor in the contractors group left the company. Their directory account is disabled. At the next review you find they still hold edit on payments, and a RoleBinding to the user jlee. Also a developer asks to "just get cluster-admin to debug quicker".

  1. Why does the contractor still have access?
  2. What do you do about already-issued tokens?
  3. How do you fix the structural problem with jlee?
  4. What do you offer the developer instead of cluster-admin?
Show answer

1) Disabling the directory account stops new logins. The OpenShift Group membership is a separate object, and the OAuthAccessToken already issued stays valid until it expires. If groups were never re-synced, the user also remains in the group.

2) Delete the user's OAuthAccessToken objects (oc get oauthaccesstokens --field-selector userName=…), then the User and Identity. Shorten token lifetimes so this window shrinks.

3) Replace the user binding with a group binding and make group membership come from the directory by scheduled sync, so a joiner/leaver process drives access instead of ad hoc edits.

4) Scoped access: edit or admin on their project, view on neighbours, oc debug only on a non-prod namespace, and a time-boxed, audited elevation process (for example a PIM-style group with an expiry) for genuine break-glass. Cluster-admin on a shared platform is never a convenience.
