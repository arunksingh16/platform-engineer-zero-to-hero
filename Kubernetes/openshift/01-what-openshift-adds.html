Lesson 1

What OpenShift adds to Kubernetes

The shortest accurate description is: OpenShift is a Kubernetes distribution whose administrator is software. The operating system, the API server's flags, the ingress layer, the monitoring stack and the upgrade itself are all managed by operators that will undo what you edit by hand. Internalise that and most of the platform's behaviour stops being surprising.

By the end you can…

Say what OpenShift contributes beyond upstream, name the two API families that configure it, locate the operator that owns any given subsystem, and list the habits from vanilla Kubernetes you must drop.

The product map, so the names stop blurring

NameWhat it is
OKDThe community upstream. Same architecture, community-supported, FCOS/CentOS Stream CoreOS nodes.
OpenShift Container Platform (OCP)The supported product you install and run yourself, on bare metal, VMware, a public cloud, or at the edge.
Managed OpenShiftROSA (AWS), ARO (Azure), OpenShift Dedicated (GCP/AWS). The provider runs the control plane lifecycle; you still own workloads, quotas, identity, and a lot of what this course covers.
Hosted control planesAn architecture, not a product: the control plane runs as Pods on a separate management cluster (lesson 2).

Do not assume managed means "someone else's problem". Managed offerings restrict what you can change (often cluster-admin is replaced by a narrower dedicated-admin), so a fix that is a one-liner on a self-managed cluster may need a support ticket on ROSA.

What is actually added

  • An immutable, operator-managed OS. Nodes run Red Hat Enterprise Linux CoreOS (RHCOS). You do not SSH in and edit files; configuration is declared and the Machine Config Operator applies it (lessons 4–5).
  • Operators all the way down. The Cluster Version Operator reads a release image and drives dozens of "cluster operators" — one each for the API server, etcd, ingress, DNS, networking, authentication, storage, monitoring, console and more (lesson 3).
  • A built-in identity layer. An OAuth server, User, Identity and Group objects, and a default kubeadmin break-glass user (lesson 8).
  • SecurityContextConstraints. A stricter, older precursor to Pod Security, enforced by admission and granted through RBAC (lesson 9).
  • Routes and the router. The pre-Ingress way of exposing HTTP(S), implemented by HAProxy and still the primary interface (lesson 11).
  • Projects, quotas and templates for tenancy (lesson 13), plus the integrated registry and ImageStreams, a layer that tracks image tags and triggers rollouts when they move.
  • OLM and OperatorHub for installing software as operators with managed upgrades (lesson 7).
  • One opinionated monitoring stack (Prometheus, Alertmanager, Thanos Querier) and a supported logging stack (lesson 14).

The control plane, as you will actually meet it

3 control-plane nodes (schedulable only in compact clusters)
  static Pods, each reconciled by its own operator:
    etcd                 ← cluster-etcd-operator
    kube-apiserver       ← cluster-kube-apiserver-operator
    kube-controller-mgr  ← cluster-kube-controller-manager-operator
    kube-scheduler       ← cluster-kube-scheduler-operator
  Deployments (the aggregated / OpenShift-specific APIs):
    openshift-apiserver, oauth-apiserver (aggregated API servers)
    oauth-openshift      (the login server, run by authentication operator)
    machine-config-server/controller
  Singletons everywhere else:
    cluster-version-operator   ← drives all of the above from the release image

You may remember static Pod manifests on /etc/kubernetes/manifests as the thing you edit to change an API server flag. On OpenShift the kube-apiserver static Pod is rendered from a revision managed by the operator. Edit the file on disk and the operator's installer Pod overwrites it on the next revision; there is no supported way to hand-tune flags. You change an API object instead, and the operator rolls a new revision across the three nodes one at a time.

Two API families, and the difference matters

config.openshift.io — cluster-wide configuration, always a singleton named cluster: APIServer, Authentication, Console, DNS, Image, Infrastructure, Ingress, Network, OAuth, Project, Proxy, Scheduler, ClusterVersion, FeatureGate. This is what you edit.

operator.openshift.io — the operator's own configuration and status: IngressController, DNS, Network, KubeAPIServer, Etcd, Console. This is where you set operator-specific behaviour (replicas, node placement, log levels) and where managementState lives.

The rule of thumb: policy goes in config; how an operator runs goes in operator; observed health is in ClusterOperator. Nothing you want is ever in a Pod spec the operator owns.

Find the owner

On a production incident the first question is "who reconciles this?" Pick a symptom or subsystem and see where to read and where to change it.

✍️ Do it by hand

A teammate says "the ingress is flaky, I bumped the router Deployment to 6 replicas with kubectl scale and it went back to 2 after a minute." Another wants to "just add a flag" to the kube-apiserver on one control-plane node.

  1. Why did the replica count revert?
  2. Where is the supported place to set router replicas?
  3. What happens to the hand-edited kube-apiserver flag?
  4. Which API family would you edit to change the cluster's default image registry allow-list?
Show answer

1) The router Deployment is owned by the Ingress Operator, which reconciles it to match the IngressController custom resource. The CR said 2 replicas; the operator is the source of truth, not the Deployment.

2) oc -n openshift-ingress-operator patch ingresscontroller/default --type=merge -p '{"spec":{"replicas":6}}' — an operator.openshift.io object.

3) It is lost the next time the kube-apiserver operator rolls a new revision, because the static Pod manifest is rendered from the operator's revision. Worse, mutating it by hand mid-revision can cause the node's installer to fail and the operator to report Degraded. Flags that are meant to be tunable are exposed through config.openshift.io/APIServer or operator.openshift.io/KubeAPIServer (such as audit profile, encryption, and log level).

4) config.openshift.io/Image (spec.registrySources with allowedRegistries). Cluster-wide policy lives in the config family.
