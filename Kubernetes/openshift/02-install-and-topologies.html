Lesson 2

Installation, topologies and hosted control planes

Installation is a design review in disguise. Several fields in install-config.yaml can never be changed on a running cluster, and the topology you pick decides your failure domains for years. Get these wrong and the fix is a rebuild.

By the end you can…

Choose between IPI, UPI, Assisted and Agent-based installs, pick a topology (standard, compact, SNO, hosted), size the cluster and service networks so they do not strand you, and say which day-1 choices are effectively permanent.

How an install actually works

openshift-install takes install-config.yaml and generates manifests and Ignition files. A temporary bootstrap node boots first and runs a minimal control plane that brings up the three real control-plane nodes, which pull the release payload, form an etcd quorum, and take over. Once the real control plane is healthy the bootstrap node is destroyed, the Cluster Version Operator starts rolling out every other operator, and wait-for install-complete returns.

Everything on the cluster after that moment is reconciled by operators from the release image. The installer is not involved again, which is why the install-time options are so consequential: the platform was built around them and there is no "reinstall this one part".

The practical consequence of IPI versus UPI is lesson 4: IPI gives you MachineSets, autoscaling and MachineHealthChecks, which is what lets nodes be disposable. On UPI you get a pile of Nodes and no controller that replaces them.

Newer small-footprint topologies (for example two-node designs with an arbiter) keep appearing in recent releases. Treat their support status as release-specific and check the current docs.

Hosted control planes

In a classic cluster each cluster carries three dedicated control-plane machines. With hosted control planes (the HyperShift project, shipped as "hosted control planes" in OpenShift and underlying ROSA HCP), a HostedCluster object on a management cluster causes the API server, etcd, controller managers and OAuth to run as Pods in a dedicated namespace there. Worker nodes are described by NodePool objects and join across the network.

  • Density and cost. Tens or hundreds of control planes share one set of management nodes, so you stop paying for three idle machines per cluster.
  • Speed. A control plane is a set of Pods; it starts in minutes, not as a node install.
  • Stronger tenancy. A tenant gets their own control plane and etcd. That is the hard-isolation answer in lesson 13.
  • Different blast radius. The management cluster is now a shared dependency. If it fails, hosted clusters keep serving workloads but cannot be managed; if it is compromised, every hosted control plane is exposed. Treat it as tier zero.

install-config.yaml: the fields that bite

apiVersion: v1
baseDomain: example.com            # permanent: the API and *.apps DNS hang off this
metadata: {name: prod-east}        # permanent: cluster name is baked into DNS and infra tags
networking:
  networkType: OVNKubernetes
  clusterNetwork:
    - {cidr: 10.128.0.0/14, hostPrefix: 23}   # pod IPs: size once
  serviceNetwork: [172.30.0.0/16]              # ClusterIP space: size once
  machineNetwork: [{cidr: 10.0.0.0/16}]        # where nodes live
controlPlane: {name: master, replicas: 3}
compute: [{name: worker, replicas: 3}]
capabilities:
  baselineCapabilitySet: None      # opt out of optional components up front
  additionalEnabledCapabilities: [Ingress, marketplace, NodeTuning]
credentialsMode: Manual            # CCO: cloud credentials approach (see below)
fips: false                        # permanent: FIPS mode is an install-time choice
platform: {aws: {region: us-east-1}}
pullSecret: '...'
sshKey: '...'

The following are effectively permanent: base domain, cluster name, platform and region, FIPS, and the overall network type plus the pod and service CIDRs. Some CIDR knobs can be extended in later releases, but do not design around that; plan to be right on day 1. The machineNetwork and node IPs depend on your environment and can change with the infra, but the cluster and service networks cannot collide with anything the cluster must reach, including on-prem ranges across a VPN.

Cloud credentials: who may the cluster act as

The Cloud Credential Operator (CCO) has three modes. Mint uses an admin credential to create narrowly scoped per-component credentials. Passthrough shares one credential everywhere — simple and over-privileged. Manual (with short-lived tokens: AWS STS, Azure Workload Identity, GCP Workload Identity Federation) means no long-lived cloud secret is stored in the cluster; you pre-create the roles with ccoctl. For a high-assurance estate, manual/short-lived is the target, and it must be chosen at install.

Capabilities

Optional platform components (console, marketplace, insights, baremetal, and others) can be excluded at install with baselineCapabilitySet and enabled later but not removed again. Smaller footprint means a smaller update and attack surface — worth deciding deliberately.

Size the networks before they size you

Each node takes a slice of the cluster network equal to the hostPrefix. The maximum node count falls out of the arithmetic, and so does the Pod headroom on each node. Try it.

Pod and service network calculator

✍️ Do it by hand

A platform team proposes clusterNetwork: 10.128.0.0/16, hostPrefix: 23 "to leave room for other uses of 10/8". They expect about 120 nodes in two years.

  1. How many nodes can this cluster ever hold?
  2. How many Pod IPs does each node get?
  3. Can they fix it by adding nodes? By editing the config later?
  4. You must connect the cluster to an on-prem network using 172.30.0.0/16. What is wrong?
Show answer

1) A /16 split into /23 slices gives $2^{23-16}=2^{7}=128$ node slices. That holds 120 nodes but leaves almost no room for growth, replacement during rolling updates (a surge node needs a slice), or an autoscaler burst. Real headroom here is about 8 slices.

2) A /23 is 512 addresses, usable around 510. With a default of 250 pods per node that is ample, but note the per-node range is fixed once chosen.

3) No. The CIDR and host prefix are install-time design inputs; adding nodes only consumes slices. Some releases allow extending the cluster network, but it is a delicate, version-specific procedure — plan to be right at install.

4) 172.30.0.0/16 is the default service network. A collision between the ClusterIP range and an on-prem route means Pods cannot reach on-prem hosts in that range, or reach the wrong thing. Choose a non-overlapping service network at install; also check the internal join/transit/masquerade subnets in lesson 10.
