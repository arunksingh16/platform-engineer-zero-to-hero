Lesson 13

Multi-tenancy

Sharing a cluster is an economic decision wearing a technical costume. Namespaces make it cheap to give teams a slice; they do not make the slices equal in trust. The skill is knowing what boundary you actually have, what a tenant can still do to their neighbours, and when the honest answer is a separate control plane.

By the end you can…

Build a tenant onboarding template, enforce fair share with quotas, isolate nodes and networks, list the noisy-neighbour paths that quotas do not cover, and choose between shared, dedicated-node and dedicated-control-plane tenancy for a given threat model.

Projects: namespaces with a front door

A Project is a Namespace with extra annotations and, crucially, a request workflow: oc new-project calls the ProjectRequest API, which creates the namespace and applies the cluster's project template, and makes the requester an admin. Users generally cannot create Namespaces directly, only Projects through that API. The template is where tenancy policy lives.

oc adm create-bootstrap-project-template -o yaml > template.yaml   # start from the default
# add: ResourceQuota, LimitRange, NetworkPolicies, RoleBindings ...
oc create -f template.yaml -n openshift-config
oc patch project.config.openshift.io/cluster --type merge \
  -p '{"spec":{"projectRequestTemplate":{"name":"project-request"}}}'

A mature template creates, for every new project: a ResourceQuota, a LimitRange with defaults, a default-deny ingress NetworkPolicy plus allows for the router (network.openshift.io/policy-group: ingress) and monitoring, and a RoleBinding for the owning group, with ${PROJECT_ADMIN_USER} and ${PROJECT_NAME} parameters. The template is applied only at creation; changing it later does not fix existing projects, so reconcile them from Git.

Who may create projects? By default all authenticated users can, through the self-provisioner ClusterRole bound to system:authenticated:oauth. On a shared platform, remove that binding (and set the rbac.authorization.kubernetes.io/autoupdate: "false" annotation so it is not re-created) and onboard through a pipeline that creates the project and binds the team's group.

Fair share: quotas

ObjectScopeUse
ResourceQuotaOne namespaceCaps total requests.cpu, requests.memory, limits.*, PVC count and storage (including per StorageClass), and object counts such as count/pods, count/secrets
LimitRangeOne namespaceDefault requests/limits for Pods that omit them, and per-container min/max. Without defaults, a quota on requests rejects any Pod that does not set them
ClusterResourceQuota (quota.openshift.io)Many namespaces, chosen by label or annotation selectorA single budget for a team that owns several projects, or for everything a user requested, with usage aggregated across them
apiVersion: quota.openshift.io/v1
kind: ClusterResourceQuota
metadata: {name: payments-team}
spec:
  selector:
    labels: {matchLabels: {team: payments}}
  quota:
    hard:
      requests.cpu: "200"
      requests.memory: 800Gi
      persistentvolumeclaims: "100"
      count/secrets: "2000"

Quotas on requests, not limits, are what govern scheduling fairness; remember from requests and limits that requests are the scheduler's currency. Quotas can also be scoped by PriorityClass so a tenant can have a small amount of high-priority capacity and plenty of default.

Where a tenant can still hurt a neighbour

Quotas handle CPU and memory. The rest of the shared surface is where real incidents come from:

Isolating nodes and networks

  • Node isolation. A namespace annotation openshift.io/node-selector (set through the project template or a cluster default) forces a tenant's Pods onto labelled nodes; add a taint on those nodes and a default toleration for the tenant so no one else lands there. Dedicated MachineSets per tenant make it a capacity unit you can bill.
  • Network isolation. Default-deny in the template, AdminNetworkPolicy for platform-wide guardrails tenants cannot lift, EgressIP and EgressFirewall for outbound identity, and optional User Defined Networks for a tenant-private pod network. Separate ingress shards for tenants with different exposure (lesson 11).
  • Pod security. The default restricted-v2 plus a policy engine (Kyverno, Gatekeeper, or ACM policies) for rules SCCs cannot express — image registries, required labels, banned host paths.

Soft versus hard tenancy

Namespace-based tenancy is soft: all tenants share one API server, one etcd, one set of cluster-scoped objects, one kernel per node. It is excellent among teams in one organisation that broadly trust each other and share a platform team. It is not a security boundary against a hostile tenant, and it is a weak boundary for strict regulatory isolation.

ModelIsolationCost
Shared cluster, namespaces and quotasSoft; shared control plane and nodesLowest; densest
Shared control plane, dedicated nodes (+ network isolation)Kernel and node noise isolated; control plane still sharedModerate; per-tenant node pool
Dedicated control plane via hosted control planes, shared worker fleet or dedicated workersOwn API server, etcd, CRDs, adminsLow control-plane cost, higher operational surface (lesson 2)
Dedicated clusterStrongestHighest; you now run a fleet (lesson 15)

Which tenancy model?

✍️ Do it by hand

A platform serves 80 internal teams in one cluster. Each project has a ResourceQuota, yet one night the API server slows and several Operators go Degraded. You find a team's controller that retries failed Jobs, creating 400,000 Job objects with ttlSecondsAfterFinished unset, and a second team's admission webhook Pod crash-looping.

  1. Why did quotas not stop the first problem?
  2. What would have?
  3. Why does the crash-looping webhook affect other tenants?
  4. What platform-level change addresses both?
Show answer

1) The ResourceQuota covered CPU and memory only. Jobs and finished Pods cost almost no compute but are stored objects; hundreds of thousands inflate etcd and slow every list and watch.

2) Object-count quotas (count/jobs.batch, count/pods) and a TTL on finished Jobs, plus API Priority and Fairness so one tenant's request flood cannot consume the API server's concurrency.

3) A ValidatingWebhookConfiguration with failurePolicy: Fail and a broad selector makes the API server reject matching writes whenever the webhook cannot answer. Matching writes include other tenants' and those of platform operators, so controllers fail, and operators go Degraded.

4) Treat webhooks and CRDs as platform-owned: restrict RBAC on webhook configurations, require selectors and short timeouts through admission policy, add count and TTL defaults in the project template, and alert on object counts and on webhook latency and failure.
