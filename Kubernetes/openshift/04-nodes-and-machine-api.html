Lesson 4

Nodes as cattle: RHCOS and the Machine API

On OpenShift a node is not a server you maintain; it is an instance of a template that the platform can recreate. The Machine API is what makes that real on IPI clusters, and the difference between a team that treats nodes as pets and one that trusts the platform shows up first at 3am during a node failure.

By the end you can…

Explain what RHCOS and Ignition do, trace Machine → Node, scale and autoscale a pool, write a MachineHealthCheck that cannot cause a storm, create an infra pool, and diagnose a Machine that never becomes a Node.

RHCOS and Ignition in one page

Red Hat Enterprise Linux CoreOS is a minimal, image-based OS: /usr is read-only, updates are whole-image transactions through rpm-ostree and applied on reboot, and the only sanctioned package set is whatever the release image ships. The OS version is part of the release payload, so updating OpenShift updates the OS.

Ignition configures the machine once, on first boot, from user data supplied by the platform. It partitions disks, writes files, creates units, and tells the machine to fetch the rest of its config from the machine-config-server on the control plane. After first boot, ongoing configuration belongs to the Machine Config Operator (lesson 5), not to Ignition.

Practical rules for an SRE: you rarely SSH to a node; when you must, use oc debug node/<name> then chroot /host and treat it read-only. core is the only user. Anything you change by hand will be reported as drift and may make the node Degraded.

The Machine API

MachineSet  ──creates──►  Machine  ──backs──►  Node
 (replicas, template)      (one cloud VM)       (kubelet registered)
      ▲                         ▲
MachineAutoscaler        MachineHealthCheck
 (min/max per set)        (delete unhealthy Machines)
      ▲
ClusterAutoscaler (cluster-wide scale-up/scale-down policy)
  • Machine — a declarative request for one VM. Its providerSpec holds the cloud details (instance type, AMI, subnet, tags). Phases: Provisioning → Provisioned → Running, or Failed, or Deleting.
  • MachineSet — a ReplicaSet for Machines. Change the template and only new Machines get it; existing ones are not replaced. Rolling a template change means scaling up and then deleting old Machines.
  • MachineAutoscaler — sets min/max for one MachineSet; the ClusterAutoscaler decides when to scale based on pending Pods and node utilisation, with cluster-wide limits.
  • MachineHealthCheck — deletes a Machine whose Node is unhealthy so its MachineSet replaces it.

This is the pattern behind the autoscaling lesson in the main course, with Karpenter's job done by the Cluster Autoscaler plus MachineSets. Compare node autoscaling and Karpenter: the Cluster Autoscaler scales pre-defined pools; it does not pick instance types per Pod.

How a Machine becomes a Node

  1. MachineSet controller creates a Machine; the cloud provider actuator creates the VM with user-data pointing at the machine-config-server.
  2. The VM boots RHCOS, Ignition runs, the machine fetches its full config, and the kubelet starts.
  3. The kubelet submits two CSRs: a client CSR, then a serving CSR. The cluster-machine-approver approves them when the request matches a known Machine.
  4. A Node appears and is linked to the Machine via nodeRef.

The failure points follow the steps. VM never exists: cloud quota, instance type unavailable, wrong subnet — read oc describe machine. VM exists, no Node: bootstrap failed or the machine-config-server is unreachable — check the instance console. Node exists but NotReady: look for pending CSRs (oc get csr | grep Pending) — a surprisingly common cause after a long outage, because kubelet certificates expired while the node was down.

A MachineHealthCheck that does not cause a storm

apiVersion: machine.openshift.io/v1beta1
kind: MachineHealthCheck
metadata: {name: workers, namespace: openshift-machine-api}
spec:
  selector:
    matchLabels: {machine.openshift.io/cluster-api-machine-role: worker}
  unhealthyConditions:
    - {type: Ready, status: "False",   timeout: 300s}
    - {type: Ready, status: Unknown,   timeout: 300s}
  maxUnhealthy: 40%        # stop remediating if more than 40% look unhealthy
  nodeStartupTimeout: 20m

The dangerous situation is not one bad node; it is every node looking bad at once. A control-plane network blip, an expired certificate, or an API outage makes all kubelets appear NotReady. An unbounded health check will happily delete every worker Machine, and the cluster rebuilds itself from nothing while you watch. maxUnhealthy is the circuit breaker: above it, remediation stops and the check reports short-circuited. Set it deliberately, and do not apply a health check to control-plane nodes without the documented procedure.

Infra nodes and dedicated pools

Platform components — routers, monitoring, the registry, logging — should not share nodes with tenant workloads. Create a MachineSet labelled node-role.kubernetes.io/infra, usually with a taint, and then point the components at it through their own configuration: nodePlacement on the IngressController, nodeSelector and tolerations in cluster-monitoring-config, and the registry operator's config. If you also want to tune them with MachineConfigs, make a matching custom MachineConfigPool so infra can roll on its own schedule (lesson 5).

When there is no Machine API

On UPI, on bare metal with no BMC integration, or on any cluster where nodes were added by hand, there are Nodes and no Machines. Replacement is whatever your automation does. On IPI bare metal the Metal3 operator gives you BareMetalHost objects and Machines mapped onto them, so a "delete Machine" reprovisions a physical host through its BMC. That is powerful and slow: reimaging a server takes many minutes and a failed BMC can strand the host. Set expectations for time-to-replace accordingly.

Note on direction: the upstream Cluster API is gradually becoming the underlying implementation on several platforms. The user-facing idea — a template-backed pool of replaceable machines — stays the same, but object kinds may differ by release.

✍️ Do it by hand

An AZ network event isolates the control-plane API from 12 of your 30 workers for six minutes. Your MachineHealthCheck has timeout: 300s and no maxUnhealthy. Afterwards, a MachineSet's instance type is also changed in the template from m6i.2xlarge to m6i.4xlarge.

  1. What does the MHC do during the event?
  2. What field should have prevented it, and with what value?
  3. After you change the instance type, do existing nodes become larger?
  4. How do you move the pool to the new size without an outage?
Show answer

1) Nodes become Unknown because kubelets cannot post status. After 300 seconds the MHC treats them as unhealthy and deletes their Machines. The VMs are terminated even though the workloads on them were fine and merely unreachable — a self-inflicted outage far worse than the six-minute blip.

2) maxUnhealthy. Here 12 of 30 is 40% unhealthy, so a value such as 20% would have short-circuited the check and left every Machine alone. Choose the largest fraction of the pool you can lose and still serve, accounting for how long replacement takes.

3) No. A MachineSet template change affects only Machines created afterwards. Existing Machines keep their original spec.

4) Scale the MachineSet up to create the larger machines, wait for the Nodes to be Ready, cordon and drain the old nodes (or delete the old Machines with the PDBs honoured), then scale down. Mind a MachineConfigPool's maxUnavailable and any PDBs that could block draining.
