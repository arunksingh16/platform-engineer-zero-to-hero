Lesson 3

The Cluster Version Operator and ClusterOperators

If you learn one thing on this platform, learn this: oc get clusteroperators is the cluster's health summary, and the three columns Available, Progressing, Degraded tell you whether a fault is in a component or merely downstream of one. Most senior on-call time is saved by reading that table correctly.

By the end you can…

Explain what the CVO does, interpret any combination of ClusterOperator conditions, trace cascading degradation to its root, and say what managementState and overrides do to your support position.

The release image is the unit

An OpenShift version is a single container image, the release payload. Inside it is a list of every operator image digest plus the manifests the platform needs, numbered so they apply in a defined order. The Cluster Version Operator (CVO) runs in openshift-cluster-version and continuously applies that payload: it creates or patches the operator Deployments and their CRDs, then waits for each to report healthy before moving on.

That is the same reconcile loop as lesson 1 of the main course, applied to the platform itself. Notice three consequences:

  • Updating is changing the desired release image. There is no per-component upgrade procedure; the CVO converges to the new payload.
  • The CVO is self-healing. If you delete an operator Deployment it is recreated; if you edit it, the CVO reverts it. That is what makes the platform consistent and what makes hand edits pointless.
  • Order is part of the contract. Manifests are grouped into run levels; etcd and the API server come before things that need them. A wrong-order upgrade is not possible, which is also why a stuck early operator blocks everything behind it.

Reading the table

$ oc get clusterversion
NAME      VERSION   AVAILABLE   PROGRESSING   SINCE   STATUS
version   4.18.4    True        False         12d     Cluster version is 4.18.4

$ oc get co
NAME                 VERSION  AVAILABLE  PROGRESSING  DEGRADED  SINCE
authentication       4.18.4   True       False        False     12d
etcd                 4.18.4   True       False        False     12d
ingress              4.18.4   True       True         False     4m
machine-config       4.18.4   True       False        True      9m

Each operator publishes a ClusterOperator object with condition types. They are not a severity ladder; they are three independent questions:

ConditionQuestion it answersMeaning of True
AvailableIs the operand doing its job right now?The component is serving. False means a user-visible outage of that function.
ProgressingIs the operator moving toward a new desired state?A rollout is in flight — normal during an update or config change, suspicious if it lasts hours.
DegradedDoes the operator believe something is wrong that it cannot fix on its own?Needs a human, even though it may still be Available.
UpgradeableIs it safe to take a minor update?Usually shown as False with a reason when something blocks it.

Degraded has a hysteresis: operators generally wait a short period before flipping it so a Pod restart does not page you. A sustained Degraded is a real signal; a momentary one on a rollout is not.

Cascading degradation: find the root, not the loudest

Operators depend on each other, and many report Degraded when something they use is broken. The commonly surprising chains:

etcd ──► kube-apiserver ──► openshift-apiserver, oauth-apiserver
                      └────► almost everything else

network ──► DNS ──► ingress ──► authentication ──► console
                                  (authentication needs the OAuth route to be reachable,
                                   which needs the router, which needs DNS and the network)

machine-config ──► nodes ──► every operator whose operand runs on a node being drained

When console, authentication and monitoring are all red, the instinct is to open the console one. Resist it. Walk the chain from the bottom: is etcd healthy? kube-apiserver? network? dns? ingress? The lowest broken operator is almost always the cause, and the ones above it clear themselves when it recovers.

The 90-second triage

oc get clusterversion
oc get co | grep -vE 'True +False +False'        # show only unhealthy rows
oc describe co <lowest-in-the-chain>               # message + reason per condition
oc -n openshift-<operator> get pods                # operand health
oc -n openshift-<operator> logs deploy/<operator>   # operator's own reasoning
oc get events -A --sort-by=.lastTimestamp | tail -30
oc get mcp                                         # is a config rollout the cause?
oc adm must-gather                                 # attach to the support case

If the API itself is unreachable, none of this works and neither does oc debug. SSH to a control-plane node as core (break-glass only), use crictl ps and crictl logs for the etcd and kube-apiserver containers, and use the on-node localhost-recovery.kubeconfig described in the recovery docs.

managementState and overrides: how to void your support

Each operator CR has spec.managementState with three values. Managed is normal. Unmanaged tells the operator to stop reconciling — an intentional escape hatch used for debugging, and one that makes the cluster unsupported until restored. Removed tells operators that support it to remove the operand (the Image Registry uses this when a cluster has no storage).

At the CVO level, ClusterVersion.spec.overrides can mark a specific manifest unmanaged: true so the CVO stops applying it. It exists for emergencies. It also sets Upgradeable=False, the cluster is unsupported, and every later update is blocked until you remove the override. Treat any override in a fleet audit as a finding.

Tempting actionWhat you risk
Scale an operator Deployment to 0 "to stop it fighting me"The CVO scales it back; you lose the intended pause and, if the CVO is also scaled down, you lose all convergence.
Set managementState: Unmanaged to patch an operandNo more reconciliation, no support, and the patch may be wiped on the next update.
Add a ClusterVersion override for a manifestBlocks updates; deferred debt that always comes due at the worst time.

✍️ Do it by hand

At 02:10 you see: authentication Available=False, console Available=False, ingress Degraded=True with reason IngressControllerUnavailable, dns healthy, network healthy, machine-config Progressing=True. Users report logins failing, but running apps still answer.

  1. Which operator do you investigate first, and why not authentication?
  2. Why are existing applications still working?
  3. machine-config is Progressing. Why is that relevant?
  4. What would you check on the ingress operator?
Show answer

1) ingress. It is lowest in the chain that is broken. Authentication's OAuth endpoint is exposed through a Route served by the router; if the router is unavailable the login route is unreachable and authentication reports unavailable. Fixing authentication directly is chasing a symptom.

2) Pods keep running regardless of the control plane, and east-west traffic does not use the router. If external application Routes also answer, the router is only partly down (some replicas, or a subset of shards) and the failing piece is narrower than the status suggests — for example only the OAuth route's endpoints. Check whether all routes fail or just the authentication one before widening the incident.

3) A MachineConfig rollout drains nodes. If router replicas are being evicted at the same time and a PDB or node placement leaves too few, you can produce exactly this: the rollout is the trigger, ingress the symptom. Check oc get mcp and which nodes are draining.

4) oc describe co ingress for the message, oc -n openshift-ingress get pods -o wide for placement and readiness, oc -n openshift-ingress-operator get ingresscontroller/default -o yaml for conditions (they are detailed: PodsScheduled, DeploymentAvailable, LoadBalancerReady, DNSReady), and the router pod logs.
