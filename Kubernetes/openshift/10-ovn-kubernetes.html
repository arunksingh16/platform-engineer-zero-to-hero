Lesson 10

Networking I: OVN-Kubernetes

OVN-Kubernetes is the default and, for new clusters, the only supported OpenShift CNI. It implements the CNI contract from the CNI sub-course with Open Virtual Network on top of Open vSwitch: a logical network described in a database and compiled into flows on every node. You will rarely touch OVS directly, but you will meet its constraints — MTU, reserved subnets, and what happens when the databases misbehave.

By the end you can…

Describe the OVN-K components, compute the pod MTU, avoid subnet overlaps, use EgressIP and EgressFirewall, understand which policy APIs apply, attach secondary networks, and start a debugging session in the right layer.

History in one paragraph

Older OpenShift 4 clusters used OpenShift SDN. It was deprecated and then removed; clusters still on it had to migrate to OVN-Kubernetes before moving to the release that dropped it. If you inherit a fleet, check oc get network.config cluster -o jsonpath='{.status.networkType}' first. The migration is an offline-ish, node-by-node operation with a defined rollback window — a project, not a command.

The architecture

Per node (current "interconnect" architecture, one OVN zone per node):
  ovnkube-node  DaemonSet Pod, containing:
     ovnkube-controller   translates Kubernetes objects into OVN logical config
     ovn-controller       programs OVS from the OVN southbound DB
     northd, nbdb, sbdb   the node-local OVN databases
     ovs-vswitchd / ovsdb-server  (run on the host via the openvswitch services)
  ovnkube-control-plane   cluster-wide helpers (allocating node subnets, coordinating zones)

Logical topology:
  each node: a logical switch (the node's pod subnet) ─► a ovn_cluster_router
  ovn_cluster_router ─► join switch ─► per-node gateway router (GR) ─► br-ex ─► physical NIC
  inter-node pod traffic: Geneve tunnels between nodes (UDP 6081)

The older design had one cluster-wide pair of OVN databases on the control plane, which was a scaling and failure-domain bottleneck. In current releases each node has its own zone, so the DB failure domain is one node. When you read older runbooks that say "restart the ovnkube-master Pod", check they apply to your release.

Pod-to-Pod is the overlay model from the CNI lessons: a veth pair into the node's logical switch, Geneve encapsulation between nodes, no NAT between Pods. Pod-to-external goes through the node's gateway router with SNAT to the node IP unless an EgressIP applies. Services are implemented by OVN load balancers rather than kube-proxy — there is no kube-proxy on an OVN-K cluster, so reasoning about iptables Service rules is a dead end.

MTU: the silent breaker

Geneve adds a header, so Pod MTU must be smaller than the node's. The documented overhead is 100 bytes for OVN-Kubernetes (with IPsec encryption, a further amount). Mis-set MTU shows up as the pattern from the CNI course: small requests work, large responses hang, TLS handshakes stall at the certificate. Try the numbers:

Pod MTU

Changing the cluster MTU after install is possible through the Network operator with a controlled, rolling procedure, and it is risky; set it correctly (for example jumbo frames on a 9000-byte fabric) at install, and make sure every hop — including VPN and Direct Connect style links — agrees.

Policy APIs

  • NetworkPolicy — standard, namespace-scoped, additive, implemented as OVN ACLs. Behaves as in the CNI lesson.
  • AdminNetworkPolicy and BaselineAdminNetworkPolicy — cluster-scoped, ordered, with explicit Allow, Deny and Pass actions. ANP sits above tenant NetworkPolicy and can enforce platform rules tenants cannot override; BANP sits below and sets defaults tenants can refine. This is the supported answer for platform-wide guardrails.
  • EgressFirewall (per namespace) — allow or deny egress to CIDRs and DNS names. Rules are ordered, first match wins, and a final deny 0.0.0.0/0 turns it into an allow-list. Intended for traffic leaving the cluster; check its interaction with cluster-internal destinations on your release.

Egress that has an identity

By default, outbound traffic from a Pod is SNATed to the IP of the node it runs on, which changes whenever the Pod moves. External systems that firewall by source IP then need to trust every node. An EgressIP object assigns a stable source address to Pods selected by namespace and Pod labels:

apiVersion: k8s.ovn.org/v1
kind: EgressIP
metadata: {name: payments-egress}
spec:
  egressIPs: ["10.0.40.50", "10.0.40.51"]      # several = HA candidates
  namespaceSelector: {matchLabels: {team: payments}}

Nodes eligible to host egress IPs are labelled k8s.ovn.org/egress-assignable. The IP is held by one node at a time and moves if that node fails. On a public cloud the IP must be within the node's subnet and the cloud network API has to cooperate; on bare metal it is an address you own and route. EgressIP is how a tenant gets a firewall-friendly source address — and, combined with EgressFirewall, a defensible outbound posture.

More than one network

The Cluster Network Operator can install Multus, which lets a Pod have extra interfaces defined by NetworkAttachmentDefinition objects. Common uses: SR-IOV or macvlan for telecom and data-plane workloads, VLAN-isolated management networks, and User Defined Networks (UDN) in recent releases, which give a tenant namespace its own primary L2 or L3 overlay, isolated from the default network. The MetalLB operator supplies type: LoadBalancer Services on bare metal using BGP or L2 announcements, where there is no cloud to create one.

Debugging in layers

  1. Is the network operator healthy? oc get co network; oc -n openshift-ovn-kubernetes get pods -o wide. A crash-looping ovnkube-node means new Pods on that node stay ContainerCreating.
  2. Pod stuck ContainerCreating: oc describe pod for the CNI error, then the node's ovnkube-node logs.
  3. Connectivity: test Pod-to-Pod on the same node, then across nodes, then to the Service, then external. The first layer that fails is the culprit. Across-node-only failures point at Geneve (UDP 6081 blocked, or MTU).
  4. Packet trace: oc debug node/x then chroot /host; ovs-ofctl dump-flows br-int, ovn-trace, and ovs-appctl ofproto/trace show what the logical network will do with a packet; tcpdump -i br-ex and on the Geneve device show it on the wire.
  5. Policy: oc get networkpolicy,adminnetworkpolicy -A; the OVN ACLs and drop logging (k8s.ovn.org/acl-logging annotation on the namespace) tell you which rule denied a flow.

✍️ Do it by hand

After a rollout, a Java service cannot reach a payment partner. Small health-check requests succeed; the TLS handshake with the partner hangs after the ClientHello. Same-node Pods work with each other. A firewall team insists on a single source IP for the partner. The cluster was configured for jumbo frames: Pod MTU shows 8900. One hop between two racks turns out to be 1500.

  1. What pattern is this, and what is the maximum Pod MTU on this fabric?
  2. What did someone likely do?
  3. How do you give the partner one source IP?
  4. How do you stop tenants from reaching the partner except this service?
Show answer

1) The classic MTU black hole: small packets pass, large ones are silently dropped where a link cannot carry them and ICMP "fragmentation needed" is filtered. Pod MTU 8900 is right for a 9000 underlay (9000 − 100 Geneve), but only if every hop carries 9000. A 1500 hop makes full-size packets vanish. A Pod MTU that is too small is safe, only slower; too large is what hangs.

2) Someone assumed jumbo frames end to end (or the cluster MTU was raised without verifying the path). Compare MTU with ip link on the Pod interface, the Geneve device and the physical NIC on both ends, and test with ping -M do -s 8800 between nodes. Fix the weak link, or lower the cluster MTU to what the path supports.

3) An EgressIP selecting the service's namespace (and Pod labels), on nodes labelled egress-assignable. The partner allow-lists one address.

4) An EgressFirewall in other namespaces denying the partner CIDR, or default-deny with an allow-list, and an AdminNetworkPolicy if the rule must override tenants. The payments namespace is the one exception.
