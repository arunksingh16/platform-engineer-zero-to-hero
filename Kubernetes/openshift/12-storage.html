Lesson 12

Storage

Storage on OpenShift is Kubernetes storage with an opinionated default stack: CSI drivers managed by operators, a default StorageClass from your platform, and an optional software-defined storage layer, OpenShift Data Foundation. The hard parts are not creating a PVC. They are what happens when a node fails with a volume attached, when the disk under etcd is slow, and when "backup" means a snapshot on the same array.

By the end you can…

Choose a StorageClass and access mode for a workload, explain WaitForFirstConsumer and its effect on multi-zone placement, describe what ODF adds and what it costs, size the etcd disk correctly, resolve a stuck volume after node failure, and design backups that survive a storage failure.

Access modes and what they imply

ModeMeaningTypical backing
RWOOne node mounts it read-write (multiple Pods on that node can)Cloud block (EBS, Azure Disk), Ceph RBD, LVMS
RWOPExactly one PodCSI drivers that support it
RWXMany nodes read-writeNFS, CephFS, EFS, Azure Files
ROXMany nodes read-onlyShared content, snapshots-as-clones

The practical rule: block storage is RWO, fast and low latency; shared file storage is RWX, slower, with locking semantics that bite databases. Do not put a database on RWX file storage because it was the one that "worked" with two replicas.

Binding mode and zones

A StorageClass with volumeBindingMode: Immediate provisions the volume as soon as the PVC is created — in whichever zone the provisioner picks, before the Pod is scheduled. A zonal volume then pins the Pod to that zone, and if no node there fits, the Pod is Pending forever. WaitForFirstConsumer delays provisioning until a Pod is scheduled, so the volume is created where the Pod landed. On multi-zone clusters it is the right default for block storage; the platform's default classes generally use it. Check yours.

Also check allowVolumeExpansion (expansion on the fly, online for most CSI drivers, grow only, never shrink) and reclaimPolicy (Delete destroys the volume with the PVC; Retain keeps it for manual recovery — the safer choice for data you cannot recreate).

ODF in one honest page

OpenShift Data Foundation deploys Ceph through Rook and presents block (RBD, RWO), file (CephFS, RWX) and object (RGW and NooBaa's multicloud gateway). It runs inside the cluster on dedicated or shared nodes, so storage and compute share a failure domain and an update cycle.

  • Minimum 3 failure domains (nodes or racks/zones) with replica-3 by default; erasure coding exists for some pools. Raw capacity is roughly one third of usable at replica 3.
  • Dedicated storage nodes are strongly preferred in production: OSDs and MONs have CPU and memory floors, and recovery after a node loss is I/O- and network-heavy, which hurts co-located workloads.
  • Network matters. Replication and recovery traffic needs a solid, ideally dedicated, network with enough bandwidth for rebalancing; a slow network makes every write slow.
  • Updates follow OLM and the OpenShift cadence; one version skew rule is that ODF must be compatible with your OpenShift minor. Upgrade it per its docs, one failure domain at a time.
  • Capacity is a hard cliff. ODF raises alerts well before Ceph's own thresholds — by default Ceph flags nearfull at 85%, stops backfill at 90% (backfillfull) and blocks writes at 95% (full). A full cluster halts every PVC at once, so alert early and plan expansion by lead time, not by the last warning.

The alternative is to keep storage outside (cloud block, an enterprise array through CSI). That separates failure domains and lifecycles at the cost of a different vendor dependency. Neither is wrong; know which you chose and rehearse its failure.

etcd and disk, again

The one storage requirement that is not negotiable: etcd needs fast, low-latency, consistent fsync. The guidance is that the 99th percentile of WAL fsync duration stays under about 10 ms; sustained values beyond that cause leader elections, slow API, and operators flapping. Use local NVMe/SSD or high-IOPS dedicated disks, do not share the control-plane disk with other I/O, and never place etcd on network file storage. The metrics to watch are etcd_disk_wal_fsync_duration_seconds and etcd_disk_backend_commit_duration_seconds; the alert etcdHighFsyncDurations is the warning. A fio-based check before go-live is cheap insurance. More in lesson 14.

Failure: node dies, volume stays attached

A RWO volume attached to a dead node cannot be attached elsewhere until the control plane is sure it is detached. The Pod rescheduled elsewhere shows Multi-Attach error for volume … Volume is already exclusively attached to one node, and sits in ContainerCreating. For a node that is truly gone, the attach/detach controller force-detaches after a timeout (around six minutes by default) once the Pod is deleted; for a node that is unreachable but possibly alive, forced detach is dangerous because two writers could corrupt a filesystem.

The safe mechanism for a confirmed-dead node is the out-of-service taint: after fencing the node (power it off), taint it node.kubernetes.io/out-of-service=nodeshutdown:NoExecute. Pods are evicted without waiting for the kubelet and volumes are force-detached. The word fenced matters; if you taint a node that is still running and writing, you cause the exact corruption the safeguard existed to prevent. On Machine-API clusters, MachineHealthCheck plus deleting the Machine does the fencing for you.

Backup is not a snapshot

A VolumeSnapshot on the same storage system is a point-in-time copy that shares the storage's failure domain: lose the array or delete the PVC with its snapshots and both are gone. A backup is a copy in a different failure domain, restorable, tested.

  • OADP (OpenShift API for Data Protection, Velero-based) backs up Kubernetes resources and, via CSI snapshots or file-level Kopia/Restic, volume data to object storage elsewhere.
  • Application-aware backups for databases (logical dumps, WAL archiving, the operator's own backup feature) beat crash-consistent volume copies.
  • Declarative state belongs in Git; etcd backup is for cluster recovery, not a substitute for application backup.
  • Restore tests are the only proof. Schedule them and record the time taken.

✍️ Do it by hand

A 3-zone cluster uses a StorageClass with volumeBindingMode: Immediate. A StatefulSet's Pod is Pending with "0/9 nodes available: 3 node(s) had volume node affinity conflict". Later, a worker in zone A is powered off by a hypervisor fault, and the replacement Pod sits in ContainerCreating with a Multi-Attach error.

  1. Explain the first Pending.
  2. Fix for new volumes?
  3. What exactly is the second problem, and how do you safely resolve it?
  4. Management asks if snapshots are their backup. Answer.
Show answer

1) Immediate binding provisioned the EBS-style volume in a zone chosen before scheduling. A zonal volume forces the Pod into that zone; the Pod's other constraints (taints, resources, anti-affinity) leave no feasible node there, so it is Pending with a volume node affinity conflict.

2) Use WaitForFirstConsumer. Existing PVs stay where they are; you recreate the PVCs (restoring data from backup or a snapshot clone into the right zone) or move the Pod's constraints.

3) The RWO volume still appears attached to the dead node. Confirm the node is truly off (fence it), then either wait for the force-detach timeout or apply the node.kubernetes.io/out-of-service:NoExecute taint to speed it up. If the node might be alive, do not do either: stop the writer first.

4) No, not on their own. Snapshots in the same storage system share its failure domain. A backup is an independent, tested copy (OADP to remote object storage, application-level backups), and the restore has to be rehearsed.
