Lesson 7

Operator Lifecycle Manager

Platform operators come from the release image; everything else — databases, service mesh, GitOps, storage, logging — arrives through the Operator Lifecycle Manager. OLM is the package manager for operators, and an operator update is a production change that can go out unattended unless you decide otherwise.

Name each OLM object and what it does, trace an install from catalog to running operator, choose approval and channel settings for production, diagnose the commonest failures at each stage, and say where OLM v1 differs.

Install modes and OperatorGroups

A CSV declares which install modes it supports: OwnNamespace, SingleNamespace, MultiNamespace, AllNamespaces. The OperatorGroup in the operator's namespace selects one. This decides the scope of the operator's watch and therefore the blast radius of its bugs and of its credentials.

Hard rules that cause outages: only one OperatorGroup per namespace, and the CRDs an operator owns are cluster-scoped — two operators cannot own the same CRD, and two versions of one CRD cannot coexist. A namespace-scoped install of an operator that ships a CRD still changes a cluster-wide API.

Production settings

apiVersion: operators.coreos.com/v1alpha1
kind: Subscription
metadata: {name: my-operator, namespace: my-operator}
spec:
  channel: stable-v2
  name: my-operator
  source: redhat-operators
  sourceNamespace: openshift-marketplace
  installPlanApproval: Manual        # review before each upgrade
  startingCSV: my-operator.v2.3.1    # pin the first version for reproducible builds

With Automatic approval, the moment a new version appears in your channel OLM upgrades the operator. For an operator that owns a database or storage layer, that is a production change you did not schedule. With Manual, an InstallPlan sits in RequiresApproval until a human or pipeline approves it. The trade is simple: Manual for anything stateful or critical, Automatic for low-risk tooling. Remember that an operator update can in turn change the operand it manages; read its release notes like you would an application upgrade.

Channels also matter. They are the operator author's way of grouping upgrade streams; moving between channels can skip or change versions. A subscription cannot jump arbitrary versions: it follows the replaces/skips graph, so a long-pinned operator may need to pass through intermediate versions one InstallPlan at a time.

The stuck-subscription reflex

oc get csv,sub,installplan,og -n <ns>
oc get sub <name> -n <ns> -o jsonpath='{.status.conditions}' | jq
oc -n openshift-marketplace get pods,catalogsource
oc -n openshift-operator-lifecycle-manager logs deploy/catalog-operator | tail
oc -n openshift-operator-lifecycle-manager logs deploy/olm-operator | tail

Deleting a CSV removes the operator Deployment but leaves its CRDs and your custom resources. Deleting a CRD deletes every custom resource of that kind cluster-wide — including the data they represent. Never delete a CRD to "clean up" an operator.

Disconnected catalogs

The default catalogs live on the internet. In a disconnected cluster you disable them and mirror a filtered catalog containing only the packages you will use (with oc-mirror), then create a CatalogSource pointing at your registry. Pin and mirror specific versions: the graph an operator upgrades along must be mirrored in full, or upgrades will fail at resolution with no obvious reason.

OLM v1

The original OLM is being succeeded by OLM v1, which replaces Subscription/InstallPlan/OperatorGroup with a simpler model: ClusterCatalog and ClusterExtension objects, with upgrade constraints stated directly and explicit service-account permissions (no implicit god-mode RBAC). The aim is to make cluster-scoped extensions install like packages. The migration is gradual and release-dependent; run what your OpenShift release supports, and keep an eye on the deprecation timetable for the classic API.

✍️ Do it by hand

A team's database operator is subscribed on channel stable with Automatic approval. Overnight, version 2.5 is published; by morning, the operator rolled and rolled every database cluster. Two clusters are unhealthy. Separately, a cleanup script deleted "the old CRDs" for another operator.

  1. What setting would have prevented the surprise rollout?
  2. How do you stop further automatic upgrades now?
  3. What happened to the databases when the CRD was deleted?
  4. How do you check whether a pending OpenShift minor update will break this operator?
Show answer

1) installPlanApproval: Manual on the Subscription, so each new version is an InstallPlan that someone approves in a window.

2) Patch the Subscription to Manual. Any pending InstallPlan stays unapproved until you decide. You may also pin startingCSV for new installs.

3) Deleting a CRD cascades to deleting every custom resource of that kind. The operator's CRs — the declared databases — are removed and the operator, if running, then tears down what it created from them. Restore from backups of the manifests (GitOps) and of the data, and never delete CRDs as a cleanup step.

4) Read the CSV's declared compatibility (the operator may set a maximum OpenShift version), check Upgradeable on the ClusterVersion, and check the operator's compatibility matrix. Update the operator to a release that supports the target before the cluster minor update.
