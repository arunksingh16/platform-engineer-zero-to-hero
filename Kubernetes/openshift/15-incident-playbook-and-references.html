Lesson 15

Fleet operations, incident playbook and references

One well-run cluster is a craft. Twenty is a system: the same configuration everywhere, drift detected rather than discovered, and an incident process that starts from the layer model you have built over the previous fourteen lessons.

By the end you can…

Describe a GitOps and policy-driven fleet model, define platform SLOs, run an incident from symptom to layer in a fixed order, and know where to verify any claim in this course.

The fleet model

Treat clusters as instances of a template, with differences declared in Git. The common building blocks:

PieceRole
OpenShift GitOps (Argo CD operator)Reconciles manifests from Git into a cluster. ApplicationSet generates one Application per cluster, environment or tenant. A pull model: a compromised pipeline cannot push to the cluster directly.
Advanced Cluster Management (ACM)A hub cluster that imports and manages spokes: inventory (ManagedCluster), placement, Policy objects that enforce or inform on configuration, cluster lifecycle (create, upgrade, destroy), and fleet observability
Policy enginesACM policies, Kyverno or Gatekeeper, and ACS for runtime and image policy, for rules SCCs and RBAC cannot express
Zero-touch provisioningFor edge and bare metal: declare a site in Git; the hub builds the cluster through the Agent-based or Assisted installer and applies a baseline
Central observabilityRemote-written metrics, forwarded logs and audit, a single alerting tier

What belongs in Git: MachineConfigs and pools, IngressControllers, the OAuth identity-provider config (minus secrets), project templates and quota policy, cluster-monitoring config, OLM Subscriptions (with Manual approval and pinned versions), ANPs, and your tenant onboarding objects. What does not: secrets in clear text — use an external secret manager or sealed secrets — and anything an operator should generate.

Three disciplines separate a managed fleet from a collection of clusters. Drift detection: Argo CD's diff and ACM's compliance status tell you when a cluster no longer matches. Staged rollout: changes go to a canary cluster, wait, then to a ring of non-critical clusters, then everything, with automatic halt on failed health. Version discipline: a small set of supported versions, with the update cadence from lesson 6 run as a standing process rather than a project.

Platform SLOs

If the platform has no SLO, the platform team's priorities are set by whoever is loudest. Choose a few service level indicators that reflect what tenants actually depend on, and measure them from outside where possible (see the SLOs lesson):

SLIHow to measure
Kubernetes API availability and latencyRatio of successful (non-5xx) requests, and p99 latency by verb, from apiserver_request_* metrics, plus an external probe against /readyz
Ingress availabilitySynthetic probes through the router (the canary route is a start) and router-reported 5xx ratio
Scheduling and node readinessTime from Pod create to Running for a canary Deployment; fraction of Ready nodes
ProvisioningPVC bind time; new node time-to-Ready
Update healthFraction of the fleet within the supported version window; update success rate and duration
Security postureOpen critical CVEs in the platform; clusters with anyuid/privileged grants outside the exceptions list; compliance scan pass rate

Give each a budget, and burn-rate alerts (as in the SLO lesson), so the update-cadence argument becomes an arithmetic one: "we have a 4-hour error budget this quarter; an update cluster costs 20 minutes of API blips, so we can afford it."

The incident playbook

An order that works because it follows the dependency chain, not the loudest symptom. Carry it as a checklist.

  1. Scope. What is down, for whom, since when, how big? One tenant, one cluster, the fleet? What changed in the last 24 hours: update, MachineConfig, operator approval, certificate expiry, a tenant release, an infra event?
  2. Can you reach the API? oc get --raw /readyz. If no: LB and VIP, API certificates, etcd and kube-apiserver static Pods via crictl on the control-plane nodes.
  3. Platform health at a glance. oc get clusterversion; oc get co | grep -vE 'True +False +False'; oc get mcp; oc get nodes; oc get csr | grep Pending.
  4. Walk the chain from the bottom. etcd → kube-apiserver → network → DNS → ingress → authentication → the rest. The lowest broken layer is the cause (lesson 3).
  5. Collect evidence. oc adm must-gather, timestamps, the YAML of unhealthy objects.
  6. Mitigate with the smallest reversible change. Pause a pool, stop the competing job, scale a router shard, fail over, cordon a node. Avoid restoring from backup unless quorum or data is lost.
  7. Communicate on a cadence, even when nothing has changed.
  8. Verify recovery with the SLIs, not just with green operators.
  9. Write the post-incident review: timeline, root cause, what made it hard to see, and which alert, runbook or guardrail now exists.

✍️ Do it by hand

Friday 16:30. A fleet-wide MachineConfig was merged at 16:00 and Argo CD synced it everywhere: a new kubelet setting. By 16:30 on three clusters, ingress is intermittently 503; oc get mcp shows workers Updating and two nodes per cluster cordoned; one cluster's router Pods are both on cordoned nodes. The SLO dashboard shows ingress burning budget fast.

  1. What is the likely mechanism?
  2. What is your first, smallest mitigation?
  3. What process failure does the fleet-wide sync reveal?
  4. What guardrails fix it?
Show answer

1) A MachineConfig change on the worker pool drains and reboots nodes. On the affected cluster both router replicas share draining nodes (no spread or too few replicas), so for a time there is no healthy router. Elsewhere reduced capacity plus long request times cause 503s.

2) Pause the worker MachineConfigPool on all affected clusters to stop further drains, and scale the router (or fix its placement) so replicas cover at least two failure domains. Do not delete the MachineConfig first; that triggers another rollout.

3) A change that reboots every node was released everywhere at once, on a Friday, with no canary stage or maintenance-window awareness. GitOps did what it was told.

4) Staged sync waves with ApplicationSets by ring, an automatic halt on SLO burn, canary pools, change-freeze windows in the sync policy, maxUnavailable set from capacity, topology spread plus PDBs for routers, and a policy that flags any MachineConfig as a high-risk change requiring review.

You are done

You can now say which operator owns any part of the platform, choose a topology and avoid the one-way doors, roll node and cluster changes safely, review an access request against OAuth, RBAC and SCCs, trace traffic through OVN-Kubernetes and the router, choose and rehearse storage failure, design tenancy with honest limits, keep etcd healthy, and run an incident in an order that follows the dependency chain.

The honest next step is practice, not more reading: build a three-node cluster, deliberately break a ClusterOperator, pause a pool during an update, fill an etcd quota in a lab, restore from a backup, and write the runbook for each. Back to the Kubernetes course or to the other courses.
