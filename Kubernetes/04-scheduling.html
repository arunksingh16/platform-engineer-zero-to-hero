Lesson 4

Scheduling, and why Pods stay Pending

Pending is not a failure. It is the scheduler telling you, precisely, that no node currently satisfies the constraints you wrote — and the event message usually names which one.

By the end you can…

Describe filtering and scoring, say what taints, tolerations, affinity and topology spread each do, and diagnose a Pending Pod from its events.

Two steps, in order

The scheduler watches for Pods with no node assigned and runs a 2-step operation on each:

StepWhat it does
FilteringFinds the set of Nodes where it's feasible to schedule the Pod. A hard yes or no per node.
ScoringRanks the remaining nodes to choose the most suitable Pod placement. Best score wins.

Nodes surviving the filter are called feasible: Nodes that meet the scheduling requirements for a Pod are called feasible nodes. And the critical sentence for debugging: If the list is empty, that Pod isn't (yet) schedulable — it remains unscheduled until the scheduler is able to place it.

Note "yet". The scheduler does not give up or fail the Pod. It re-tries forever, which is exactly what makes node autoscaling possible in lesson 7: something else can notice the Pending Pod and create a node for it.

Once a node wins, the scheduler notifies the API server about this decision in a process called binding. It writes a name onto the Pod — lesson 1's pattern again. The kubelet on that node takes it from there.

What filtering actually checks

FilterRejects the node when…
Resource fitRemaining requests cannot cover this Pod's requests (lesson 3)
TaintsThe node is tainted and the Pod lacks a matching toleration
Node selector / affinityNode labels do not match what the Pod requires
Port conflictsA requested hostPort is already taken
Volume constraintsThe Pod's volume cannot attach there — commonly a zone mismatch

Taints and tolerations: nodes refusing Pods

Everything else is the Pod choosing nodes. Taints are the reverse — the node repelling Pods by default.

# on the node
kubectl taint nodes gpu-1 workload=gpu:NoSchedule

# in a Pod that is allowed there
tolerations:
  - key: workload
    operator: Equal
    value: gpu
    effect: NoSchedule

Three effects, and the difference matters:

EffectMeaning
NoScheduleDo not place new Pods here without a toleration. Existing Pods stay.
PreferNoScheduleTry not to. A scoring preference, not a filter — it will still land here if nothing else fits.
NoExecuteAs NoSchedule, and evict Pods already running that do not tolerate it.

A toleration permits; it never attracts. Tolerating the GPU taint does not send your Pod to a GPU node, it only stops that node refusing. To actually aim at it you need a node selector or affinity as well. Pairing a taint with a label is the standard way to reserve nodes for a workload.

Kubernetes taints nodes itself too — node.kubernetes.io/not-ready, unreachable, disk-pressure and others. A sudden wave of evictions usually means a node picked up a NoExecute taint.

Affinity and spread: shaping placement

MechanismExpresses
nodeSelector"only on nodes with this label". Simple, exact, hard.
Node affinitySame idea with operators (In, NotIn, Exists) and a soft variant.
Pod affinity"near Pods like these" — co-locate with a cache, for example.
Pod anti-affinity"away from Pods like these" — keep replicas off the same node.
Topology spread constraints"spread evenly across zones or nodes, within a skew I choose".

Each comes in two strengths, and the names are a mouthful but the distinction is the important part:

  • requiredDuringSchedulingIgnoredDuringExecution — a filter. Not satisfiable means Pending, forever.
  • preferredDuringSchedulingIgnoredDuringExecution — a score. Honoured if possible, ignored if not.

IgnoredDuringExecution appears in both: these rules are checked when placing a Pod and never re-checked. A Pod does not move because conditions changed later. Pods never move at all (lesson 2).

The most common self-inflicted Pending

Required anti-affinity on hostname with more replicas than nodes. "No two replicas on the same node" with 5 replicas and 3 nodes means 2 Pods are unschedulable by construction, and they will wait forever.

Use topology spread constraints with a maxSkew instead when you want balance rather than an absolute rule — it degrades gracefully instead of deadlocking.

Reading the real thing

kubectl describe pod gives you a one-line tally, and it is almost always enough:

0/3 nodes are available:
  1 node(s) had untolerated taint {workload: gpu},
  2 Insufficient cpu.

Read it as arithmetic. Three nodes, three rejections, every node accounted for. Each clause names a filter and a count, so you know exactly which constraint to relax — add a toleration, lower the request, or get more nodes.

MessageUsually means
Insufficient cpu / memoryRequests do not fit. Lower them, or add capacity.
had untolerated taintReserved nodes. Add the toleration — and a selector if you meant to target them.
didn't match Pod's node affinity/selectorNo node carries the label. Check for a typo before adding nodes.
didn't match pod anti-affinity rulesUsually more replicas than nodes under a required rule.
had volume node affinity conflictThe volume is in one zone and the feasible nodes are in another.

✍️ Do it by hand

Three nodes, 4 CPU allocatable each. node-3 is tainted team=data:NoSchedule. Current requests: node-1 3.5, node-2 3.8, node-3 0.

  1. A Pod requests cpu: 1 with no tolerations. What happens?
  2. The same Pod with a matching toleration?
  3. Does adding the toleration guarantee it lands on node-3?
  4. A Deployment has 4 replicas with required anti-affinity on hostname. How many schedule?
  5. How would you express "spread across nodes, but do not block the rollout"?
Show answer

1) Pending. node-1 has 0.5 free and node-2 has 0.2, so both fail the resource filter; node-3 fails on the taint. The message would read 0/3 nodes are available: 1 node(s) had untolerated taint {team: data}, 2 Insufficient cpu.

2) It schedules on node-3 — now the only feasible node.

3) No. A toleration only stops a node refusing; it does not attract. Here node-3 wins because the others are full. If node-1 had room, scoring would decide, and it might well prefer the emptier node — but that is a preference, not a promise. To guarantee it, add a node selector.

4) Three. One per node, and the fourth is Pending forever, because a required rule cannot be relaxed.

5) A topology spread constraint over kubernetes.io/hostname with maxSkew: 1 and whenUnsatisfiable: ScheduleAnyway. You get balance when it is available, and placement rather than deadlock when it is not.
