Lesson 3

Requests and limits

Two numbers per container, and almost every confusing production incident traces back to them. They sound like the same thing. They are used by different components, at different times, for different purposes.

Explain what requests and limits each do and who enforces them, work out a Pod's QoS class, and predict whether a container gets throttled, OOMKilled or evicted.

Two numbers, two readers

    memory: 256Mi

The documentation is precise about the split: the kube-scheduler uses this information to decide which node to place the Pod on for requests, while for limits the kubelet enforces those limits so that the running container is not allowed to use more of that resource than the limit you set.

The scheduler does not look at actual usage

This single fact explains more confusion than anything else in Kubernetes. A node is "full" when the sum of requests reaches its capacity — regardless of what is actually being used.

So a node sitting at 9% real CPU can refuse to accept a new Pod, because the Pods on it asked for everything. Requests are an accounting system, and you are paying for what you declare.

The units bite people once each

  • CPU is measured in cores. 1 is one core; 500m is 500 millicores, half a core. It is a rate, not an amount.
  • Memory is bytes, usually with a suffix. Watch the two families: Mi is 2²⁰ (1,048,576) while M is 10⁶ (1,000,000). 256Mi and 256M differ by about 5%.

The common typo is writing cpu: 1000 meaning one core. That asks for a thousand cores, and the Pod stays Pending forever.

CPU and memory fail completely differently

CPU is compressible — you can have less of it and simply go slower. Memory is not: once bytes are written, the only way to reclaim them is to kill something. Kubernetes enforces this asymmetry exactly.

Over its limitWhat happens
CPUcpu limits are enforced by CPU throttling. When a container approaches its cpu limit, the kernel will restrict access to the CPU corresponding to the container's limit. The container survives, and gets slow.
Memorymemory limits are enforced by the kernel with out of memory (OOM) kills. When a container uses more than its memory limit, the kernel may terminate it.

There is a subtlety in that memory quote worth keeping: terminations only happen when the kernel detects memory pressure. Thus, a container that over allocates memory may not be immediately killed. So an over-limit container can run fine for hours and die the moment the node gets busy — which is why OOMKills so often arrive in clusters, not in testing.

Practical consequence: a CPU limit that is too low produces a service that is mysteriously slow under load, with no errors and nothing in the logs. Latency rises and nothing looks broken. It is one of the most expensive debugging sessions in platform engineering, and the fix is one number.

QoS: what you get when the node runs out

You never set a QoS class. Kubernetes derives it from the numbers you wrote, and it decides who dies first when a node is under pressure.

ClassCondition
GuaranteedEvery container has both CPU and memory requests and limits set, with limit equal to request for each.
BurstableNot Guaranteed, but at least one container has some request or limit set.
BestEffortNo requests or limits anywhere in the Pod.

And the consequence, quoted: When a Node runs out of resources, Kubernetes will first evict BestEffort Pods running on that Node, followed by Burstable and finally Guaranteed Pods. When this eviction is due to resource pressure, only Pods exceeding resource requests are candidates for eviction.

That last sentence is the one to remember. Staying under your request is genuine protection — the eviction logic looks at what you asked for, so a Burstable Pod living within its request is a poor candidate for eviction even under pressure.

So what should you set?

There is no universal answer, but there is a defensible default position:

SettingRecommendationWhy
Memory requestAlways set itWithout it the scheduler cannot reserve anything and you are BestEffort — first to be evicted.
Memory limitSet it, at or near the requestMemory is incompressible. An unbounded leak takes down the whole node, not just itself.
CPU requestAlways set itIt is your share of the node under contention, and the scheduler's only input.
CPU limitContentious — often leave it offThrottling a latency-sensitive service to enforce a ceiling nobody needed is a common self-inflicted wound. Omit it, and the Pod uses spare CPU when it is there.

The counter-argument for CPU limits is real: without them, one noisy workload can starve its neighbours, and performance becomes dependent on who else is on the node. If you need predictability more than speed, set them. Just do it knowingly, rather than because a template had the field.

You cannot set these numbers without measuring first

Every value above is a claim about how much your service uses — which means you need the data from the Observability course before you can set them honestly. Container memory and CPU are gauges, and what you want is a high percentile over a realistic window, not an average.

Averages are what cause OOMKills. A service averaging 200Mi with a daily peak of 900Mi, given a 256Mi limit, dies once a day at the same time and looks healthy on every dashboard that shows means. Lesson 5 there is about computing percentiles for exactly this.

✍️ Do it by hand

A node has 4 CPU and 8Gi allocatable. Three Pods are running, each requesting cpu: 1, memory: 1Gi. Actual usage across all three is about 0.3 CPU total.

  1. How much CPU can the scheduler still allocate?
  2. A new Pod requests cpu: 1500m. Does it schedule?
  3. One container sets memory: requests 1Gi / limits 1Gi and cpu: requests 1 / limits 1. QoS class?
  4. Another sets only memory: requests 1Gi and nothing else. QoS class, and when is it evicted?
  5. A service has cpu: limits 200m. Under load, p99 latency rises from 40ms to 3s with no errors. What do you check?
Show answer

1) 1 CPU. 4 minus the 3 requested. Actual usage of 0.3 is irrelevant — the scheduler counts requests only.

2) No. 1500m > the 1000m remaining, so it stays Pending — on a node that is 92% idle. This is the single most surprising behaviour for newcomers, and the trigger for node autoscaling in lesson 7.

3) Guaranteed. Both resources have request and limit set, and equal. Evicted last.

4) Burstable — something is set, but not everything. It is evicted after BestEffort Pods, and only if it is exceeding its 1Gi request.

5) CPU throttling. A 200m limit caps the container at a fifth of a core; past that the kernel throttles it. No errors, nothing logged, just latency. Check the throttling metric, then raise or remove the limit.
