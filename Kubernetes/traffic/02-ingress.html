Lesson 2

Ingress and ingress controllers

Ingress is two things people constantly conflate: a small API object that says "route this host and path to that Service", and a controller you install that actually does the routing. Create the object without the controller and nothing happens — the same trap as NetworkPolicy without an enforcing CNI.

By the end you can…

Write an Ingress with TLS, explain the role of the controller and IngressClass, pick between the common controllers, and say why the annotation approach became the reason people moved to Gateway API.

What it is

Ingress (networking.k8s.io/v1) describes HTTP and HTTPS routing: hosts, paths, backends and TLS secrets. An ingress controller watches those objects and configures a real proxy — NGINX, Envoy, HAProxy, Traefik — to match. The controller itself is exposed to the world once, usually through a single LoadBalancer Service.

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: shop
  namespace: prod
spec:
  ingressClassName: nginx        # which controller owns this
  tls:
  - hosts: [shop.example.com]
    secretName: shop-tls         # certificate + key
  rules:
  - host: shop.example.com
    http:
      paths:
      - path: /orders
        pathType: Prefix
        backend:
          service: {name: orders, port: {number: 80}}
      - path: /
        pathType: Prefix
        backend:
          service: {name: web, port: {number: 80}}

How to use it

  1. Install a controller (usually with Helm) and note its IngressClass name.
  2. Point DNS at the controller's load balancer address; tools like external-dns automate this.
  3. Get certificates — commonly cert-manager, which issues and renews them into the TLS secret.
  4. Write Ingress objects in each application namespace. Backends must be Services in the same namespace.

Where Ingress runs out of road

  • HTTP only. No first-class TCP, UDP or gRPC-specific routing.
  • Annotations carry the real features. Rewrites, timeouts, rate limits, auth and canaries are controller-specific annotations, so Ingress objects are not portable between controllers despite the shared API.
  • One object, many owners. The platform team owns the load balancer and TLS; app teams own routes — but both live in the same Ingress resource, with no way to split permissions.
  • No standard for traffic splitting or header matching.

The Ingress API is frozen: it is stable and supported, but new capabilities go to Gateway API instead. That is the next lesson.

✍️ Do it by hand

  1. You applied an Ingress, but kubectl get ingress shows no ADDRESS and nothing is reachable. First two things to check?
  2. Two controllers are installed. How does an Ingress pick one?
  3. Your team needs a canary sending 10% of traffic to v2 on one controller, via annotation. What is the portability cost?
  4. A route needs to point at a Service in another namespace. Does Ingress allow it?
Show answer

1) Is a controller installed and running, and does ingressClassName match its IngressClass? An Ingress nobody claims stays inert.

2) By spec.ingressClassName matching an IngressClass resource each controller registers.

3) The annotation is specific to that controller. Moving controllers means rewriting every such Ingress.

4) No. Backends must be in the Ingress's own namespace; cross-namespace routing is one of the things Gateway API adds, with explicit permission.
