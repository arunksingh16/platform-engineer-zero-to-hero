Ingress, gateways and service mesh

Kubernetes Services get traffic to Pods. They do not do host-based routing, TLS termination, authentication, rate limiting, retries or mutual TLS. Ingress, Gateway API, API gateways like Kong and service meshes like Istio each add a slice of that, at different places in the path, with different costs. Most "which one?" arguments are really "which slice do I need?" arguments.

Lessons

    Why this is a side course

    It sits on top of Pod networking: everything here assumes Pods can already reach each other. Read it after the CNI course, or after lesson 2 of the main course if you only need the edge.

    What you will be able to do

    Say which layer a request is handled at and which component owns that layer. Write an Ingress and its Gateway API equivalent. Decide whether you need an API gateway at all, and what Kong adds over a plain controller. Explain what a mesh gives you that an ingress cannot, what it costs, and when "no mesh" is the right answer.

    For a scenario-driven explanation you can use in a design review, see "Why do we need Istio?": follow a playback-to-entitlement call, identify the missing controls, compare simpler options and define a measurable pilot.
