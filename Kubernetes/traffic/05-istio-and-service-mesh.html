Lesson 5

Istio and service meshes, plus how to choose

A service mesh moves cross-cutting network behaviour — mutual TLS, retries, timeouts, traffic splitting, per-request metrics — out of every application and into the platform. Istio is the most featureful mesh and the one with the most to operate. Whether you need one is a question about east-west traffic, not about the edge.

By the end you can…

Explain what a mesh does, the difference between sidecar and ambient mode, write a basic Istio policy, name the alternatives, and use a decision table to choose among all four layers in this course.

What a mesh does

  • Identity and mTLS: every workload gets a certificate tied to its service account; connections are encrypted and mutually authenticated without application changes.
  • Authorization: "only the checkout service may call payments" as policy, enforced on identity rather than IP.
  • Resilience: retries, timeouts, circuit breaking and outlier detection set centrally.
  • Traffic shaping: weighted routing, mirroring, fault injection.
  • Telemetry: request rate, errors and latency per service pair, plus tracing hooks, uniform across languages.

How Istio is built

A control plane, istiod, distributes configuration and certificates. The data plane is Envoy proxies, deployed in one of two ways:

Sidecar modeAmbient mode
Proxy placementAn Envoy container injected into every Pod.A per-node ztunnel for L4 and mTLS, and optional waypoint proxies per namespace or service for L7.
CostCPU and memory per Pod; Pods restart to adopt or upgrade.Much lower baseline; L7 cost only where you add a waypoint.
MaturityLong established.Newer; now supported for production use, but check feature parity for your needs.

Istio's ingress is an ingress gateway: an Envoy deployment configured with Gateway API resources, or with Istio's own Gateway and VirtualService. Istio's native APIs are more expressive; Gateway API is the direction of travel.

# require mTLS for everything in the namespace
apiVersion: security.istio.io/v1
kind: PeerAuthentication
metadata: {name: default, namespace: prod}
spec:
  mtls: {mode: STRICT}
---
# only checkout may call payments
apiVersion: security.istio.io/v1
kind: AuthorizationPolicy
metadata: {name: payments-from-checkout, namespace: prod}
spec:
  selector: {matchLabels: {app: payments}}
  action: ALLOW
  rules:
  - from:
    - source: {principals: ["cluster.local/ns/prod/sa/checkout"]}
# 90/10 split between versions
apiVersion: networking.istio.io/v1
kind: VirtualService
metadata: {name: web}
spec:
  hosts: [web]
  http:
  - route:
    - {destination: {host: web, subset: v1}, weight: 90}
    - {destination: {host: web, subset: v2}, weight: 10}

Enable gradually: label a namespace for the mesh, start with PERMISSIVE mTLS (which accepts both), watch the telemetry, then move to STRICT.

What it costs

  • Resources: sidecars add CPU, memory and a little latency to every hop.
  • Complexity: a large API surface, and a new failure mode — "is it the app or the proxy?".
  • Upgrades: control plane and data plane versions must be managed together; sidecars need Pod restarts.
  • Skills: debugging Envoy configuration is a specialty.

The alternatives

OptionCharacter
LinkerdLightweight Rust micro-proxy, simple and focused on mTLS, retries and metrics. Fewer features, much less to run.
Cilium Service MesheBPF and per-node Envoy, no sidecars; natural if Cilium is already your CNI (see CNI lesson 5).
ConsulMesh across Kubernetes and VMs, tied into HashiCorp tooling.
Kuma / Kong MeshEnvoy-based, multi-zone and VM friendly.
Managed meshesIstio-based add-ons from cloud providers (for example AKS) or Cloud Service Mesh; the provider handles upgrades.
No meshLibrary-level retries and TLS, plus NetworkPolicy, plus cert-manager. Perfectly valid at moderate scale.

Traffic stack chooser

✍️ Do it by hand

  1. A team with 12 services wants encrypted internal traffic and little operational burden. What would you try first?
  2. You enable STRICT mTLS and a legacy service outside the mesh starts failing. Why, and what was the safer rollout?
  3. Sidecars are using more memory than your applications. Name two ways out.
  4. A mesh is already installed. Do you still need an ingress controller or gateway?
Show answer

1) Linkerd or Istio ambient, or Cilium mTLS if you already run Cilium. Avoid sidecar Istio with its full feature surface unless you need it.

2) The out-of-mesh client cannot speak mTLS. Start in PERMISSIVE, find who is not meshed from telemetry, then move to STRICT.

3) Move to ambient mode (no per-Pod proxy), or switch to a lighter mesh; also trim proxy resource requests and scope what each sidecar must know.

4) Yes. A mesh handles east-west; you still need an edge for external traffic, though the mesh's own gateway can serve as that edge.
