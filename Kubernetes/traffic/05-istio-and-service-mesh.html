Lesson 5

Istio and service meshes, plus how to choose

A service mesh provides a platform layer for cross-cutting network behaviour — mutual TLS, retries, timeouts, traffic splitting and per-request metrics. Istio is one implementation. The reason to adopt it is a concrete service-to-service problem, not simply having microservices.

By the end you can…

Explain why a team might need Istio using a production scenario, distinguish it from a load balancer or gateway, compare sidecar and ambient mode, and choose a simpler alternative when appropriate.

If someone asks: "Why do we need Istio?"

A short answer you can explain

"We do not need Istio just because we run Kubernetes. We need consistent identity, access policy and traffic controls between services, and maintaining those separately in every application has become unreliable. Istio can provide a shared enforcement layer. We should adopt it only if those benefits justify running and debugging another critical platform component."

A scenario: Play works, but the platform is hard to operate

Imagine a fictional music platform with 40 services owned by several teams using Java, Go and Python. This is a teaching example, not Spotify's architecture. A public gateway already routes listeners to the playback API:

Listener -> public gateway -> playback API -> entitlement service
                                         -> catalog service
Background importer ---------------------> entitlement service?

The edge works. The problems are now inside the platform:

  1. Teams implement internal TLS and certificate rotation differently. Some internal calls are still plaintext.
  2. The entitlement service should accept only approved caller workloads, but shared network reachability is being mistaken for permission.
  3. One SDK retries three times while another retries five times. A slow dependency causes a retry storm.
  4. A new entitlement version needs a small, measurable share of internal requests before wider rollout.
  5. Incidents cross language and team boundaries, but service-pair request metrics are inconsistent.

Explain each requirement, then the mechanism

What changes with a deliberately configured mesh
RequirementIstio mechanismWhat you still own
Encrypt and authenticate participating workloadsWorkload identity, managed certificate rotation and mTLS on captured mesh pathsEnrollment, trust boundaries, bypass prevention and enforcing the intended policy; installation alone is not enforcement.

Keep slow calls from consuming every resourceConfigured timeouts, bounded retries and connection/outlier controls where supportedEnd-to-end deadlines, load shedding, idempotency and avoiding retries at multiple layers. A mesh does not create dependency capacity.

In sidecar mode, Envoy handles the supported captured traffic next to the application. In ambient mode, ztunnel provides the secure L4 layer; HTTP routing, request metrics and L7 authorization require appropriate waypoints. Do not promise all these outcomes from ztunnel alone.

Why not just use the existing components?

  • LoadBalancer Service: exposes and distributes connections; it does not by itself provide authenticated workload identity and uniform internal HTTP policy.
  • Ingress or an edge API gateway: controls traffic traversing that gateway. Direct playback-to-entitlement calls do not automatically pass through it. A deliberately designed internal gateway may meet a narrower requirement without a full mesh.
  • NetworkPolicy: remains useful for network segmentation, but the standard API does not provide certificate-based caller identity or HTTP traffic splitting. Use it alongside, not as a synonym for, mesh policy.
  • Application libraries and certificate automation: can meet the requirements without a mesh if teams can reliably maintain them. Certificate issuance alone does not wire application mTLS, authorization or safe retries.

When "no Istio" is the better answer

A small catalog application with an edge gateway, working application TLS, consistent client libraries and no unmet internal traffic-policy requirement may gain little from Istio. Service count is context, not a threshold: even many services do not automatically require a mesh, and a few services can have strong identity requirements. Compare the smallest solution that closes the actual gap.

Prove the reason before rolling it out

Pilot one non-critical caller/destination pair. Record the baseline latency, error rate and resource use; define acceptable overhead before testing. Verify that an allowed identity succeeds, a disallowed identity fails, certificates rotate, and a rollback works. If HTTP features are required, test them on the chosen data plane. Test dependency timeouts without duplicated retries, then expand only after the platform team can operate upgrades, policy changes and proxy incidents.

Practise the explanation

A colleague says: "We already have an ALB or Application Gateway. Why add Istio?" Answer in four parts: the failing scenario, the missing capability, the mechanism and the trade-off.

Show a sample answer

"Our edge gateway already gets traffic into the platform. The unresolved problem is playback calling entitlements internally: callers need workload identity, explicit authorization and consistent traffic controls across our language stacks. Istio can enforce those on participating service-to-service paths; ambient HTTP features need a waypoint. It adds proxies, resource cost and operational complexity, so we will pilot that path and compare it with application TLS/policy or a narrower internal gateway before adopting it broadly."

What a mesh does

  • Identity and mTLS: every workload gets a certificate tied to its service account; connections are encrypted and mutually authenticated without application changes.
  • Authorization: "only the checkout service may call payments" as policy, enforced on identity rather than IP.
  • Resilience: retries, timeouts, circuit breaking and outlier detection set centrally.
  • Traffic shaping: weighted routing, mirroring, fault injection.
  • Telemetry: request rate, errors and latency per service pair, plus tracing hooks, uniform across languages.

How Istio is built

A control plane, istiod, distributes configuration and certificates. Sidecar and waypoint proxies use Envoy; ambient's L4 ztunnel is a separate purpose-built proxy, not Envoy. The two deployment models are:

Sidecar modeAmbient mode
Proxy placementAn Envoy container injected into every Pod.A per-node ztunnel for L4 and mTLS, and optional waypoint proxies per namespace or service for L7.
CostCPU and memory per Pod; Pods restart to adopt or upgrade.Much lower baseline; L7 cost only where you add a waypoint.
MaturityLong established.Newer; now supported for production use, but check feature parity for your needs.

Istio's ingress is an ingress gateway: an Envoy deployment configured with Gateway API resources, or with Istio's own Gateway and VirtualService. Istio's native APIs are more expressive; Gateway API is the direction of travel.

# require mTLS for everything in the namespace
apiVersion: security.istio.io/v1
kind: PeerAuthentication
metadata: {name: default, namespace: prod}
spec:
  mtls: {mode: STRICT}
---
# only checkout may call payments
apiVersion: security.istio.io/v1
kind: AuthorizationPolicy
metadata: {name: payments-from-checkout, namespace: prod}
spec:
  selector: {matchLabels: {app: payments}}
  action: ALLOW
  rules:
  - from:
    - source: {principals: ["cluster.local/ns/prod/sa/checkout"]}
# 90/10 split between versions
apiVersion: networking.istio.io/v1
kind: VirtualService
metadata: {name: web}
spec:
  hosts: [web]
  http:
  - route:
    - {destination: {host: web, subset: v1}, weight: 90}
    - {destination: {host: web, subset: v2}, weight: 10}

These policy fragments illustrate a sidecar-mode deployment, not a complete installation. The version split also needs a Service, healthy endpoints and a DestinationRule defining v1/v2 subsets. In sidecar mode, migrate gradually using PERMISSIVE (plaintext and mTLS), observe clients, then enforce STRICT. Ambient uses mTLS for traffic between enrolled workloads; PERMISSIVE is not the same migration switch there. Review ambient-specific enrollment, policy attachment and protection against out-of-mesh plaintext paths.

What it costs

  • Resources: sidecars add CPU, memory and a little latency to every hop.
  • Complexity: a large API surface, and a new failure mode — "is it the app or the proxy?".
  • Upgrades: control plane and data plane versions must be managed together; sidecars need Pod restarts.
  • Skills: debugging Envoy configuration is a specialty.

Traffic stack chooser

✍️ Do it by hand

  1. A team with 12 services wants encrypted internal traffic and little operational burden. What would you try first?
  2. You enable STRICT mTLS and a legacy service outside the mesh starts failing. Why, and what was the safer rollout?
  3. Sidecars are using more memory than your applications. Name two ways out.
  4. A mesh is already installed. Do you still need an ingress controller or gateway?
Show answer

1) First assess whether application TLS and certificate automation already meet the requirement. If not, compare a focused mesh such as Linkerd with Istio's appropriate data plane; validate the actual encryption, identity and policy guarantees rather than treating every CNI authentication feature as equivalent to application-traffic encryption.

2) In sidecar mode, STRICT rejects clients without the required mesh mTLS. Use a staged PERMISSIVE migration, identify exceptions and then enforce STRICT. Ambient requires its own enrollment and plaintext-path policy review.

3) Move to ambient mode (no per-Pod proxy), or switch to a lighter mesh; also trim proxy resource requests and scope what each sidecar must know.

4) Yes. A mesh handles east-west; you still need an edge for external traffic, though the mesh's own gateway can serve as that edge.
