Lesson 1

How traffic gets in, and the layers involved

Before choosing Ingress, Kong or Istio, you need a map of where requests travel and what each stop can do. Two distinctions carry almost everything: which direction the traffic goes, and which protocol layer a component understands.

By the end you can…

Label traffic as north-south or east-west, say what Service types do and do not do, and place Ingress, an API gateway and a mesh on the map.

Two directions

DirectionMeaningTypical tool
North-southBetween the outside world and the cluster.Load balancer, Ingress controller, Gateway API, API gateway.
East-westBetween workloads inside the cluster.Services and kube-proxy or the CNI; optionally a service mesh.

The "which tool" question usually has a different answer for each direction, and mixing them up is the most common source of over-engineering — for example installing a mesh to solve what is purely an edge routing problem.

Two layers

L4 components see connections: IP, port, TCP or UDP. They can balance and forward but cannot look inside. L7 components parse the protocol — usually HTTP or gRPC — so they can route by host, path or header, terminate TLS, retry, rewrite and authenticate.

A Kubernetes Service is L4. That is the baseline everything else is measured against.

What Services give you

TypeWhat it doesLimit
ClusterIPStable virtual IP and DNS name inside the cluster.Not reachable from outside.
NodePortOpens a port on every node.High port numbers, you provide the front door.
LoadBalancerAsks the cloud for an external L4 load balancer.One per Service: cost adds up, and no host or path routing.

Exposing twenty HTTP services as twenty LoadBalancers means twenty public IPs, twenty bills and twenty TLS setups. That is the problem L7 routing at the edge solves: one entry point, many backends chosen by host and path.

The map

ComponentDirectionLayerWhat it adds
Ingress controllerNorth-southL7Host/path routing, TLS termination.
Gateway API implementationNorth-south (and optionally mesh)L4 and L7The same, with a cleaner role model and more route types.
API gateway (Kong, others)North-southL7Authentication, rate limits, transformations, API lifecycle.
Service mesh (Istio, Linkerd, Cilium)East-west (and edge)L4 and L7mTLS, retries, traffic splitting, per-request telemetry between services.

These overlap on purpose

Istio can run an ingress gateway; Kong can implement Gateway API; Cilium can be a CNI, a mesh and a Gateway API implementation. The categories describe jobs, not products. Pick the job first.

✍️ Do it by hand

Classify each need as north-south or east-west, and L4 or L7.

  1. Route api.example.com/orders to one Deployment and /users to another.
  2. Encrypt all traffic between the checkout and payments services.
  3. Expose a PostgreSQL port to a partner network.
  4. Return 429 to clients who exceed 100 requests per minute.
Show answer

1) North-south, L7 — host and path routing: Ingress or Gateway API.

2) East-west, L4 identity with L7 optional — a mesh feature (mTLS).

3) North-south, L4 — a LoadBalancer Service or a Gateway API TCPRoute, not an HTTP ingress.

4) North-south, L7 — rate limiting is gateway territory; a basic ingress controller may offer it through annotations, a gateway offers it as a first-class plugin.
