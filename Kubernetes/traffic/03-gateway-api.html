Lesson 3

Gateway API: the successor to Ingress

Gateway API is the Kubernetes project's answer to every complaint in the last lesson. It splits one overloaded object into three, each owned by a different role, and turns the features that were annotations into typed fields.

By the end you can…

Name the three core resources and who owns each, write a Gateway and HTTPRoute, express a weighted canary without annotations, and say when to move from Ingress.

Three objects, three owners

ResourceOwned byMeaning
GatewayClassInfrastructure providerWhich implementation handles Gateways of this class (like StorageClass).
GatewayPlatform / cluster operatorA listener: ports, protocols, hostnames, TLS. Says which namespaces may attach routes.
HTTPRoute (and GRPCRoute, TLSRoute, TCPRoute, UDPRoute)Application developerMatches and backends, attached to a Gateway.
apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata: {name: public, namespace: infra}
spec:
  gatewayClassName: envoy
  listeners:
  - name: https
    port: 443
    protocol: HTTPS
    hostname: "*.example.com"
    tls:
      certificateRefs: [{name: wildcard-tls}]
    allowedRoutes:
      namespaces: {from: Selector, selector: {matchLabels: {gateway-access: "true"}}}
---
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata: {name: shop, namespace: prod}
spec:
  parentRefs: [{name: public, namespace: infra}]
  hostnames: [shop.example.com]
  rules:
  - matches: [{path: {type: PathPrefix, value: /}}]
    backendRefs:
    - {name: web-v1, port: 80, weight: 90}
    - {name: web-v2, port: 80, weight: 10}

The weights are the 10% canary that needed a controller-specific annotation under Ingress. Header matching, redirects, rewrites and request mirroring are likewise standard fields.

What it fixes

  • Role separation: the platform team controls listeners and certificates; app teams only create routes in namespaces the Gateway admits.
  • Portability: advanced behaviour is in the spec, with conformance tests, rather than annotations.
  • More than HTTP: gRPC, TLS passthrough, TCP and UDP route types.
  • Cross-namespace references are possible but must be allowed explicitly by a ReferenceGrant in the target namespace.

Who implements it

Envoy Gateway, Istio, Cilium, Kong, NGINX Gateway Fabric, Traefik, Contour, HAProxy and the major cloud load balancers all have implementations at varying conformance levels. Gateway API is also being used for mesh traffic (the GAMMA initiative), so the same route types can configure east-west behaviour.

Should you move?

SituationAdvice
New clusterStart with Gateway API.
Simple Ingress, no annotationsWorks fine; migrate when convenient. The ingress2gateway tool helps convert.
Heavy annotation use, multi-team clusters, canariesMigration pays off — you are already paying for the lack of structure.
Your controller is being retiredMigrate to a controller with Gateway API support, not to another Ingress implementation by default.

CRDs are not built in

Unlike Ingress, Gateway API resources are CRDs you install separately, and the version of the CRDs must be supported by your implementation. Check this first when something does not work.

✍️ Do it by hand

  1. Who should be able to change the TLS certificate on port 443: platform or app team? Which object holds it?
  2. An HTTPRoute in prod is not being picked up by the Gateway in infra. Name two causes.
  3. An HTTPRoute backend is a Service in another namespace. What must exist?
Show answer

1) Platform; the Gateway listener holds the certificate reference.

2) The Gateway's allowedRoutes does not admit the namespace, or parentRefs or hostnames do not match the listener. Check the route's status conditions.

3) A ReferenceGrant in the Service's namespace permitting the reference.
