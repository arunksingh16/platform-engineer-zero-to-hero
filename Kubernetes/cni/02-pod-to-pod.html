Lesson 2

How a packet gets from Pod to Pod

There is no Kubernetes magic in this path. It is a network namespace, a virtual cable, a routing decision, and — in about half of all clusters — an extra set of headers wrapped around your packet that quietly costs you 50 bytes of every frame.

By the end you can…

Name every hop between two Pods on different nodes, explain what a veth pair and a network namespace are, tell encapsulated from native routing and say what each demands of the underlay, and do the MTU arithmetic that explains why large responses hang while small ones work.

The Pod's end: a namespace and half a cable

A Linux network namespace is an isolated copy of the whole network stack — its own interfaces, routing table, iptables rules, and port space. Every Pod gets one, and every container in the Pod shares it. That shared namespace is what a Pod is, networking-wise, and it is why containers in a Pod talk over localhost and why two of them cannot both bind port 8080.

A namespace with no interfaces is a sealed room, so the CNI plugin builds a veth pair: two virtual interfaces wired back-to-back, so whatever enters one leaves the other. One end is moved into the Pod's namespace and renamed eth0; the other stays in the host namespace with a name like veth3f2a1b.

# on the node, find the sandbox and look inside its namespace
nsenter -t $(crictl inspect --output go-template \
  --template '{{.info.pid}}' $SANDBOX) -n ip addr show eth0

# and the host end of the same cable
ip -d link show type veth

Then the plugin fills in the rest of the room: an address from IPAM, a default route pointing at the host end of the veth, and — on the host side — a route sending that one address back down the cable. For the common host-local IPAM plugin, the pool is the node's PodCIDR from lesson 1 and the allocation state is a directory of files on disk:

/var/lib/cni/networks/<network-name>/10.244.1.37   # contains the container ID holding it

Why a node sometimes "runs out" of IPs with Pods deleted

Because that allocation state is files, and files survive crashes. A kubelet or runtime killed at the wrong moment can skip the DEL that releases an address, and the file stays. Do that a few hundred times on a long-lived node and IPAM reports exhaustion while kubectl get pods shows a nearly empty node.

It is the same class of bug as a stale lock file, and plugins have grown garbage collection to deal with it — the CNI spec added a GC operation for precisely this.

Same node: two shapes, and the shape matters

With both Pods on one node, the packet never touches a physical NIC. But plugins disagree about what sits between the two host-side veth ends:

ShapeHost sideUsed by
BridgeAll veth ends are enslaved to a Linux bridge (cni0, cbr0). Pods on a node are an L2 segment and ARP for each other.Flannel, the reference bridge plugin, kindnet
Point-to-point routedNo bridge. Each veth is its own link with a /32 host route; the node routes between them and answers ARP by proxy.Calico, Cilium

The routed shape looks stranger and is usually better: no broadcast domain to grow, no bridge forwarding table to overflow, and every Pod's traffic passes through the node's routing and policy layer where it can be inspected and dropped. The bridge shape is simpler to reason about and is why Flannel is the plugin people learn on.

Across nodes: encapsulate, or make the network learn

Now the hard part. Node A has a packet for 10.244.2.19, which lives on node B. The physical network between them has never heard of 10.244.0.0/16 — it knows about node addresses, not Pod addresses. There are exactly two answers, and every CNI is some version of one of them.

Encapsulated (overlay)Native (unencapsulated) routing
IdeaWrap the Pod packet inside a node-to-node packetTeach the real network where Pod ranges live
MechanismVXLAN, Geneve, IP-in-IPBGP to the fabric, cloud route tables, or real VPC IPs
Underlay mustCarry UDP or IP protocol 4 between nodes. That is all.Accept and propagate routes for your Pod CIDRs
Overhead50 bytes (VXLAN/Geneve), 20 (IP-in-IP)None
Pod IPs areInvisible outside the clusterRoutable, and visible to your firewalls and flow logs
Debuggingtcpdump shows tunnels; you must decapsulate to read ittcpdump shows the actual conversation

Overlay wins on portability — it works on any network that passes UDP, including one you do not control and cannot change. Native wins on performance and legibility, but it is a request to the network team, and in a cloud it is usually mediated by route tables with their own hard limits.

Most plugins do both and choose per-destination. Calico's CrossSubnet mode routes natively between nodes in the same subnet and only encapsulates when it has to cross a boundary the underlay will not route — which is the correct answer often enough to be a sensible default.

The MTU bug, which you will meet eventually

Encapsulation adds bytes to every frame, and the underlay's MTU does not grow to accommodate it. So the Pod-facing MTU must come down by exactly the overhead:

ModeOverheadPod MTU on a 1500 underlay
Native routing01500
IP-in-IP201480
VXLAN (IPv4)501450
VXLAN + WireGuard encryption~110~1390

Get it wrong — by hard-coding 1500, or by moving onto an underlay that is itself a tunnel — and you do not get a clean failure. You get this, and it is one of the most misdiagnosed symptoms in Kubernetes:

"Small requests work, large responses hang"

curl to the health endpoint is instant. The TLS handshake completes. Then the first big response body stalls forever and eventually times out. Small files fine, large files never.

That is an oversized frame being dropped silently, with the ICMP fragmentation needed that would have told the sender to back off being eaten by a firewall. Path MTU discovery fails, so the sender keeps retransmitting a packet that can never arrive.

Confirm it in one command, from inside a Pod — this sends a 1472-byte payload that must not be fragmented, which is exactly 1500 on the wire:

ping -M do -s 1472 <pod-ip-on-another-node>   # fails if the real path MTU is lower
ping -M do -s 1422 <pod-ip-on-another-node>   # succeeds on a VXLAN path (1450)

The fix is to set the plugin's MTU correctly, not to disable PMTU discovery.

Leaving the cluster

One more rewrite happens that the network model does not cover. When a Pod talks to something outside the cluster CIDR, its source address is usually masqueraded to the node's IP, because the outside world has no route back to a Pod address.

Most plugins do this by default for any destination outside the Pod CIDR, and it is the reason an external service's logs show node IPs instead of Pod IPs. On a native-routing or cloud CNI where Pod IPs are genuinely routable, you can turn it off — and then your database audit log suddenly shows which Pod connected, which is worth real money during an incident.

✍️ Do it by hand

A cluster runs VXLAN on a 1500-byte underlay. A new service calls an internal API; small calls succeed, responses over about 1.5 KB hang. Pod-to-Pod ping works and so does DNS.

  1. What is the Pod MTU supposed to be here?
  2. Why did ping and DNS not reveal the problem?
  3. Which single command would confirm the diagnosis from inside a Pod?
  4. The team moves the cluster to native routing to "remove the overhead". What must the network provide now?
  5. After that move, the security team can suddenly see Pod IPs in firewall logs. Why?
Show answer

1) 1450. 1500 minus 50 bytes of VXLAN overhead (outer Ethernet-less IP + UDP + VXLAN header).

2) Both send tiny packets. ping's default payload is 56 bytes and a DNS query is a few dozen — they fit under any plausible MTU. Only a full-size frame triggers the drop, which is why the failure correlates with response size rather than destination.

3) ping -M do -s 1472 <remote-pod-ip>. -M do forbids fragmentation, so a 1500-byte frame that cannot pass fails immediately, while -s 1422 succeeds — and the gap between the two brackets the real path MTU.

4) A route for every node's Pod CIDR, learned by the fabric — BGP peering with the nodes, or programmed cloud route tables. Without it, the packet reaches a router that has no idea what 10.244.2.19 is and drops it.

5) Because the Pod addresses are now real addresses on the wire rather than payload inside a tunnel. That is the legibility benefit of native routing — and also the reason it needs the network team's agreement, since those ranges are now part of their address plan.
