Lesson 1

Why a CNI exists at all

A fresh cluster with no network plugin installed does not half-work. Nodes report NotReady, every Pod sits in ContainerCreating, and the error says the CNI config is uninitialized. Kubernetes specifies the network it needs in detail and then deliberately refuses to build it.

By the end you can…

State the three rules of the Kubernetes network model, explain what a CNI plugin is and who calls it, draw the line between what the CNI does and what kube-proxy and DNS do, and size a Pod CIDR without stranding your cluster.

The model: one IP per Pod, no NAT

Kubernetes imposes a network model that any implementation must satisfy. The docs state the requirements plainly: pods can communicate with all other pods on any other node without NAT, and agents on a node (e.g. system daemons, kubelet) can communicate with all pods on that node.

A fourth consequence falls out and matters more than it looks: a Pod must see its own IP as the same address everyone else uses to reach it. No source rewriting, no port translation in the middle.

Why insist on this? Because the alternative is port bookkeeping. The docs call the IP-per-Pod model IP-per-pod precisely to avoid dynamic port allocation, which brings a lot of complications — every application must be configurable to take ports as flags, every service discovery layer must carry a port as well as an address, and every conflict becomes a cluster-wide scheduling constraint.

What the model buys you

Because every Pod has its own IP and its own port space, a container can bind port 80 and mean port 80. Two replicas on the same node both bind 80 and never collide, because they are in different network namespaces. Your application config does not change between your laptop and the cluster.

This is the same move as spec versus status in main course lesson 1: Kubernetes states a property it will maintain, and hides the mechanism that maintains it.

And the part Kubernetes does not implement

Having specified all that, Kubernetes ships no code that does it. The implementation is delegated to a network plugin, and on a modern cluster that means a CNI plugin.

CNI is the Container Network Interface: a CNCF specification, plus a set of plugin binaries, plus a contract about how they are invoked. It predates Kubernetes' adoption of it and is used by other runtimes too, which is exactly why Kubernetes picked it — the networking problem is not Kubernetes-specific.

The contract is almost comically small. A plugin is an executable. The container runtime runs it with the operation in an environment variable and the network config on stdin, and reads a JSON result from stdout:

OperationMeaning
ADDPut this container's network namespace on the network. Return the interfaces, IPs and routes you assigned.
DELTear it down and release the address. Must be safe to call more than once.
CHECKConfirm the container's networking is still as reported.
VERSIONReport which spec versions this binary speaks.

Two directories hold the whole arrangement on every node:

/etc/cni/net.d/        # network configuration files, read in lexical order
/opt/cni/bin/          # the plugin binaries the runtime executes

Note who does the calling. It is not the kubelet — it is the container runtime (containerd, CRI-O). The kubelet asks the runtime for a sandbox; the runtime creates the network namespace and invokes CNI to populate it. This is why a CNI problem so often surfaces as a runtime-level event on the Pod rather than anything in the scheduler or the API server.

The error you will actually see

Warning  FailedCreatePodSandBox  kubelet
  failed to set up sandbox container: plugin type="..." failed (add):
  ... network plugin is not ready: cni config uninitialized

Pods stuck in ContainerCreating and nodes NotReady with no CNI installed is the normal, expected state of a half-built cluster — not a bug. Install a plugin and the node flips to Ready within seconds, because the kubelet was only ever waiting for /etc/cni/net.d to contain a valid config.

Who does what: the division of labour

"Networking" in Kubernetes is at least four separate jobs, run by four separate things. Confusing them is the most common source of a wasted debugging hour, so it is worth fixing the boundaries now.

Test them in that order and you narrow the fault in about four commands: curl a Pod IP directly, then the ClusterIP, then the DNS name, then the external address. The first one that fails names the owner.

The one overlap worth knowing now: some CNI plugins take over the second row as well. Cilium can run with kubeProxyReplacement enabled and there is no kube-proxy on the node at all. Lesson 5 explains why anyone would want that.

Addresses are finite, and you choose the limit early

Every Pod gets an IP, which means every cluster needs a pool of them, and that pool is chosen at install time and is painful to change afterwards.

The classic scheme — Flannel, Calico in its default mode, kubeadm clusters generally — splits one big cluster CIDR into a per-node block called the node's PodCIDR. The controller manager does the splitting, with --cluster-cidr and --node-cidr-mask-size (default /24 for IPv4). The kubelet caps Pods per node separately, at 110 by default.

So three independent numbers interact, and getting them wrong produces either stranded address space or a cluster that cannot grow. Try it:

Pod CIDR planner

Carve a cluster CIDR into per-node blocks and see what the arithmetic actually permits.

Two failure modes show up immediately in that calculator, and both are real clusters people have had to rebuild:

  • Too few nodes. A /20 cluster CIDR with /24 node blocks gives you 16 nodes, forever. The sixteenth node joins and the seventeenth never gets a PodCIDR.
  • Mostly waste. A /24 block is 254 usable addresses for a node that will never run more than 110 Pods. More than half the space is reserved and idle, which only matters when the cluster CIDR has to come out of a real corporate address plan.

And a trap the calculator flags: setting maxPods above what the node block holds. The kubelet will happily admit Pods the IPAM cannot address, and they fail at sandbox creation with an IPAM exhaustion error rather than anything that mentions Pods per node.

Cloud CNIs break this arithmetic completely

The AWS VPC CNI does not carve a cluster CIDR at all — Pods take real IPs from your VPC subnets, so the limit becomes subnet size and per-instance ENI capacity instead. That is a genuinely different model with a different set of catastrophes, and it gets its own treatment in lesson 4.

✍️ Do it by hand

You are designing a cluster. Corporate networking will give you exactly one 10.60.0.0/18 for Pods. You expect 40 nodes now and maybe 120 in two years, running about 60 Pods each.

  1. With the default /24 node block, how many nodes fit?
  2. Does that meet the two-year target?
  3. What node mask would you choose instead, and what does it cost you?
  4. A Pod on a brand-new node is stuck in ContainerCreating while Pods on older nodes are fine. Which of the four owners above is implicated?
  5. Same cluster: Pod-to-Pod by IP works, but curl to a Service ClusterIP hangs. Is your CNI the problem?
Show answer

1) 64 nodes. From /18 to /24 is 6 bits, so 26 = 64 blocks of 256 addresses.

2) No. 64 < 120. The cluster would stop accepting nodes a little over halfway to the target, and the symptom at that point is nodes joining and never becoming usable.

3) /25 — 7 bits from /18, so 128 node blocks of 126 usable addresses each, comfortably above 60 Pods. The cost is headroom: if a node ever needs more than ~126 Pods you cannot get there without re-IPing the cluster. /26 would give 256 nodes but only 62 Pod addresses per node, which is under your 60 target with almost no margin — too tight.

4) The CNI plugin. Pods on existing nodes are fine, so the model works; something about this node specifically — its plugin DaemonSet not yet running, no PodCIDR assigned, or the pool exhausted — is blocking sandbox creation.

5) No. Pod IP reachability is exactly the CNI's job and it is working. Service VIPs are kube-proxy's job (or a kube-proxy replacement). Look there.
