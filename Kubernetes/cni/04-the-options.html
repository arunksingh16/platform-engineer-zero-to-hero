Lesson 4

The options: Flannel, Calico, Cilium, cloud CNIs

There is no best CNI, which is an unsatisfying thing to be told and still true. There are about five real answers, each optimal for a different set of constraints, and the constraints that matter are mostly not technical preferences — they are who owns your underlay, whether anyone audits your Pod IPs, and how much dataplane your team can carry at 3am.

By the end you can…

Say what each major plugin does differently in one sentence, know which choices a managed cluster takes away from you, recognise the IP-exhaustion failure mode of cloud CNIs, and defend a choice with constraints rather than taste.

Four questions that decide it

Work these out before looking at any feature matrix. They eliminate most of the field on their own.

QuestionWhy it decides things
Who owns the network under the nodes?If you cannot ask for routes, you need an overlay. If you can, native routing is faster and far easier to debug.
Must Pod IPs be real addresses outside the cluster?Firewalls, flow logs, per-Pod security groups and some compliance regimes need it. It costs you address space from a real plan.
What policy do you actually need?None, L3/L4, or L7 and DNS-based. Each tier eliminates options — and the first tier eliminates Flannel.
Who operates it?A dataplane nobody on the team can debug is a liability however good its benchmarks are.

Changing your mind later is expensive

Swapping CNI on a running cluster means every Pod gets a new address, usually node by node with workloads drained, and the two plugins' routes and iptables rules coexisting badly in the middle. People do it, with a careful plan and a maintenance window — but the usual advice is to build a new cluster and migrate traffic, which tells you how much fun the in-place version is.

That is the real argument for spending an afternoon on this decision rather than ten minutes.

The field

Flannel — the simple one

A small daemon that gives each node a subnet and connects nodes with a VXLAN overlay (or host-gw direct routing when all nodes share a subnet). That is the whole product. It has no NetworkPolicy support at all, which is the single most important thing to know about it: policies apply cleanly and do nothing, exactly as described in lesson 3.

Pick it when you want connectivity and nothing else — a learning cluster, a CI cluster, an internal tool with no multi-tenancy. Avoid it when anything in the cluster has a security boundary.

Canal — Flannel's network, Calico's policy

Not a separate project so much as a documented combination: Flannel does the dataplane, Calico's policy engine enforces NetworkPolicy on top. It exists because "Flannel but with policy" was such a common request. It is a reasonable, boring upgrade path for an existing Flannel cluster, and a slightly odd thing to choose from scratch now that Calico does both.

Calico — the routed, policy-first one

Calico's identity is native routing rather than encapsulation: Pod addresses are real routes, distributed by BGP, either peered with your physical fabric or spoken node-to-node in a full mesh or via route reflectors. It will encapsulate with VXLAN or IP-in-IP when it must, and CrossSubnet mode does exactly that — native where it can, tunnel where it cannot.

The second half is policy. Calico predates NetworkPolicy and its own CRDs go well beyond it: cluster-wide policies, explicit deny, rule ordering, NetworkSet objects for external CIDR groups, and policy for hosts and not only Pods. It also runs policy-only alongside someone else's CNI — the standard way to get real policy on top of a cloud plugin.

Its dataplane is pluggable: the long-standing iptables/nftables one, and an eBPF one for the same reasons as Cilium's. Operationally it is a node agent (Felix), a routing daemon, and — above a few dozen nodes — Typha, which fans out API server watches so the control plane is not serving every node individually.

Pick it when you run your own infrastructure with a network team to peer with, or when you need serious policy. Think twice when nobody wants to learn BGP and the overlay modes would do.

Cilium — the eBPF one

Cilium replaces most of the Linux networking path with eBPF programs loaded into the kernel. Practically, that buys four things that are hard to get otherwise: policy based on cryptographic-ish identities rather than IPs, L7-aware rules (allow GET /healthz, deny everything else on that port), a kube-proxy replacement that does not degrade as Services multiply, and Hubble — flow visibility that answers "what was denied, and why" without tcpdump.

It is a CNCF graduated project and it is what sits underneath several managed offerings, so a lot of people run it without choosing it. It also carries the most surface area of anything here: ClusterMesh, egress gateways, transparent encryption, bandwidth management, Gateway API. Lesson 5 is about how it works.

Pick it when you need L7 or DNS-based policy, deep flow observability, or kube-proxy's scaling behaviour is hurting. Think twice when your team's kernel debugging skills are thin and your requirements are modest — the failure modes are further from familiar tools.

Cloud CNIs — Pods on the real network

The AWS VPC CNI, and Azure CNI in its VNet mode, take a completely different line: skip the overlay and skip BGP, and give each Pod a genuine address from your cloud subnet, attached to the instance as a secondary IP on an elastic network interface.

What that buys is integration. Pod traffic is ordinary VPC traffic, so flow logs, security groups, firewall rules and load balancer target registration all work on Pods directly, with no translation layer. On AWS that extends to security groups attached to individual Pods and load balancers targeting Pod IPs instead of node ports.

What it costs is addresses, and this is the characteristic outage:

IP exhaustion looks like a scheduling problem and is not

Pods go Pending or fail at sandbox creation. The nodes have plenty of CPU and memory, so the usual Pending triage finds nothing, and the cluster autoscaler may even add nodes that do not help.

Two separate ceilings cause it. Per node: an instance type supports a fixed number of network interfaces and addresses per interface, which caps Pods per node far below 110 on small instances — prefix delegation raises this substantially by handing out /28 blocks instead of single addresses. Per cluster: the subnets simply run out, because every Pod consumed a VPC address that something else in the organisation also wanted.

Both are capacity planning problems that have to happen before the cluster exists, which is why a networking-aware person belongs in that design review.

Historically these plugins did no policy enforcement at all and the answer was to run Calico in policy-only mode beside them; the major cloud CNIs have since grown their own policy agents. Check what your version actually enforces rather than assuming either way — and then run the 30-second test from lesson 3.

Choose one

Answer honestly rather than aspirationally — "we might need L7 policy one day" is how clusters end up running things nobody understands.

CNI chooser

✍️ Do it by hand

Three design reviews. Give an answer and the single constraint that drove it.

  1. A bank, on-prem, 60 nodes. Security requires per-namespace isolation with explicit deny rules, and the network team already runs BGP everywhere.
  2. A startup on EKS. Their auditors want VPC flow logs that attribute traffic to individual workloads, and the security team wants security groups per workload.
  3. The same startup two years on: 300 nodes, 4,000 Services, and complaints that new Services take minutes to become reachable. They also want to allow only POST /v1/charge between two particular services.
  4. A CI cluster that builds and destroys itself hourly, no multi-tenancy.
  5. In case 2, where does NetworkPolicy enforcement come from?
Show answer

1) Calico. The driving constraint is explicit-deny, cluster-wide policy — which standard NetworkPolicy cannot express — and the BGP fabric makes native routing free. Cilium would also work; Calico is the lower-novelty answer given an existing BGP operation.

2) The AWS VPC CNI. The constraint is Pod IPs being real VPC addresses; nothing else gives you flow-log attribution and per-Pod security groups, because those are VPC features that only apply to VPC addresses. Budget the subnet space deliberately and consider prefix delegation from day one.

3) Cilium. Two constraints now point the same way: L7 policy is not expressible in standard NetworkPolicy, and "new Services take minutes" is the classic iptables-mode kube-proxy scaling symptom that a kube-proxy replacement removes. On EKS this means a migration, which is the price of the earlier decision.

4) Flannel, or whatever the local distribution ships. No security boundary means no policy requirement, and the cluster's lifetime is an hour. Spending operational attention here buys nothing.

5) Not from the VPC CNI by default in older versions — historically from Calico in policy-only mode alongside it, and in current versions from the plugin's own network policy agent, which must be enabled. Verify with the deny-all probe rather than the release notes.
