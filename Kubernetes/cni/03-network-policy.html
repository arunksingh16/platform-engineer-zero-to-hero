Lesson 3

NetworkPolicy and who enforces it

A flat network where every Pod can reach every other Pod is the price of the model in lesson 1. NetworkPolicy buys some of it back — but the API accepts your policy whether or not anything in the cluster intends to enforce it, and that is the detail that gets people hurt.

By the end you can…

Explain why policy is default-allow until a Pod is selected, read an additive rule set with no deny in it, avoid the selector gotcha that quietly widens a rule, write a default-deny that does not break DNS, and check in one command whether your plugin enforces any of it.

The default is "everything"

Out of the box, the documentation is explicit: By default, a pod is non-isolated for egress; all outbound connections are allowed, and the same for ingress. Nothing is filtered. Your payments Pod can reach your marketing database, and the compromised image-resizer in a far-off namespace can reach both.

A NetworkPolicy changes that, and it changes it in a specific, surprising way:

The one rule that explains all the others

A Pod is unfiltered until some policy selects it. The moment any policy selects that Pod for a direction, the Pod becomes isolated in that direction, and from then on only traffic matching some policy is allowed. Everything else is dropped.

So policies do not deny. They select — and selection is what denies, by flipping the default for that Pod from allow-all to deny-all.

Three consequences follow, and they are the whole mental model:

  • Policies are additive. Two policies selecting the same Pod produce the union of what they allow. There is no ordering, no priority, no first-match-wins.
  • There is no deny rule. You cannot write "allow everything except this". You narrow by allowing less, never by subtracting.
  • Directions are independent. Isolating ingress does nothing to egress. A Pod can be locked down inbound and still free to exfiltrate.

They are also namespaced objects that select by label, not by address. Scale a Deployment and the new Pod is covered the moment it exists, with no address bookkeeping anywhere. That is the same identity-over-address idea that lesson 5 takes to its conclusion.

Default-deny, the way everyone starts

This is the canonical first policy. It allows nothing, which is the point — it selects every Pod in the namespace and provides no rules, so every Pod becomes isolated for ingress with an empty allow-list:

apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-ingress
  namespace: prod
spec:
  podSelector: {}          # {} means every Pod in this namespace
  policyTypes: [Ingress]   # ingress only — egress is untouched

Then you add back what the application needs, one allow at a time:

spec:
  podSelector:
    matchLabels: {app: api}
  policyTypes: [Ingress]
  ingress:
    - from:
        - podSelector:
            matchLabels: {app: web}
      ports:
        - protocol: TCP
          port: 8080

Note what the second policy does not say: it does not mention the deny. The two coexist, the union is "api accepts 8080 from web, and nothing else accepts anything", and either can be deleted independently.

The YAML gotcha that widens your rule

These two differ by one dash and they are not close to equivalent:

# AND — Pods labelled app=web, in namespaces labelled team=payments
from:
  - namespaceSelector: {matchLabels: {team: payments}}
    podSelector:       {matchLabels: {app: web}}

# OR — every Pod in those namespaces, PLUS app=web Pods anywhere
from:
  - namespaceSelector: {matchLabels: {team: payments}}
  - podSelector:       {matchLabels: {app: web}}

One list element with two selectors is an intersection. Two elements is a union. The second form is almost never what someone meant to write, and it reviews clean because the words are all correct.

The thing that breaks: DNS

Turn on default-deny-egress in that simulator without allow-dns-egress and watch the DNS column go red. In a real cluster that is not a red square, it is an incident: every name lookup in the namespace times out, applications hang on connect rather than failing fast, and the logs are full of resolver errors that point at CoreDNS, which is perfectly healthy.

Egress policies isolate everything outbound, and name resolution is outbound traffic. Allow it explicitly:

spec:
  podSelector: {}
  policyTypes: [Egress]
  egress:
    - to:
        - namespaceSelector:
            matchLabels: {kubernetes.io/metadata.name: kube-system}
          podSelector:
            matchLabels: {k8s-app: kube-dns}
      ports:
        - {protocol: UDP, port: 53}
        - {protocol: TCP, port: 53}

Both protocols. UDP carries almost all of it; TCP carries the retry when a response does not fit, and omitting it produces a failure that only appears for large responses — the same shape as the MTU bug in lesson 2, and just as annoying to find.

Note the kubernetes.io/metadata.name label. The control plane sets it on every namespace automatically, which makes it the reliable way to select one namespace without relying on a label someone may not have added.

Who is actually enforcing this?

Now the part that justifies this lesson living in a CNI course. NetworkPolicy is an API object; the API server stores it and nothing else happens. Enforcement is the network plugin's job, and the docs warn plainly that policies are implemented by the network plugin, so with a plugin that does not support NetworkPolicy, creating the resource will have no effect.

No error. No warning. No status field. kubectl get networkpolicy lists your carefully reviewed policy, the compliance checkbox is ticked, and the cluster is as flat as the day it was built. Flannel is the common case — it is a networking plugin only, and the usual fix is Canal, which is Flannel for connectivity plus Calico for policy.

Check it in 30 seconds

Do not infer this from documentation. Prove it on the cluster in front of you:

kubectl create ns np-test
kubectl -n np-test run target --image=nginx --labels app=target
kubectl -n np-test expose pod target --port 80
kubectl -n np-test apply -f - <<'EOF'
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: {name: deny-all}
spec:
  podSelector: {}
  policyTypes: [Ingress]
EOF
kubectl -n np-test run probe --rm -it --image=busybox --restart=Never -- \
  wget -qO- --timeout=4 http://target
# connection refused/timeout  → enforced.
# the nginx welcome page      → your plugin is ignoring policy.
kubectl delete ns np-test

What the standard API cannot do

NetworkPolicy is a deliberately small, portable API, and its limits are where plugin-specific CRDs come in:

You wantStandard NetworkPolicyWhere it lives instead
Cluster-wide rulesNo — policies are namespacedCalico GlobalNetworkPolicy, Cilium CiliumClusterwideNetworkPolicy, or the newer AdminNetworkPolicy API
Explicit deny, and priorityNo — allow-only, unorderedAdminNetworkPolicy, or plugin CRDs with an order field
L7 rules (this HTTP path, that Kafka topic)No — L3/L4 onlyCilium policy, or a service mesh
Rules by DNS nameNo — labels, CIDRs and portsCilium toFQDNs, Calico NetworkSet/domain rules
A log of what was deniedNoPlugin flow logs: Hubble, Calico flow logs

Stay on the standard API for as long as it fits — it is the only part that survives changing plugins. Reach for a CRD when you have a requirement the standard genuinely cannot express, not because the CRD is nicer.

✍️ Do it by hand

Namespace prod has web, api, db. You apply default-deny-ingress (selects all) and allow-web-to-api (api accepts 8080 from app=web).

  1. Can api still reach db on 5432?
  2. Can api still call an external payment API on the internet?
  3. A teammate adds a policy selecting api that allows ingress from app: batch. Does that narrow or widen what reaches api?
  4. You want "everything except db may reach the internet". How do you express that?
  5. kubectl get netpol shows all three policies and traffic is unchanged. First thing you check?
Show answer

1) No. db is selected by the default-deny, so it is isolated for ingress, and no policy allows anything to it. The connection is dropped at db, not at api.

2) Yes. Both policies set policyTypes: [Ingress] only. Egress is untouched, so every Pod in prod still has unrestricted outbound access.

3) Widens. Policies are additive — the union now lets in app=web on 8080 and app=batch. Nothing a new policy can do will take away an allow granted by an existing one.

4) Not as a single exception, because there is no deny. You isolate every Pod for egress and then grant outbound to everything except db — either by selecting only the non-db Pods, or with an ipBlock allow plus an except for internal ranges. With standard NetworkPolicy the exception has to become a positive statement about someone else.

5) Whether your plugin enforces NetworkPolicy at all. Run the 30-second deny-all test above before debugging a single selector — Flannel without Calico accepts every policy you write and applies none of them.
