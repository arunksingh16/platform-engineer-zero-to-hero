Lesson 5

eBPF, Cilium, and where the dataplane is going

Two lessons ended with "Cilium, because eBPF", which is not an explanation. Here is the actual argument: the Linux packet path Kubernetes inherited scales with the number of rules, Kubernetes generates rules in proportion to Services times endpoints, and at some cluster size those two facts collide.

By the end you can…

Explain why iptables-mode kube-proxy degrades with cluster size, say what eBPF is in one paragraph without hand-waving, describe identity-based policy and why it scales differently, and name honestly what an eBPF dataplane costs you.

The problem: rules grow, and packets walk them

kube-proxy's job from lesson 1 is turning a Service VIP into a Pod IP. In its long-standing iptables mode it does that by writing netfilter rules — a chain per Service, a chain per endpoint, plus the probability arithmetic that spreads connections across backends.

Two costs follow, and only the second one is really fatal:

  • Matching is a walk. Netfilter evaluates rules in a chain in order. More Services means more rules between the packet and its answer. kube-proxy's chain structure keeps this from being as bad as a single flat list, but the direction of travel is clear.
  • Updating is a rewrite. This is the one that hurts. Rules are applied as a table, so a change means regenerating and reloading a large ruleset. At tens of thousands of rules a single endpoint change — one Pod becoming ready — takes real wall-clock time, and changes queue behind each other during a rollout.

The symptom is distinctive and never mentions iptables: a new Service or a new Pod takes a long time to actually receive traffic, deployments appear to succeed while half the fleet still routes to dead endpoints, and it all gets worse as the cluster grows rather than failing outright.

IPVS mode addressed the lookup half by using kernel hash tables for load balancing, and a newer nftables mode addresses the update half with an incremental, better-indexed ruleset. Both are real improvements inside the netfilter world. eBPF leaves it.

What eBPF actually is

eBPF lets you load a small program into the running kernel, attached to a hook — the moment a packet arrives at a device, the moment a socket connects, the moment a process makes a syscall — where it runs on every event, in kernel space, with no module to compile and no reboot.

The reason this is safe enough to deploy on production nodes is the verifier. Before loading, the kernel statically checks the program: bounded loops, no out-of-range memory access, a finite instruction budget. A program that cannot be proved safe is rejected. Then it is JIT-compiled to native instructions, so it runs at roughly the speed of kernel code, because it is kernel code.

Programs keep state in maps — hash tables, arrays and LPM tries that both the program and userspace can read and write. That is the structural difference from iptables in one word:

Note where the pain starts. Below a few hundred Services none of this matters and anyone telling you otherwise is selling something. Past a few thousand, with endpoints churning on every deploy, it stops being theoretical.

Cilium's two real ideas

1. Socket-level load balancing

Because eBPF can attach at the socket layer, Cilium can resolve a Service VIP to a backend address when the application calls connect(), before a packet exists. The Pod's connection is established directly to the backend; there is no per-packet address translation on the way out, and no conntrack entry maintained for the rewrite.

That is the kube-proxy replacement in one sentence, and it is why the cost curve above flattens: the work happens once per connection, as a map lookup, instead of per packet against a ruleset.

2. Identity instead of addresses

This is the deeper change. Policy in lesson 3 is written about labels but enforced, in a traditional dataplane, by expanding those labels into the current set of Pod IPs and writing rules about addresses. Every scale-up, every rollout, every evicted Pod invalidates that expansion and forces an update.

Cilium instead allocates a numeric security identity per unique label set, shares it cluster-wide, and carries it with the traffic — so the enforcement point can decide using the identity rather than a lookup from address to meaning:

app=api, env=prod     → identity 4721
app=web, env=prod     → identity 5588
# policy: allow 5588 → 4721 on tcp/8080

Now scale api from 3 Pods to 300. The identity does not change, the policy does not change, and nothing is reprogrammed — the new Pods simply carry identity 4721. Policy churn is proportional to how often your labels change, which is rarely, instead of how often your Pods change, which is constantly. On a large cluster that is the difference between a dataplane that keeps up and one that does not.

It also makes the denial legible. Because the identity is in the drop event, Hubble can say web was denied to api on 8080 by policy X instead of leaving you to correlate two IP addresses against a Pod list that has since changed.

L7 policy is not eBPF all the way down

Worth being precise, because the marketing blurs it. L3/L4 decisions happen in eBPF. HTTP-aware rules — allow GET /healthz, deny the rest — need something that parses HTTP, and Cilium redirects that traffic to an Envoy proxy running on the node.

It is still per-node and transparent, which is better than a sidecar per Pod. But it is a userspace proxy in the path, with the latency and failure modes that implies. "eBPF is fast" does not transfer automatically to the L7 features.

What it costs

An honest list, because every lesson so far has had one:

  • Your debugging instincts stop working. iptables -L shows almost nothing on an eBPF node. The state lives in maps, and reading it means cilium monitor, cilium bpf lb list, bpftool — real tools, but not ones your on-call rotation already knows.
  • Kernel version matters. Features gate on kernel support in a way that iptables never did. On a managed node image you may simply not have the kernel a feature wants.
  • Memory. Maps are preallocated and sized by configuration. Conntrack and load balancer maps on a busy node are not free, and a map that fills up drops entries rather than growing.
  • Surface area. ClusterMesh, egress gateway, encryption, bandwidth manager, Gateway API. Every one is a feature you can enable and then have to operate.

Which loops back to lesson 4's last question. A dataplane your team cannot debug at 3am is not an upgrade, and a 40-node cluster with modest policy needs gets nothing here that Calico does not already give it.

✍️ Do it by hand

A 300-node cluster, ~4,000 Services, iptables-mode kube-proxy. During a large rollout, some clients get connection refused for several minutes against Pods that were deleted long ago.

  1. What is the mechanism behind the delay?
  2. Why does it get worse during a rollout specifically?
  3. Give two fixes: one that keeps netfilter, one that leaves it.
  4. After moving to Cilium, scaling a Deployment from 3 to 300 causes no measurable policy-programming work. Why not?
  5. The team enables L7 policy and p99 latency rises slightly. Is that a bug?
Show answer

1) Every endpoint change requires regenerating and reloading a very large ruleset. Until that completes on a given node, that node still forwards to the old backends — so the staleness is per node and the error is a connection to a Pod that no longer exists.

2) A rollout changes many endpoints in quick succession. Each change triggers another full reprogramming, and they queue, so the window in which a node's view is stale stretches from a moment into minutes.

3) Keeping netfilter: switch kube-proxy to nftables mode (or IPVS), which makes updates incremental rather than wholesale. Leaving it: an eBPF kube-proxy replacement, where a backend change is a single map write.

4) Because policy is programmed against the identity derived from the Pod's labels, not against its address. 300 Pods with identical labels share one identity, so the existing rules already cover every new Pod the moment it has that label set.

5) No — it is the design. L7 rules are not enforced in eBPF; matching traffic is redirected to a per-node Envoy proxy that parses the protocol. You traded latency for HTTP-aware control, deliberately. Apply L7 rules only to the traffic that needs them.
