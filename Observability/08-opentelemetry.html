OpenTelemetry

You now know metrics, logs and traces. OpenTelemetry (OTel) is the open standard for producing and shipping all three, so you aren't locked to one vendor.

By the end you can…

Name the OTel components (API, SDK, OTLP, Collector), read a Collector config, and decode a traceparent header by hand to explain how context propagates between services.

The problem OTel solves

Before OTel every vendor had its own agent and format. Switching from one backend to another meant re-instrumenting all your code. OpenTelemetry (a CNCF project) defines one set of APIs, SDKs, data formats and conventions. You instrument once; you choose where data goes by configuration.

The pieces

PieceWhat it is
APIThe interfaces your code calls (tracer.start_span, meter.create_counter). Safe to depend on from libraries: with no SDK it does nothing.
SDKThe implementation: samples, batches and exports data. Configured once at app start.
Instrumentation librariesReady-made wrappers for frameworks (Flask, Express, JDBC…) so you get spans and metrics with little or no code ("auto-instrumentation").
OTLPOpenTelemetry Protocol: the wire format (gRPC on 4317, HTTP on 4318) for traces, metrics and logs.
CollectorA standalone service that receives, processes and exports telemetry. Sits between your apps and your backends.
Semantic conventionsAgreed attribute names (http.request.method, db.system, service.name) so data from different languages looks the same.
ResourceAttributes describing who is emitting: service.name, service.version, k8s.pod.name, cloud.region.

The Collector pipeline

Receivers accept data (OTLP, Prometheus scrape…). Processors transform it (batch, add attributes, sample, drop). Exporters send it on. Changing backend = editing the exporters, not your app.

Instrumenting by hand (Python)

from opentelemetry import trace
from opentelemetry.sdk.trace import TracerProvider
from opentelemetry.sdk.trace.export import BatchSpanProcessor
from opentelemetry.exporter.otlp.proto.grpc.trace_exporter import OTLPSpanExporter
from opentelemetry.sdk.resources import Resource

provider = TracerProvider(resource=Resource.create({"service.name": "checkout"}))
provider.add_span_processor(BatchSpanProcessor(OTLPSpanExporter(endpoint="http://localhost:4317")))
trace.set_tracer_provider(provider)
tracer = trace.get_tracer(__name__)

with tracer.start_as_current_span("charge-card") as span:
    span.set_attribute("payment.provider", "stripe")
    ...  # your code; child spans nest automatically

Context propagation — how a trace crosses services

For service B's span to join service A's trace, A must pass the trace identity along with the request. OTel uses the W3C traceparent HTTP header:

traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
             │  └────────── trace-id (32 hex) ─────┘ └ parent span-id ┘ └ flags (01 = sampled)
             └ version

The receiving service reads it, keeps the same trace-id, and creates its own spans with the incoming span-id as parent. Then it passes a header downstream with its span-id.

✍️ Do it by hand

Service A receives no header, so it starts a new trace and calls B with traceparent: 00-aaaa…aaaa-1111111111111111-01. B calls C.

  1. What trace-id does C see?
  2. B creates a span with id 2222222222222222. What is that span's parent id, and what span-id goes in the header B sends to C?
  3. Decode the flags in …-00. What does it mean for sampling?
Show answer

1) The same aaaa…aaaa — the trace-id never changes. 2) Parent id = 1111111111111111 (A's span). The header to C carries 2222222222222222 (or a deeper child span's id) as the parent. 3) Flags 00 mean "not sampled": the trace is propagated so IDs still correlate, but spans are not recorded/exported.
