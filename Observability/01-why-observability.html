Monitoring vs observability

Monitoring means watching things you already know can go wrong: "alert me if CPU > 90%". You decided the questions in advance.

Observability is a property of a system: can you understand what is happening inside it by looking at the data it emits — including for problems you never predicted? A system is observable when you can ask new questions ("why are only users in Germany on the iOS app slow?") without shipping new code.

To do that, software emits telemetry. There are three main kinds, called signals.

📈 Metrics
Numbers over time. Cheap, great for "is something wrong, and since when?"
📜 Logs
Timestamped event records. Great for "what exactly happened?"
🧵 Traces
The path of one request across services. Great for "where was the time spent?"

Watch a request travel

Each service emits metrics (how many / how slow), logs (what happened) and trace spans (how long this request spent here).

✍️ Do it by hand

In one minute, 1,000 checkout requests arrived and 50 of them returned an error.

  1. What is the error rate as a percentage?
  2. If traffic doubles to 2,000 requests per minute at the same error rate, how many errors per minute is that?
  3. Which signal gave you these numbers — metrics, logs or traces?
Show answer

1) 50 ÷ 1000 = 0.05 = 5%. 2) 5% of 2000 = 100 errors/min. 3) Metrics — aggregate numbers over time. Notice a metric tells you that 5% fail, but not why.

The investigation loop you will use for the rest of your career

Metrics tell you something is wrong and when → traces tell you which service or call is responsible → logs tell you the exact error. Telemetry that can be linked (same trace ID in logs and spans) makes this loop fast. That linking is what OpenTelemetry standardises, in lesson 8.
