Lesson 6

Logs you can actually search

Metrics say that something broke. Logs say what happened. But only if they are written so a machine can search them.

By the end you can…

Convert an unstructured log line into a structured one, use levels and correlation IDs properly, and follow one request through many services by hand.

Unstructured vs structured

Unstructured (human-friendly, machine-hostile):

2026-11-03 10:15:02 ERROR Payment failed for user 4821 after 2300ms

To find all slow payments you'd need a fragile regex. Structured (one JSON object per line):

{"ts":"2026-11-03T10:15:02Z","level":"error","service":"payment",
 "msg":"payment failed","duration_ms":2300,
 "trace_id":"ab12","error":"gateway_timeout"}

Now "show me service=payment and duration_ms > 2000" can be expressed as a field query. How fields are indexed depends on the system and configuration; for example, Loki indexes labels and can parse JSON fields at query time.

The most important field: trace_id

One user action touches many services, each writing its own logs. When available, the same correlation ID (the trace ID from lesson 7) lets you find lines for one request across services and jump between a log line and the trace.

Habits that make logs useful

  • Structured JSON, consistent field names across services.
  • Include consistent fields such as service, level, and a UTC timestamp. Include trace_id when tracing context is available.
  • Never log secrets or personal data (passwords, tokens, card numbers).
  • Logs are the most expensive signal by volume — log events that matter, not every loop iteration.
  • High-cardinality identifiers do not belong in metric labels. If request or user correlation is genuinely needed, use an approved opaque or pseudonymous identifier in logs or traces with appropriate access and retention controls; do not log raw personal data.
