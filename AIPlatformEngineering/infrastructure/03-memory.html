Lesson 3 / Fit is a budget, not a promise

Will the workload fit?

“Seven billion parameters × two bytes” estimates weights. It does not estimate the whole training job or a busy inference replica.

By the end you can…

Calculate a transparent memory budget, identify architecture-dependent assumptions, and explain why peak allocation needs measurement.

1. Keep units explicit

One GB is 10⁹ bytes; one GiB is 2³⁰ bytes. A 7-billion-parameter model with two-byte weights contains 14 GB, or 13.04 GiB, of weight data. Advertised device memory and tools may use different units. Convert before comparing.

2. Training has more than weights

Budget weights, gradients, optimizer state, activations, temporary buffers and runtime overhead. An illustrative mixed-precision Adam layout has 2-byte weights, 2-byte gradients, a 4-byte master weight copy and two 4-byte optimizer moments: 16 bytes per parameter in total. That is 104.31 GiB for 7 billion parameters before activations. This is an example layout, not a universal PyTorch multiplier; some implementations retain different representations.

Sharding can distribute persistent state across workers. It does not divide all memory evenly: gathered layers, replicated tensors, communication buffers and activations can dominate peaks. Activation checkpointing trades recomputation for fewer saved activations; a recovery checkpoint on storage solves a different problem.

3. Inference needs room for requests

For a conventional attention model with a KV cache on every layer:

KV bytes = 2 × layers × KV heads × head dimension
           × retained tokens per request × concurrent requests
           × bytes per cached value

The 2 counts keys and values. Use KV heads, not query heads: grouped-query attention can use fewer KV heads. Sliding windows, hybrid architectures, prefix sharing, cache quantization, allocation blocks and eviction change actual usage. A mixture-of-experts model also needs a different weight-residency analysis.

Example: 32 layers × 8 KV heads × 128 dimensions × 4,096 retained tokens × 8 requests × 2 bytes × 2 = 4 GiB. With 13.04 GiB weights, 2 GiB workspace, 1 GiB runtime overhead and 2 GiB unused reserve, the total is 22.04 GiB. This fits a hypothetical 24 GiB device budget, but does not prove eight requests meet latency targets.

Per-device memory planner

Ideal equal sharding of weights, training state and KV cache is assumed. Workspace, overhead and reserve are entered per device. The training mode ignores KV fields; inference ignores other training state. This planner does not model adapter training.

Default: weights 13.04 GiB + KV 4 GiB + workspace 2 GiB + overhead 1 GiB + reserve 2 GiB.

22.04 GiB per device including reserve; capacity 24 GiB.

Quantized weight sizes exclude scales, zero points and padding. KV heads may be replicated rather than evenly sharded when the parallel layout requires it. Change device count only after checking the actual runtime layout.

4. Validate the peak, not just steady state

Record memory during model loading, the largest supported sequence/batch, backward, optimizer update, checkpoint save and recovery. Loading a full state dictionary on every worker can fail even if steady-state sharding fits. Test allocator fragmentation and cache eviction under mixed request lengths.

Offloading to CPU or storage can reduce resident GPU state, but adds transfer latency and host capacity requirements. Quantization requires quality validation. Reducing sequence length changes the workload contract. Every “fix” has a cost to measure.

Work it yourself

Double retained tokens to 8,192 with eight requests. Does the default 24 GiB device budget still fit?

Worked answer

KV doubles to 8 GiB; total becomes 26.04 GiB. It no longer fits. Four concurrent requests would restore the original KV size, but reduce concurrency. A larger device, supported sharding or a validated precision change may be alternatives.

Interview practice

“Why did a model that loaded successfully fail under traffic?”

A strong answer

Weight loading only checked one part of memory. I would inspect peak request state, KV-cache growth, temporary workspaces and fragmentation at realistic context lengths, then revise admission limits and benchmark latency and memory together.
