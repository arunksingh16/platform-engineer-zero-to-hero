Lesson 2 / Constraints before rankings

Choosing an accelerator

The fastest advertised chip is not necessarily the cheapest way to finish a training run or serve an acceptable answer.

By the end you can…

Shortlist hardware using hard constraints, then compare compatible candidates on measured workload outcomes.

1. Understand three different ceilings

  • Memory capacity: how much state fits on each device. Running out produces allocation failures or forces sharding/offload.
  • Memory bandwidth: how quickly values move between device memory and compute. A large memory does not necessarily have high bandwidth.
  • Compute throughput: how many operations execute per second for a specified numerical format and execution pattern.

Arithmetic intensity is operations performed per byte moved. A rough upper bound is the smaller of peak compute and memory bandwidth × arithmetic intensity. Real kernels, communication and scheduling reduce achieved performance. Small-batch decode often stresses memory bandwidth; large matrix operations in training or prefill can be compute-heavy. Treat these as hypotheses to profile, not universal labels.

Never compare an FP4 sparse peak against a BF16 dense peak as if they describe the same workload. BF16 and FP16 use two bytes per value but represent numbers differently. Quantization uses lower-precision representations; model quality, kernels, metadata and runtime support determine whether it is useful.

2. Apply gates in order

  1. Compatibility: supported model operations, numerical format, framework, runtime, driver and operating system.
  2. Fit: peak memory per device and host memory, including staging and loading.
  3. Movement: accelerator links, GPU-to-NIC locality, scale-out network and input delivery.
  4. Delivery: obtainable quantity in the required location and time window.
  5. Outcome: deadline-compliant training or latency-compliant serving at acceptable total cost.

3. Different ecosystems, same questions

NVIDIA GPUs commonly use CUDA software, AMD GPUs use ROCm, and Google TPUs or AWS Trainium use different accelerator software stacks. These are ecosystem examples, not interchangeable devices. Portability includes operator support, compiler behavior, numerical validation, observability and team experience. A cheaper device that needs substantial porting can be a poor short-term choice.

CPU inference may be sufficient for a small model, low traffic or a tolerant batch deadline. A hosted endpoint may avoid operating a fleet. Conversely, a large distributed job may justify a tightly connected accelerator system even when its hourly price is higher.

4. Compare cost using outcomes

Invented training comparison: configuration A uses 8 GPUs at $3/GPU-hour for 20 hours: $480. B uses 8 at $5 for 10 hours: $400. B is cheaper per completed run and fits a 12-hour deadline; A does not. Add host, storage, network and recovery costs before a purchase decision.

For inference, measure successful requests meeting the same quality and latency targets per dollar. Keep model revision, input/output mix, cache conditions, precision quality gate and offered load comparable. A peak token-rate claim alone cannot select a fleet.

Work it yourself

Your model requires 90 GiB per replica including headroom. Profile B has faster networking than C. Which do you try first for single-device inference?

Worked answer

C passes the single-device fit gate; B does not. Confirm software and load-test C. A sharded B configuration is another candidate, but introduces more devices and communication. Fast networking does not repair a single-device memory shortage.

Interview practice

“Which GPU would you select?”

A strong answer

I need the workload and constraints first. I would eliminate unsupported and undersized configurations, establish supply and topology, then benchmark the remaining choices against deadline or latency targets. My recommendation would include full allocation cost and the evidence that would justify changing it.
