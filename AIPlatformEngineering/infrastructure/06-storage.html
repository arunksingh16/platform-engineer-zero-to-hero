Lesson 6 / Keep the expensive compute fed

Feeding accelerators and saving progress

The GPUs are idle while thousands of small files are opened. Buying faster accelerators will make that imbalance more expensive.

By the end you can…

Budget the full data path, estimate checkpoint time, and distinguish a fast local cache from durable recovery storage.

1. Draw all the stages

Data starts in a durable source, moves through a network and cache, is decoded or tokenized by CPU workers, enters host buffers and transfers to accelerators. The slowest exposed stage can limit progress. Prefetching overlaps stages but cannot compensate indefinitely for an inadequate sustained rate.

Trace the training data

  1. Durable datasetVersioned objects or shared files supply training shards.
  2. Stage and cacheLocal NVMe avoids repeated remote reads; cold nodes still need filling.
  3. Prepare batchesCPU transforms, tokenization and buffering consume cores and RAM.
  4. Consume on GPUTransfer batches to the accelerator; empty queues expose upstream stalls.

2. Work the input budget

Eight workers each consuming 0.5 GB/s need 4 GB/s of aggregate input at that representation. A 2 GB/s upstream stage can supply at most half that rate. This does not imply exactly 50% GPU utilization: caching, compression, overlap and compute intensity change the relationship.

Measure useful bytes and samples/tokens per second together. Compressed storage bytes differ from decoded batch bytes. The calculator below assumes rates have been normalized to the same byte representation. Benchmark cold-cache startup and steady-state reuse separately; a warm local-cache benchmark can hide an overloaded source.

Find the bottleneck

Input ceiling 2 GB/s: 50% of demand. An 800 GB checkpoint at 4 GB/s takes at least 200 seconds.

Feed ceiling = min(storage, CPU, network). Write lower bound = checkpoint GB / effective GB/s. Change storage to 8: the bottleneck moves to the 5 GB/s network. This steady-flow model omits jitter, metadata and shared read/write contention.

3. Checkpoints are a recovery protocol

A recoverable training checkpoint includes the required model and optimizer state, progress counters, scheduler state and any random-number/data-position state needed by the training system. Weights alone may be enough for inference, but not to resume equivalent training.

Write shards to a new checkpoint location, verify required parts, then publish a completion manifest or pointer using the storage system's supported commit semantics. Never advertise a partly written checkpoint as recoverable. Test restore on replacement workers; account for resharding and software compatibility. Keep durable checkpoints outside the failed node.

If a blocking checkpoint takes 200 seconds after every 1,800 seconds of useful computation, its wall-time share is 200 / (1,800 + 200) = 10%. More frequent checkpoints reduce lost work but increase overhead. Under a simplified uniform-failure assumption, average lost computation is roughly half the useful-work interval; restore time and correlated failures add further cost. Asynchronous saves help only if staging memory, write throughput and consistency hold up.

4. Inference storage is a startup constraint

Model artifacts must reach new replicas, deserialize into host/device memory and warm the runtime before readiness. A 140 GB artifact read at an effective 2 GB/s takes at least 70 seconds for transfer alone. Ten simultaneous starts may share the same bottleneck. Pre-staging and local caches can help; verify artifact identity and ensure caches can be rebuilt.

Cloud role examples are S3, Azure Blob and Cloud Storage for durable objects; managed shared filesystems for compatible shared access; and local SSD/NVMe for staging. Choose by access pattern and measured throughput rather than treating those roles as equivalent APIs.

Work it yourself

GPU utilization falls every 30 minutes and shared-storage writes spike. What do you investigate?

Worked answer

Correlate checkpoint timing with step stalls, host staging memory, write throughput and read contention. Measure save and restore, check whether all ranks are writing duplicate state, and consider supported sharded/asynchronous saves or separate bandwidth. Do not disable recovery blindly.

Interview practice

“How do you size storage for AI?”

A strong answer

I separate durable capacity, input throughput, metadata operations, preprocessing, cache fill and recovery throughput. I test concurrent readers and writers, cold starts and restore time. Dataset terabytes alone are not a sizing plan.
