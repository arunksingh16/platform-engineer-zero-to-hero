Lesson 1 / Start with the workload

From Kubernetes to AI infrastructure

Your Pod is Running. The training job still misses its deadline, and the assistant still makes users wait. Kubernetes placed the work; it did not prove the system can do that work efficiently.

By the end you can…

Explain the basic AI vocabulary, trace training and inference, and write a workload contract before choosing infrastructure.

1. Translate the vocabulary

A tensor is a multidimensional array of numbers. A model combines tensor operations using learned numbers called parameters or weights. A language model consumes tokens: pieces of text produced by its tokenizer, not necessarily whole words. A 7-billion-parameter model has seven billion learned numbers, not seven billion lines of source code.

A CPU is flexible at coordination and varied execution. An accelerator specializes in executing certain operations efficiently; GPUs execute many numerical operations in parallel. Kernels are implementations of those operations. GPU memory holds weights and working data close to computation. Host RAM and disk do not become GPU memory merely because the Pod can access them.

Kubernetes concept you knowAdditional AI question
Resource requestDoes peak device memory fit, including temporary allocations?
ReplicaIs this an independent model copy, or one worker of a distributed copy?
Node affinityAre workers close enough on the accelerator and network fabric?
ReadinessAre weights loaded and execution warmed, not just the HTTP port open?
Persistent storageCan it deliver data and commit recovery checkpoints at the required rate?

2. Follow one training step

Training changes weights to reduce an error measure called the loss. A batch contains examples processed together. A forward pass makes predictions; a backward pass computes gradients, which describe how changing weights affects the loss. An optimizer uses gradients and its own state to update weights.

A training batch, step by step

  1. Read and prepareStorage supplies examples; CPU workers tokenize or transform them.
  2. ForwardAccelerators compute predictions and save activations needed later.
  3. BackwardCompute gradients; distributed workers may exchange gradients or parameters.
  4. Update and repeatOptimizer changes weights. Periodically commit a recoverable checkpoint.

Playback highlights logical stages; real systems overlap data loading, computation and communication. With reduced motion, Play advances one step.

Pretraining learns from a large dataset. Full fine-tuning continues training an existing model's weights. Parameter-efficient fine-tuning, such as training adapters, updates a much smaller parameter subset. It can reduce gradient and optimizer memory substantially, but still needs the base model and activation computation.

3. Follow one inference request

A request, step by step

  1. Route and queueAn independent ready replica receives a prompt; admission policy bounds waiting.
  2. PrefillProcess input tokens and build attention state for the prompt.
  3. DecodeGenerate tokens iteratively, retaining a key/value attention cache.
  4. CompleteStream the answer, release request state and admit new work.

Inference uses weights without optimizer updates. Online inference prioritizes user-visible latency; batch inference can trade waiting time for efficient large batches. The KV cache stores attention keys and values, not a final-answer cache. It grows with retained tokens and active requests. The existing serving-engine lesson explains scheduling and prefix reuse.

4. Write a workload contract

Our fictional training team has a dense model, a fixed training-token budget and a completion deadline. Our inference team runs an internal coding assistant. Neither team can select a GPU responsibly from parameter count alone.

  • Training: model architecture, trainable parameters, precision, sequence length, global batch, token budget, validation requirements, deadline and recovery objective.
  • Inference: model revision, precision and quality floor, input/output length distributions, arrival rate and bursts, concurrency, TTFT, token-generation pace and errors.
  • Both: budget, software compatibility, location, capacity availability, data paths and failure tolerance.

Example inference targets: p95 time to first token below 1.5 seconds, p95 per-request mean output-token time below 50 ms, errors below 0.5%. These are teaching targets, not universal standards. Record end-to-end completion time and streaming stalls too. An average can conceal a bad long-tail experience.

Work it yourself

A team says “we have 200 users, so buy four GPUs.” What is missing?

Worked answer

Users are not requests per second. Ask how many users are active, their arrival pattern, prompt and answer lengths, model, precision and latency targets. Measure one candidate replica with representative traffic before converting demand to replica count.

Interview practice

“What changes when a Kubernetes platform starts running AI?”

A strong answer

Device memory and topology become placement constraints. Training workers may require coordinated startup and recoverable shared progress. Inference readiness includes model loading, and scaling must account for queues and cold starts. I would establish workload targets and benchmark useful throughput before buying capacity.
