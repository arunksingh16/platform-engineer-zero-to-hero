Lesson 4 / Parallel work has a communication bill

Scaling training across accelerators

Eight accelerators are not automatically eight times faster. The question is how work and state are divided, and what each worker must wait for.

By the end you can…

Choose a parallelism strategy, trace its communication, and calculate scaling efficiency without changing the learning objective silently.

1. Data parallelism: different examples, same model

Each worker, also called a rank, processes a different slice of the batch with a full model replica. Gradients are combined so replicas apply consistent updates. An all-reduce combines values across ranks and makes the result available to each. In practice, gradient communication can overlap backward computation.

Data-parallel step

  1. Split the batchGPU 0 takes examples A; GPU 1 takes examples B. Both hold the model.
  2. Compute locallyEach rank computes forward and backward on its own examples.
  3. SynchronizeCombine gradients. The faster rank can wait for a straggler.
  4. Update togetherApply the consistent update; start the next step.

Data parallelism helps throughput when a full replica fits. Ordinary replicated data parallelism does not reduce its per-rank model state. Global batch = per-rank microbatch × data-parallel ranks × gradient-accumulation steps. With 2 examples × 8 ranks × 4 accumulation steps, the global batch is 64. Doubling ranks without adjustment changes batch size and potentially training behavior.

2. Shard persistent training state

Fully sharded data parallelism distributes parameters, gradients and optimizer state. Before computing a layer group, ranks gather required parameters; after backward they distribute reduced gradient shards. It can make a larger model fit, at the cost of communication and temporary gathered state. Wrapping/grouping, prefetching and resharding policy affect both speed and peak memory.

Sharded-state lifecycle

  1. Persistent shardsEach rank owns a fraction of parameters and optimizer state.
  2. Gather for computeAll-gather the next parameter group; temporary memory rises.
  3. Compute and reduceForward/backward use parameters; reduce-scatter distributes gradient shards.
  4. Release and updateRelease gathered buffers according to policy and update local state.

3. Tensor and pipeline parallelism

Tensor parallelism divides individual layer operations across accelerators. The ranks repeatedly exchange intermediate results. It can reduce per-device work and memory but is sensitive to link performance, often favoring a tightly connected scale-up domain.

One layer across two GPUs

  1. PartitionGPU 0 holds one matrix slice; GPU 1 holds another.
  2. Compute piecesBoth contribute to the same layer for the same microbatch.
  3. Exchange resultsThe partitioning scheme requires a collective or transfer.
  4. Next layerThe pattern repeats many times, making latency important.

Pipeline parallelism assigns consecutive layer groups to different stages. Microbatches flow between stages. During fill and drain, some stages are idle: pipeline bubbles. Uneven stage times also create waiting.

A simplified forward pipeline

  1. Tick 1Stage A computes microbatch 1; stage B waits.
  2. Tick 2A computes microbatch 2; B computes microbatch 1.
  3. Tick 3A has finished; B computes microbatch 2.
  4. Backward followsGradients traverse the stages; real training uses a forward/backward schedule.

This forward-only sketch shows bubbles; it is not a full training schedule or timing prediction.

Strategies can combine. A job with tensor degree 2, pipeline degree 2 and data-parallel degree 4 has 16 ranks. Expert parallelism for mixture-of-experts models introduces token routing and all-to-all communication; it is a separate design dimension, not a free multiplier.

4. Measure scaling honestly

For comparable work, scaling efficiency = measured speedup / resource multiplier. If an 8-GPU baseline processes 20,000 tokens/s and 16 GPUs process 34,000, speedup is 1.7 and efficiency is 85%. GPU-seconds per token increase by 2/1.7 ≈ 1.18: about 18% more allocation per token. The larger job may still be worthwhile to meet a deadline.

Record model, sequence length, precision, global batch, accumulation, parallel layout and convergence/quality checks. Separate compute, exposed communication, input stalls and checkpoint time. Peak FLOPS cannot predict this curve. Distinguish strong scaling of a fixed workload from scaling the workload along with resources.

Work it yourself

A model's persistent training state does not fit one GPU. A teammate proposes four replicated data-parallel ranks. Will that fix it?

Worked answer

No: each rank still holds the replicated state. Evaluate state sharding, model parallelism, reduced memory techniques or a larger device. Then measure temporary memory and communication. Parameter-efficient fine-tuning is an option only if it meets the learning objective.

Interview practice

“Why did doubling GPUs improve throughput by only 20%?”

A strong answer

I would compare step breakdowns, collective time, input delivery and stragglers while holding the training contract constant. I would check placement and partitioning before buying more GPUs, and compare deadline benefit with GPU-hours per completed run.
