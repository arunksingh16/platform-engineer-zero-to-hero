Lesson 2 / Engine internals

Read the scheduler, do not rebuild it

Monday morning, p95 time to first token has doubled. Nothing was deployed. The model, the engine version and the replica count are unchanged. GPU utilisation reads 97%, exactly as it did last week. Aggregate throughput is flat. Your dashboard is telling you the truth and you still cannot see the problem, because the problem is in the scheduler and you have never read it.

By the end you can…

Explain from an engine's design why paged KV memory cuts waste from 60–80% to under 4%, why admission happens every iteration, what chunked prefill trades away, and what preemption costs — and diagnose the opening incident.

1. Lesson 1 asked for a big batch. Something has to produce it

Lesson 1 ended with a number: 213 concurrent requests of 2,000 tokens is what fits in an A100's spare memory, and decode throughput depends almost entirely on getting near it. That number is not something the GPU gives you. It is the output of two pieces of software:

  • A block manager that decides whether a request's KV cache can be allocated at all.
  • A scheduler that decides, on every forward pass, which admitted requests are in it.

Both are a few thousand lines of ordinary Python in vLLM and SGLang. Reading them is the single highest-return hour in this course, and it is the reason this lesson does not ask you to implement any of it.

2. KV memory is a memory-allocator problem

Suppose you allocate each request a contiguous region large enough for its maximum possible length — the obvious implementation. With an 8,192-token limit and a typical request that actually uses 2,000, three quarters of every reservation is dead. Add requests of mixed sizes arriving and leaving and you also get classic external fragmentation: free memory that exists but not in one usable piece.

The PagedAttention work measured exactly this on the systems that preceded it and reported 60–80% of KV memory wasted on fragmentation and over-reservation. Read that as a batch-size figure rather than a tidiness figure: wasting 70% of your KV memory means roughly a third of the concurrency, which lesson 1 showed is the only lever decode has.

The fix is the one operating systems settled on decades ago. Carve KV memory into fixed-size blocks — 16 tokens each in vLLM's default configuration — and give every request a block table mapping its logical token positions to physical blocks that need not be adjacent. Attention kernels are rewritten to follow the table instead of assuming contiguity.

Request A logical: [0..15][16..31][32..47]
Block table:          #104    #7      #88        ← scattered, deliberately

Physical KV blocks: #7  #88  #104 ... interleaved with every other request

Now the only waste is the unfilled remainder of each request's last block. Work it out with lesson 1's figures: one block is 16 tokens × 128 KB = 2 MB, an average request wastes half of one, and 213 requests therefore waste about 213 MB out of 56 GB of KV cache — under half a percent. That is where the published "under 4%" claim comes from, and you can now derive it rather than quote it.

The indirection buys a second thing

Once a request's tokens are described by a table of block pointers, two requests can point at the same physical block. That makes prefix sharing and copy-on-write for parallel samples a bookkeeping change rather than a new subsystem. Section 6 returns to this.

3. The batch is rebuilt on every forward pass

The second idea is older than paging and just as important. Output lengths are heavily skewed: in a coding assistant, most answers are a few dozen tokens and a few are many hundreds. Hold a batch fixed until all members finish and the arithmetic is brutal — a batch of 32 whose longest member runs 500 steps spends most of those steps computing padding for slots that finished at step 40.

Continuous batching, introduced as iteration-level scheduling in Orca, makes admission a per-iteration decision. A request that emits its stop token releases its blocks immediately and the next waiting request takes the slot on the very next pass. The GPU stops idling between requests, and the effective batch stays near the memory limit instead of decaying toward one.

4. Chunked prefill, and the trade it makes on your behalf

Here is the collision. Lesson 1 measured a 2,000-token prefill at roughly 380 ms of solid compute. A decode step is 18 ms. If a scheduler lets that prefill take a whole forward pass to itself, every other request in the batch — possibly two hundred of them — waits 380 ms for its next token. Users do not experience that as latency; they experience it as the answer freezing mid-sentence.

Chunked prefill splits a long prompt into pieces of a few hundred tokens and mixes a piece with the decode work of other requests in the same pass. The stall becomes bounded and small. This is the stall-free scheduling idea from Sarathi-Serve, and it is now the default in both vLLM and SGLang.

Scheduling policyTime to first tokenInter-token latencySuits
Prefill-prioritisingBest: a new request starts immediatelyWorst: long prompts stall everyone mid-streamShort prompts, batch jobs, no streaming UI
Decode-prioritisingWorst: new requests wait behind active onesBest: existing streams never stutterLong-running generations, strict streaming targets
Chunked prefill (default)Slightly worse than prefill-firstNear decode-first, with a bounded stallMixed interactive traffic — almost everyone

There is no setting that is best at both. The scheduler is spending one latency to buy the other, and the only question is which one your users feel. That is a product decision wearing a flag's clothing.

Now diagnose Monday morning

Nothing was deployed, so look at the input. The p95 input length has grown from 800 tokens to 3,500 — the team started pasting whole files instead of snippets. Prefill work per request rose more than fourfold, so a larger share of every forward pass goes to prefill chunks, admission slows, and requests sit in Waiting longer. Queue time is counted inside time to first token, so TTFT doubles. Aggregate throughput is flat because the GPU is doing exactly as much work as before, just more of it on input. And GPU utilisation could never have shown this: it was already 97%.

The confirming measurement is input token length percentiles alongside num_requests_waiting. The fix is a capacity decision, not a flag.

5. Preemption: the scheduler throwing away your work

Admission can succeed and later become untenable. Sequences grow as they decode, so a batch that fit at step 1 may not fit at step 300. When the block manager runs out, the scheduler picks victims and reclaims their blocks. Two recovery strategies exist:

  • Recompute — discard the KV cache and prefill the request again from scratch when it is re-admitted. Cheap in memory, pays the full prefill cost twice.
  • Swap — copy the blocks out to host memory and back. Pays PCIe bandwidth instead, which lesson 1's framing tells you is roughly an order of magnitude worse than HBM.

Either way, work that was already done is done again. A victim request's latency roughly doubles, and because victims are usually the longest-running requests, the damage lands squarely in your p99. Preemption is also the single most common reason a published inference benchmark is wrong: the author pushed concurrency until the server was thrashing and reported the resulting number as capacity. Lesson 3 makes it a dashboard panel and lesson 5 makes it a disqualifying condition.

6. Two designs for reusing a prefix

If two requests begin with the same 1,500 tokens of system prompt and source file, the second one's prefill for that span is pure waste — the key and value vectors are a deterministic function of the tokens before them. Both engines exploit this, differently, and the difference is instructive rather than decisive.

Block-level automatic prefix cachingRadixAttention
GranularityThe fixed block. A prefix is reused in whole-block units; a partial block at the boundary is recomputed.A radix tree keyed on token sequences, so reuse follows the actual shared span.
MatchingHash of a block's token contents plus its position, so identity is cheap to check.Tree walk to the longest matching prefix, with LRU eviction of cold branches.
SchedulingIndependent of the cache: admission order does not try to group cache-sharing requests.Cache-aware: requests sharing a branch can be scheduled together to keep it resident.
Reported effectPrefill skipped for matched blocks.Up to 5× throughput on prefix-heavy workloads, with no noticeable overhead when there are no hits.

Three things stay true in both designs, and all three are failure modes you will meet:

  1. The prefix must be a prefix. Put a timestamp or a request ID at the start of your prompt and reuse drops to zero. Move it to the end and nothing is lost. This is the cheapest serving win available and teams give it away constantly.
  2. The cache is per replica. Route the follow-up request to a different pod and it recomputes. Cache-aware routing is a load-balancer feature, which the inference fleet lesson covers.
  3. It only helps prefill. A workload spending 87% of its wall clock in decode cannot be rescued by prefix caching, however perfect the hit rate. Lesson 1's waterfall is the argument.

7. Interrogate the metric: "GPU utilisation is 97%"

This is the most misleading number on an inference dashboard, and the opening incident turned on it.

What people read it asWhat it actually is
"The GPU is nearly saturated, so we need more GPUs."The fraction of sampled time during which at least one kernel was resident on the device. A single tiny kernel looping forever reads as 100%.

Lesson 1 explains why this is nearly useless here: a memory-bound decode step keeps a kernel resident for its whole duration while the arithmetic units idle waiting on HBM. 97% utilisation is compatible with using 3% of the compute roof. The questions worth asking instead:

  • Achieved memory bandwidth against the datasheet figure — for decode, this is the real saturation measure.
  • Model FLOPs utilisation against dense peak — for prefill, the same.
  • The scheduler's own counters: running and waiting request counts, KV cache usage, preemption count. These are facts about the queue, and no device-level metric can substitute for them.

Lesson 3 turns that list into panels, and deletes the ones that cannot be defined.

Read the code, then pass the three-sentence test

Reading beats reimplementing here, but only if you read with a question. Pick one engine and answer each of these from the source, not from a blog post:

  1. Follow one request from arrival to its first forward pass. Which object owns the block table, and at what point are physical blocks actually reserved?
  2. Find the decision that admits a request into the next batch. What exactly is compared against what? Write the condition down as an inequality.
  3. Find the preemption path. Which request is chosen as the victim, and does your engine recompute or swap by default?
  4. Find where a prefix cache hit is detected. What is hashed or matched, and what invalidates it?

The test: explain in three sentences how a request's blocks get looked up during attention. If you cannot, you have read about the design rather than read it — go back to the block table.

What a good answer to question 2 looks like

Stated as an inequality rather than a feeling: the scheduler admits the next waiting request only while the blocks its current token count requires, rounded up to the block size, are available in the free pool — and, under chunked prefill, only while the total tokens already committed to this pass stay under the per-pass token budget. Two separate limits, one on memory and one on compute per step, and either can be the binding one. If you tuned a flag without knowing which, you were guessing.

Sources and deeper reading

Read the paper for the mechanism and the code for the truth. Blogs simplify, usually in the direction that makes the design sound cleaner than it is.

  • vLLM and PagedAttention and the SOSP 2023 paper — the fragmentation measurement and the block table design.
  • Inside vLLM: anatomy of a high-throughput inference system — scheduler and block manager, written against the code.

  • Orca (OSDI 2022) and continuous batching explained — iteration-level scheduling and the heavy-tailed length assumption behind it.

  • vLLM automatic prefix caching — the operational rules for when reuse happens.
