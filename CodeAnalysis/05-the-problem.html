Lesson 5

The problem

Everything so far was preparation for one real task. Here it is, the way it actually arrives: as a sentence in a status update that sounds fine until you ask it three questions.

By the end you can…

Interrogate a reported accuracy figure, build and measure a structural IO detector, decide whether a language model belongs in the design, and write up a result somebody can check.

The situation

The task

A platform team runs a large Python monorepo. CI is slow, and they cannot cache build steps because nobody knows which ones are hermetic — the same question as lesson 1, at scale. An engineer is asked to find out which functions perform IO.

They come back with: "Trained a language-model classifier to identify if a function performs IO. 80% accuracy."

Is this good work? Should the team build on it? Hold the instinct to answer — you now have the tools to find out, and the finding is more interesting than either yes or no.

First: is the intent right?

Yes, and clearly so. Lesson 1 listed four jobs blocked on this exact question, and the team is squarely in the first: without knowing which steps touch the outside world, nothing can be cached safely. Bazel's definition of hermeticity is the formal version of their problem. Whatever happens next, the engineer was pointed at something real and valuable.

So this is not a story about a bad idea. It is about a reported result that cannot be checked, and a method chosen before the problem was measured.

Second: the three questions

From lesson 4, in order:

What fraction of functions actually do IO?

Not stated. And this single missing number decides everything, because accuracy on an imbalanced sample is dominated by the majority class. On a typical codebase, most functions are formatting, validation, small pure transforms. Say 15% do IO.

What does the baseline score?

def does_io(function):
    return False

On a codebase that is 15% IO, that scores 85% accuracy. The reported classifier scores 80%.

Read that again. If the base rate is anywhere near 15%, the trained model performs worse than a function that returns False — and would have taken five seconds instead of a training run.

What are precision and recall?

Not stated, and they are the only numbers that would settle it. A model could score 80% accuracy while catching 90% of real IO, or while catching almost none. Those are completely different outcomes and accuracy cannot distinguish them.

The honest conclusion

The claim is not wrong. It is unfalsifiable as reported — there is no way for a reader to tell whether it represents good work or no work. That is a reporting failure before it is a modelling failure, and it is the more common one.

The fix costs nothing: state the sample size, the base rate, precision and recall, and the baseline. Lesson 4 had the template.

Third: build the boring thing first

Before reaching for a model, find out what structure alone gets you — because that is the bar anything fancier has to clear. You already have the design from lessons 2 and 3:

  1. Parse every file with ast.
  2. Find the calls in each function, and classify each one: known IO primitive, known-pure, unresolvable, or another function here.
  3. Propagate IO and UNKNOWN up the call graph to a fixed point.
  4. Resolve UNKNOWN according to what the answer is for — IO if a miss is unsafe.

That is solution/detect_io.py: about 150 lines, standard library only, no training, no inference cost, and every verdict traceable to a line of code. Run on the sample project:

$ python3 detect_io.py sample_project/
IO       banner        sample_project/report.py:34
UNKNOWN  dispatch      sample_project/report.py:43
UNKNOWN  emit          sample_project/report.py:38
IO       from_file     sample_project/util.py:43
NO_IO    header        sample_project/report.py:9
NO_IO    join_path     sample_project/util.py:20
IO       load_config   sample_project/util.py:35
...
20 functions: 7 IO, 10 no IO, 3 unknown

Two of those lines are worth pausing on. load_config is marked IO although it contains no IO primitive — it reaches open through read_text, which is lesson 2 working. And join_path is correctly left clean even though it calls os.path.join, because that is string manipulation that happens to live in an IO-flavoured module.

Fourth: measure it the way you would want yours measured

$ python3 evaluate.py
20 labelled functions, 9 of them IO (45% positive)

policy              TP  FP  FN  TN  accuracy  precision  recall     F1
----------------------------------------------------------------------
UNKNOWN -> IO        9   1   0  10      95%       0.90    1.00   0.95
UNKNOWN -> no IO     7   0   2  11      90%       1.00    0.78   0.88

baseline (always answer no IO): 55% accuracy, 0.00 recall

Now state the limits before anyone asks, because this is where a result earns trust:

  • 20 functions is a tiny sample, and it was written to contain hard cases. The 45% base rate is nothing like a real codebase.
  • So 95% is not transferable. It is a demonstration that the pipeline works end to end, not a performance claim about your monorepo.
  • What does transfer is the shape: over-approximating gives recall 1.00 — it misses no IO at all — and pays one false alarm for it. For build caching, which is what the team needed, that is the correct trade.

Notice what the structural detector gives you that a classifier does not: every verdict comes with a reason and a line number, so a human can overrule it, and the IO primitive list is a thing you can edit when you disagree.

So where does the model belong?

Not nowhere. Look at what the structural detector could not do: three of twenty functions came back UNKNOWN, and lesson 3 showed that bucket never empties. Those are the cases needing judgement — is this .write a file or a buffer, does this plugin do IO — and judgement from context is what a language model is genuinely good at.

That is the reframe. Not "classify every function", which is a job structure does better, cheaper, and explainably. Instead: let static analysis resolve what it can, and have the model adjudicate only the residue.

The arithmetic is the surprising part — the same model, at the same accuracy, becomes far more useful by being pointed at a smaller population.

Same model, two places to put it

At the defaults, the model scores 80% accuracy both times. Applied to everything, its precision is around 0.41 — four out of every seven functions it flags are innocent, and engineers stop trusting the list by Thursday. Applied only to what structure could not resolve, the same model lands near 0.95, because it is no longer being asked the 92% of questions that had a cheaper, better answer.

One number that does not improve

Watch the recall column. Static-only with unknowns resolved as IO gets recall 1.00 — it cannot miss, by construction. Any pipeline that lets a model say "no IO" about an unresolved function gives that up.

So the hybrid is not strictly better. It buys precision with recall. If you are generating sandbox policies or deciding what to cache, where a miss is a production incident, the right answer may well be the unglamorous one: over-approximate and live with the false alarms.

What the write-up should have said

Same work, reported so it can be argued with:

A checkable claim

"412 functions were sampled and hand-labelled; 15% perform IO. A structural AST and call-graph detector resolved 92% of them, reaching precision 0.79 and recall 1.00 when unresolved functions are treated as IO. The majority-class baseline scores 85% accuracy and recall 0. The remaining 32 functions were adjudicated by a language model with 80% accuracy on that subset, raising precision to 0.95 at the cost of recall falling to 0.95. For the build-cache use case we ship the structural detector alone, because recall 1.00 is worth more than the precision."

Longer, and every sentence can be checked by someone who disagrees with you. That is the difference between a number and a result.

✍️ Do it by hand

A colleague reports a new IO classifier: "91% accuracy on 2,000 functions."

  1. What are the first two things you ask?
  2. They answer: 8% of the 2,000 functions do IO. What does the baseline score, and what do you now think of 91%?
  3. They add: it flagged 240 functions, of which 100 really do IO. Compute precision and recall.
  4. It is for deciding which CI steps can be cached. Ship it?
  5. What would you do with the 60 functions it missed?
Show answer

1) What is the base rate, and what does the baseline score? Then precision and recall.

2) 92% of 2,000 do no IO, so always answering "no IO" scores 92%. The classifier's 91% is one point worse than doing nothing.

3) 160 of the 2,000 do IO. TP = 100, FP = 240 − 100 = 140, FN = 160 − 100 = 60. Precision = 100 ÷ 240 = 0.42. Recall = 100 ÷ 160 = 0.63.

4) No. Recall 0.63 means 60 functions that do IO would be treated as cacheable — 60 chances to serve a stale or wrong build output silently. That is the expensive error for this job.

5) Do not try to fix the classifier first. Run a structural detector over them: most will resolve immediately and explainably, and whatever is left is a much smaller, much more interesting set — which is where a model is worth its cost.

🎓 You made it

You took a one-line claim, found the question it failed to answer, built the simple thing it should have been measured against, and worked out where the complicated thing actually earns its place. That sequence — baseline first, measure honestly, add machinery only where it beats the baseline — is most of platform engineering judgement.

The code is in solution/: run it against your own repository and see what it says. Then go and read the three UNKNOWN functions it gives you, because that is where the interesting part of your codebase lives.
