Lesson 4

Measuring a detector

You have a detector. Someone asks how good it is and you say "80% accurate". This lesson is about why that sentence, on its own, carries almost no information — and what to say instead.

By the end you can…

Build a confusion matrix, compute precision, recall and F1, work out the majority-class baseline, and say which metric matters for a given job and why.

Four ways to be right or wrong

First you need ground truth: a sample of functions somebody labelled by hand. Then every prediction lands in one of four boxes. Take the positive class to be "does IO".

That grid is a confusion matrix, and every metric below is just a different ratio taken from it. Which ratio you pick decides what you are able to see.

Accuracy, and why it lies here

Accuracy is the obvious one: the fraction you got right.

accuracy = (TP + TN) / (TP + TN + FP + FN)

Now the thing that breaks it. In a real codebase, most functions do not do IO. Formatting helpers, validators, maths, data classes, small pure transforms — the majority. Suppose 15% of functions do IO.

Write this detector:

def does_io(function):
    return False   # no, never, not once

It reads no code, has no call graph and took five seconds to write. On a codebase that is 15% IO it is 85% accurate, because it is right about every single one of the 85% that do no IO.

This is the majority-class baseline: always answer whichever label is more common. Scikit-learn ships exactly this as a sanity check, noting that dummy estimators are useful to get a baseline value of those metrics, and warns that conventional accuracy can be above chance only because the classifier takes advantage of an imbalanced test set.

So "80% accurate" on a codebase that is 15% IO does not mean the detector learned something. It means it is five points worse than a function that returns False.

An accuracy figure without its base rate is not a result

You cannot evaluate "80% accurate" without knowing the class balance, because the number that makes it impressive or embarrassing is not in the sentence. Two things always travel with an accuracy score: what fraction of the sample was positive, and what the baseline scored on that same sample. Reported without them, the figure cannot be checked — which also means it cannot be wrong, which is the problem.

Two honest numbers

Split the question in two. Both come straight off the matrix, and the definitions are standard — scikit-learn states them as precision = tp / (tp + fp) and recall = tp / (tp + fn).

MetricFormulaThe question it answers
PrecisionTP / (TP + FP)Of the functions I flagged as IO, how many really were?
RecallTP / (TP + FN)Of the functions that really do IO, how many did I catch?
F12PR / (P + R)One number when you need one, weighting both equally

The return False detector scores zero on both. It never flags anything, so it catches nothing. That is the point: precision and recall are blind to the true negatives that were inflating accuracy, so a useless detector has nowhere to hide.

F1 is the weighted harmonic mean of the precision and recall. The harmonic mean matters — it is dragged down by the smaller of the two, so you cannot score well by maximising one and abandoning the other.

Which one you need depends on what breaks

There is no universally correct metric. There is a correct metric for a job, and you find it by asking which mistake costs more — the same question you answered in lesson 3 when deciding how to resolve "unknown".

JobThe expensive mistakeOptimise
Build cachingFN — miss IO, cache a result that should never have been cached, serve a wrong answer silentlyRecall

Parallelising testsFN — miss a shared write, get flakiness that takes a week to track downRecall
"Functions to review" list for humansFP — waste engineers' time on false alarms until they stop reading the listPrecision

Three of those four want recall, which is not a coincidence: in platform work a silent wrong answer usually costs more than a visible false alarm. It is also why lesson 3 recommended over-approximating — that is the same decision, taken before you had the numbers to justify it.

You have done this exact reasoning before

In Observability lesson 9 an SLI was defined as good events ÷ valid events, and the whole skill was choosing the denominator so the ratio means what you think. Precision and recall are the same move: identical numerator (TP), different denominators, completely different questions.

The error budget maths rhymes too. "99.9% of requests succeeded" and "80% of functions classified correctly" are both fractions whose usefulness depends entirely on what was counted and how rare the interesting case is.

Reporting it so it can be checked

Everything above collapses into one habit. A claim about a detector should let a reader disagree with it. That needs four things:

  1. The sample. How many functions, drawn from where, labelled by whom.
  2. The base rate. What fraction actually do IO.
  3. Precision and recall — not accuracy alone, and never a single number without saying which.
  4. The baseline on the same sample, so the reader can see what the work bought.

"80% accurate" fails all four. "On 412 hand-labelled functions, 18% of which do IO, the detector reached 0.74 precision and 0.91 recall; the majority-class baseline scores 82% accuracy and 0 recall" fails none — and is a sentence someone can argue with.

✍️ Do it by hand

A detector is run on 500 labelled functions. 100 of them really do IO. It flags 120 functions, of which 80 really do IO.

  1. Fill in the confusion matrix: TP, FP, FN, TN.
  2. Precision? Recall?
  3. Accuracy?
  4. What does the majority-class baseline score on this sample?
  5. You need this for sandbox policies. Is it good enough, and what would you do next?
Show answer

1) TP = 80. FP = 120 − 80 = 40. FN = 100 − 80 = 20. TN = 500 − 80 − 40 − 20 = 360.

2) Precision = 80 ÷ 120 = 0.67. Recall = 80 ÷ 100 = 0.80.

3) Accuracy = (80 + 360) ÷ 500 = 88%.

4) 400 of 500 do no IO, so always answering "no IO" scores 80%. The detector beats it by 8 points — a genuine improvement, and much less impressive than 88% sounds on its own.

5) Not good enough. Recall 0.80 means 20 functions that do IO are being reported as clean, and each one is a sandbox policy that blocks something the job needs. For this use you would push recall towards 1.0 — resolve unknowns as IO — and accept the precision falling as the price.
