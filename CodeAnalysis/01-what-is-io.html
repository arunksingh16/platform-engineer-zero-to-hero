Lesson 1

What counts as IO?

Some functions only do arithmetic on what you hand them. Others reach outside for a file, a clock, a database. Almost everything a platform does to your code depends on telling those two apart — and the line is blurrier than it looks.

By the end you can…

Say what makes a function pure, split IO into reads and writes, explain why each one breaks a different platform guarantee, and classify a function by hand.

A function that can be trusted twice

Start with the easy case:

def area(width, height):
    return width * height

Call area(3, 4) today, next Tuesday, on a different machine, twice at the same moment on two CPU cores. You get 12 every time. Nothing else in the world is different afterwards.

That is a pure function, and the definition has two halves:

  • The result depends only on the arguments. Same arguments in, same result out — always.
  • Calling it changes nothing that anyone else can see.

Now break the first half:

def is_weekend():
    return datetime.date.today().weekday() >= 5

No arguments at all, and yet the answer changes. It asked the operating system what day it is. The clock is outside, so this function reads from the outside world — and it will cheerfully return a different answer on Saturday than it did on Friday, with no code change in between.

And the second half:

def append_line(path, line):
    with open(path, "a") as f:
        f.write(line + "\n")

This one returns nothing interesting. Its entire point is the dent it leaves in the world: a file is now longer than it was.

Reads and writes break different things

"Does this function do IO?" is really two questions, and they matter for different reasons. Keep them separate — the rest of this course depends on it.

DirectionWhat it meansWhat it costs you
ReadThe result depends on state outside the argumentsYou cannot cache or reuse the result, because the outside may have changed
WriteThe call changes state others can observeYou cannot safely retry, re-run, or run it in parallel with itself

A function can do neither (pure), one, or both. The classic "both" is a cache-filling helper: it goes and gets something, then leaves a copy behind.

What the outside world includes

Files and the network are the obvious ones. These are just as much outside, and juniors miss them constantly:

the clock randomness environment variables stdin / stdout the current working directory other processes the machine's hostname

If removing it from the machine would change the answer, it is outside.

The effects that are not IO

One more case, because it trips people up:

def add_tag(tags, tag):
    tags.append(tag)
    return tags

This changes something the caller can see — the list they passed in. That is a genuine side effect, and it can absolutely cause bugs. But it never leaves the process: no file, no socket, no clock. So it is effectful but not IO.

Why keep them apart? Because the platform jobs below care about the process boundary. A sandbox cannot block a list mutation, and a build cache is not invalidated by one. Throughout this course, IO means crossing the process boundary.

Four reasons a platform wants to know

This is not a theory exercise. Four everyday pieces of platform work are blocked on exactly this question.

1. Build caching

Bazel defines a hermetic build system as one that, given the same input source code and product configuration, always returns the same output by isolating the build from changes to the host system. The payoff it names is direct: The output of an action can be cached, and the action need not be run again unless inputs change.

Read that as a statement about reads. A build step that secretly reads the system clock, an environment variable, or a package from the internet is not a function of its declared inputs — so its cached output is a lie waiting to be served.

2. Tests that can run in parallel

Two tests that both write to /tmp/fixture.db cannot run at the same time, and will fail in a way that looks random. Two pure tests can run on as many cores as you have. Knowing which tests touch shared outside state tells you which ones are safe to parallelise — and often explains your flakiest test.

3. Sandboxing and least privilege

To grant a job the narrowest set of permissions that still works, you need to know what it will reach for. Bazel's own advice is to enable strict sandboxing at the per-action level, since actions in a build can be stateful and affect the build or the output. A policy you write by guessing is either too tight — and breaks at 3am — or too loose, and protects nothing.

4. Blocking calls in async code

Python's asyncio documentation warns that blocking (CPU-bound) code should not be called directly. For example, if a function performs a CPU-intensive calculation for 1 second, all concurrent asyncio Tasks and IO operations would be delayed by 1 second. Synchronous IO blocks in the same way and for much longer: a plain requests.get() inside an async handler stalls every other task on that loop until the network answers. Finding those calls means finding the IO.

✍️ Do it by hand

For each one: pure, reads, writes, or both? And if it is not pure, name what outside thing it touches.

  1. def slugify(title): return title.strip().lower().replace(" ", "-")
  2. def session_id(): return f"{time.time()}-{os.getpid()}"
  3. def backup(src, dst): shutil.copyfile(src, dst)
  4. def port(): return int(os.environ.get("PORT", 8080))
  5. def greet(): return "Hello, " + open("name.txt").read()
Show answer

1) Pure. String methods only, and they return new strings rather than modifying the original.

2) Reads — the clock and the process ID. No arguments, different answer every call. This is a good example of a function most people would call "pure-ish" at a glance.

3) Both. It reads src from the filesystem and writes dst to it. Re-running it is only safe because it overwrites rather than appends — which is a property of this function, not of writes in general.

4) Reads — an environment variable. Nothing is written, but the result depends on how the process was started, so you cannot cache it across environments.

5) Reads — the filesystem, via a function it calls rather than anything on this line. That is the whole difficulty of lesson 2.
