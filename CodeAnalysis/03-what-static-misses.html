Lesson 3

What static analysis cannot see

The detector from lesson 2 rests on one assumption: that when you see a call, you can tell which function it refers to. Python decides that while it runs. This lesson is about where that assumption breaks, why no amount of cleverness repairs it, and what to do instead.

By the end you can…

Name the four things that defeat a static call graph, explain why a detector needs a third answer rather than yes or no, choose between over- and under-approximating, and describe what runtime detection adds and what it still misses.

Four ways the call graph breaks

1. The callee is a value

HANDLERS = {"csv": to_csv, "json": to_json}

def export(fmt, rows):
    return HANDLERS[fmt](rows)

There is a Call node here, and its func is a subscript expression. Which function does it name? Whichever one fmt picks out, which depends on an argument, which may come from a config file or an HTTP request. The tree simply does not contain the answer.

Same problem, more shapes: getattr(obj, name)(), a function passed in as a parameter, a callback registered in a list, a method looked up on an instance whose class you cannot pin down.

2. The same method name means different things

def dump(f, rows):
    f.write(json.dumps(rows))

Is f.write IO? If f is a file, yes. If it is an io.StringIO, no — that writes to memory. If it is a socket, yes and over the network. The attribute name write is shared by all of them, and nothing in this function says which you will get.

3. The code does not exist yet

eval and exec build code at runtime. importlib.import_module(name) loads a module chosen by a string. A decorator can replace a function with a different one. A test can monkeypatch open itself. In each case the thing that eventually runs was not in the file you parsed.

4. The language runs out

Call into a C extension, ctypes, or a Rust module and your Python parser has nothing left to read. numpy and database drivers are mostly not Python. The call graph stops at that edge, and plenty of IO lives on the other side of it.

So the detector needs three answers

This is the most important idea in the course, and it is easy to skip past. A detector that can only say yes or no is forced to guess on cases 1–4. A detector that can say unknown is telling the truth, and tells you exactly where the remaining work is.

VerdictMeansExample
IOA path to a known IO primitive was foundread_config reaches open
No IOEvery call was resolved, and none reached IOnormalize calls only string methods
UnknownAt least one call could not be resolvedexport calls HANDLERS[fmt]

Keep that third bucket. Collapsing it into either of the others is the single most common way these tools become quietly useless — and in lesson 5 it turns out to be the bucket worth spending real effort on.

Being wrong on purpose

Eventually something has to act on the verdict, and "unknown" is not an action. So you choose, per use case, which way to resolve it — and the choice is not a matter of taste.

ChoiceUnknown is treated asYou getUse when
Over-approximateIONever misses real IO. Flags plenty of innocent functions.A miss is unsafe: sandbox policies, build caching, anything where being wrong corrupts or breaks production
Under-approximateNo IOA short, clean list. Silently wrong.A miss is cheap: ranking candidates, a dashboard, suggesting refactors to a human

An analysis that never claims "no IO" about a function that actually does IO is called sound for that property. Soundness costs false alarms, and it is almost always the right trade when a cache serves a wrong answer or a sandbox blocks a syscall your job needed.

This is not a gap in your tooling

It is tempting to assume a better analyser would resolve everything. It would not. Rice's theorem (1953) says that for any non-trivial property of what a program computes, there is no general procedure that decides it correctly for all programs. "Performs IO" is exactly such a property.

So "unknown" is permanent. Real analysers get better by shrinking the unknown set on code people actually write — not by eliminating it. That reframing matters: your job is not to reach 100%, it is to make the leftovers few and visible.

The other direction: run it and watch

If you cannot tell what the code will do, let it tell you what it did. Python has a hook built for this. PEP 578 added runtime audit hooks, and the standard library raises an event for the operations that matter — the docs describe the table as all events raised by sys.audit() or PySys_Audit() calls throughout the CPython runtime and the standard library.

import sys, io

seen = []
sys.addaudithook(lambda e, a: seen.append((e, a))
                 if e in ("open", "socket.connect", "exec", "compile") else None)

open("/etc/hosts").read()                     # a real file
io.StringIO("looks like a file").write("x")   # same method name, no IO
eval(compile("1+1", "<s>", "eval"))           # code made at runtime

Actual output:

open             ('/etc/hosts', 'r', 16777216)
compile          (b'1+1', '<s>')
exec             (<code object <module> at 0x109477210, file "<s>", line 1>)

Look at what that settled. Case 2 from earlier — is .write IO? — answered: the file produced an event, the StringIO produced nothing, because it never touched the outside world. And case 3, code built at runtime, showed up as compile and exec. No parser could have told you either.

Outside Python the same idea runs lower down: strace records syscalls, eBPF probes the kernel, and container runtimes build seccomp profiles by watching a workload.

You have already used a runtime IO detector

If you did Observability lesson 8, auto-instrumentation works on exactly this principle: it wraps known libraries at import time so every outbound call reports itself. The trace waterfall you got is a record of IO that happened — produced without anyone reading the source.

Which also means it inherits this lesson's limitation. A span only exists for a call that ran.

And its one big catch

Runtime detection is precise about what it saw and blind to everything else. A branch not taken is a branch not observed. Run your test suite with an audit hook and you learn about the paths your tests cover — which is rarely all of them, and you will not be told which ones you missed.

Compare the two honestly:

StaticRuntime
SeesEvery branch in the sourceOnly the path that ran
Precision on what it seesFuzzy — unresolved callsExact — it happened or it did not
NeedsSource codeTo execute the code, with inputs
Typical failureFalse alarms from unknownsConfident silence about untested code

They fail in opposite directions, which is the useful part: use static analysis to enumerate the functions, runtime observation to resolve the unknown ones, and keep whatever is still unresolved visible.

✍️ Do it by hand

Your static detector reports these verdicts on a 400-function codebase: 60 IO, 310 no IO, 30 unknown.

  1. You are generating a sandbox policy. Which way do you resolve the 30, and how many functions do you then treat as doing IO?
  2. You are producing a list of "pure functions we could safely cache". How many functions go on the list if you want the list to be trustworthy?
  3. You run the test suite with an audit hook. 12 of the 30 unknowns turn out to do IO; the other 18 are never executed at all. What can you now say about those 18?
  4. A colleague says the hook proves the 18 are pure. What is wrong with that?
Show answer

1) Over-approximate — a missed syscall means the job dies in production. Treat 90 as doing IO and accept that some are innocent.

2) 310. Only the functions you positively resolved as doing no IO. An unknown on this list is a wrong cache hit, which is the expensive kind of mistake.

3) 12 are now confirmed IO, so the unknown set shrinks to 18. About those 18 you have learned nothing at all — "not observed" is not a finding.

4) It confuses absence of evidence with evidence of absence. The hook reports what ran; those 18 never ran. The honest next step is to raise coverage on them or leave them unknown — not to reclassify them.

Where this goes next

You now have two detectors that disagree, three possible verdicts, and a choice about how to resolve the third. Which raises the question the whole course has been walking towards: how do you tell whether any of this actually works?

Lesson 4 is about measuring a detector honestly — and about why "80% accurate" may be a worse result than it sounds.
