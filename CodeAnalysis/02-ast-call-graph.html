Lesson 2

Reading code as a tree

Lesson 1 ended on a function whose IO was invisible: greeting() touches the filesystem, but nothing on its two lines says so. To find that, you stop reading code as text and start reading it as a structure — then follow the calls.

By the end you can…

Explain what an abstract syntax tree is, find every call in a function with ast.walk, build a call graph, and propagate IO through it until nothing changes.

Why not just search for "open("?

It's the obvious first idea, so let's kill it properly. grep -r "open(" finds this:

def read_config(path):
    with open(path) as f:       # ← found, and correct
        return f.read()

And also finds these, all of them wrong:

url = "https://example.com/open(now)"   # a string
# remember to open(path) in binary mode  # a comment
def reopen(conn): ...                    # substring of another name

And misses these, all of them real:

opener = open          # renamed
opener(path)

io = __import__("io")  # reached through a module object
io.open(path)

Text search does not know what a string is, what a comment is, or where a name begins and ends. The parser does — because the parser is the same one Python itself uses to run your code.

The tree

Python hands you its parser in the standard library. ast.parse turns source text into an abstract syntax tree: a nested structure where every construct is a node with typed children.

import ast

src = '''
def area(width, height):
    return width * height
'''
tree = ast.parse(src)
print(ast.dump(tree, indent=2))

Which gives you, trimmed to the interesting part:

FunctionDef(
  name='area',
  args=arguments(args=[arg(arg='width'), arg(arg='height')]),
  body=[
    Return(
      value=BinOp(
        left=Name(id='width'),
        op=Mult(),
        right=Name(id='height')))])

"Abstract" means it keeps the structure and throws away the typography — spaces, line breaks, comments, whether you wrote 'x' or "x". What survives is what the code means. A string containing the text open( is a Constant node and could never be mistaken for a Call.

Finding every call

ast.walk yields every node in the tree, in no particular order. Filter for one type and you have a complete list of the calls in a function:

for node in ast.walk(tree):
    if isinstance(node, ast.Call):
        print(ast.unparse(node.func))

Run that over read_config and you get open and f.read. Two shapes show up in node.func, and you will handle both constantly:

  • Name — a bare call like open(path). The name is node.func.id.
  • Attribute — a dotted call like f.read() or requests.get(url). The last part is node.func.attr, and what it hangs off is node.func.value.

The tree for three functions

These are real ast.parse outputs from Python 3.14. Expression-context nodes (Load, Store) are left out — they say whether a name is being read or assigned, which is not what we are after here.

One function is not enough

Do that to greeting and the result is honest but useless:

def greeting():
    return "Hello, " + read_config("name.txt")

# calls found: read_config

No IO primitive here. read_config is not open. To get the right answer you need the thing you already know from lesson 1 — that read_config reads the filesystem — and a way to pass that knowledge up to its callers.

So build a call graph: one node per function, an arrow from each caller to each function it calls. Then the question becomes a question about the graph.

Propagate until nothing changes

The rule has three steps and no cleverness at all:

  1. Seed. Mark the functions you already know do IO — the primitives: open, socket.socket, time.time, and so on. This list is yours to write.
  2. Sweep. Go through every function. If it calls anything currently marked IO, mark it IO too.
  3. Repeat step 2 until a whole sweep changes nothing.

That last condition is called reaching a fixed point: more work would not change the answer, so you stop. It terminates because each sweep can only ever add marks, and there are finitely many functions to mark.

Watch IO spread

Only open is marked to begin with. Everything else is worked out.

You have met this shape before

"Mark the seeds, follow the arrows, stop when nothing changes" is reachability, and it is everywhere in platform work: which services are affected if this one goes down, which packages pull in a vulnerable library, which tests to re-run after a change, which IAM roles can reach a bucket. The seeds and the arrows change. The loop does not.

Direction matters

Notice which way the marks travelled: from the thing that does IO to the things that call it. That is the opposite direction from the arrows, and it is the direction that is useful — you want to know that render_page is tainted, not that open is.

It also explains a feeling you may have had about real codebases: IO at the bottom of a deep call stack contaminates everything above it. One logging call in a utility function can make half your "pure" helpers impure, and the graph is the only way to see it.

✍️ Do it by hand

A small program. open and time.time are the only known IO primitives.

def stamp():        return time.time()
def slug(t):        return t.strip().lower()
def load(p):        return open(p).read()
def title(p):       return slug(load(p))
def banner(p):      return title(p) + str(stamp())
def shout(s):       return s.upper()
  1. Which functions are marked after the first sweep?
  2. After the second?
  3. Which sweep changes nothing, so you can stop?
  4. Which functions are still pure at the end?
  5. shout is pure. Does that mean it is safe to cache a call to shout(banner(p))?
Show answer

1) stamp and load — they call the primitives directly.

2) title (it calls load) and banner (it calls stamp). Both get marked in the same sweep because a sweep looks at every function.

3) The third. Nothing left to mark, so you have reached the fixed point. Note it takes one extra sweep to discover that — you only know you are done once a sweep is wasted.

4) slug and shout.

5) No. shout is pure, but the expression is not: the argument banner(p) does IO before shout ever runs. Purity is a property of a function, and caching is a property of a call — including everything that was evaluated to make its arguments.

Where this goes next

You now have a detector: parse, find calls, build the graph, propagate to a fixed point. Written out it is well under a hundred lines of standard library Python, and it is genuinely useful.

It is also wrong in ways that matter. Every step assumed you can tell which function a call refers to — and Python will happily decide that while it runs. Lesson 3 is about the cases that break this, and what to do instead.
