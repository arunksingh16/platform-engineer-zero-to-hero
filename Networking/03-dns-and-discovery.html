DNS and service discovery

You changed the record. Some listeners still reach the old region. That is not necessarily a broken load balancer.

By the end you can...

Distinguish authoritative answers from cached answers and explain DNS-based failover's limits.

Who answers?

An application asks a stub resolver; a recursive resolver finds and caches answers from authoritative DNS servers. A/AAAA records supply IPv4/IPv6 addresses; CNAME points to another name. Provider alias records are provider-specific conveniences, not a universal DNS record type.

The TTL tells caches how long an answer may be retained. NXDOMAIN and other negative answers can also be cached. OS, runtime and application caches add behavior; some clients retain addresses longer than expected. Existing connections do not move when a record changes.

Use documented endpoint names rather than pinning a managed proxy's observed IP. Choose an explicitly supported static-IP service when an allowlist requires it. DNS rotation is not per-request balancing: one client can reuse one connection for thousands of requests.

Map the concept

A cold recursive lookup

Conceptual lookup for api.example.com, with empty caches and no CNAME. The recursive resolver does the walking; the application does not contact each authority.

  1. Application → recursive resolver

    The stub asks for an A or AAAA record. A usable cache entry could end the lookup here.

  2. Resolver → root → .com authority

    The root refers the resolver to .com nameservers. The .com authority refers it to example.com nameservers; neither needs to know the API address.

  3. Resolver → example.com authority

    The authority supplies the record and TTL. The resolver caches the result and returns the answer.

  4. Client → returned address

    The client opens an application connection. DNS is no longer in the packet path; routes, policy, a listener and valid TLS are still needed.

Scrub the failover clock

At t=0 the resolver caches A for 60 seconds. A fails and the authoritative answer changes to B at t=10. Assume compliant caching, no prefetch/serve-stale and no detection delay.

50 seconds

At t=10, the authority says B but the resolver can keep A for another 50 seconds. Existing connections do not migrate.

Different DNS failures, different investigations

NXDOMAIN: the name does not exist in this DNS view. SERVFAIL: resolution failed, for example because an upstream is unreachable or DNSSEC validation failed. Timeout: no usable reply arrived in time. Record which resolver answered before changing records. DNSSEC authenticates DNS data; it does not encrypt queries or authenticate your HTTP application.

Split-horizon DNS gives different answers inside and outside a network. Hybrid clients need forwarding rules and reachability to the intended resolver. A private endpoint without working private DNS often leaves clients trying the public path.

Discovery is not reachability

DNS or a service registry tells you where to try. Routes, policy, listener health and application authorization determine whether that attempt works. DNS health checks also need an appropriate vantage point; public probes cannot automatically test arbitrary private addresses.

At t=60: up to 50 seconds after the failure in this simplified compliant-cache example. Health detection would add delay in reality. The existing connection is independent of DNS TTL; it needs to fail, close or be re-established. TTL is not an end-to-end recovery guarantee.
