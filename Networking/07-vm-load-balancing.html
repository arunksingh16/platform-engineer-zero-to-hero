Load balancing a fleet of VMs

A minimal lab is not an HA design

This HAProxy fragment assumes three reachable lab backends on port 8080 exposing a readiness path. It intentionally omits public TLS, authentication and production hardening. Do not expose it directly to the internet.

frontend lab_http
    bind 127.0.0.1:8080
    mode http
    default_backend api_vms

backend api_vms
    mode http
    balance roundrobin
    option httpchk GET /ready
    http-check expect status 200
    server api1 10.20.1.11:8080 check
    server api2 10.20.1.12:8080 check
    server api3 10.20.1.13:8080 check

The loopback bind limits the frontend to local clients. Merge this into a version-appropriate HAProxy configuration with global/default timeout settings; validate with haproxy -c -f /path/to/haproxy.cfg before reload. This is a configuration illustration, not a runnable standalone deployment.

How does the frontend survive?

  • Cloud VMs: prefer a managed LB directly to application VMs when it meets the requirements. If custom proxies are necessary, a managed LB can front multiple proxy VMs across failure domains.
  • Controlled on-premises network: two proxies may share a floating VIP with Keepalived/VRRP where the network supports it. Prevent split-brain and test failover. Existing connection state does not automatically transfer.
  • Routed infrastructure: multiple entry points with BGP/ECMP or anycast require routing expertise, health withdrawal and careful flow symmetry. This is not a beginner shortcut.
  • DNS failover: possible, but bounded by resolution caches, detection and client reconnect behavior.

Cloud networking is not a shared Ethernet segment

Do not assume gratuitous ARP or moving a VIP with VRRP works in a VPC/VNet. Use provider-supported frontend, IP movement or routing mechanisms with explicit failure handling.

Do it by hand

You have two proxies but DNS points only at proxy A. A dies. What is missing? What else must survive?

Show answer

A tested mechanism to steer new connections to B: managed frontend, supported VIP/routing failover, or health-aware DNS with accepted delays. B also needs capacity, current configuration, certificates and reachable backends. Test a host failure, not just stopping one backend process.
