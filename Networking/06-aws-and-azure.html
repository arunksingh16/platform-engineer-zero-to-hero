Gateway Load Balancer is for appliances such as firewalls, not an HTTP API gateway. API Gateway (AWS) and API Management (Azure) add API policies, authentication integration, quotas and lifecycle features; they are not merely alternate names for generic load balancers.

Azure Application Gateway also offers TCP/TLS proxy capabilities; inspect current feature, SKU and deployment constraints if you need a terminating transport proxy. Do not infer that it supports UDP or that Standard Load Balancer terminates TLS. Azure Load Balancer also has a cross-region topology: "all Azure load balancers are regional" is too broad.

Try a first-pass selection

This is a teaching aid, not a complete architecture recommendation. Exposure, private-origin support, protocol versions and failure behavior still need review.

Write the contract before deployment

Record public/internal exposure, IP family, protocols on both legs, TLS ownership, client-IP forwarding, probes, idle limits, drain behavior, zone support, quotas and pricing dimensions. Static IP requirements can change the choice. Never trust arbitrary client-supplied forwarding headers; accept them only through your known proxy chain.

Do it by hand

You have private VM APIs needing /catalog and /playlist routing, plus cacheable global media. Which components belong where?

Show answer

AWS: an ALB for the APIs; CloudFront for media from a suitably protected origin. Azure: Application Gateway for regional APIs, Front Door for global media delivery. Public client access and private backend addresses are compatible through a public proxy; a truly private-only service needs an internal entry point and private client connectivity. Do not chain every product by default.
