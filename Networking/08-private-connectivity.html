Lesson 8

Private connectivity and egress

"Private subnet" does not mean isolated, encrypted or authorized. Define who may initiate each connection, which route it takes, and how replies return.

By the end you can...

Separate routing, packet filtering, address translation and identity.

Four different controls

  1. Routing: a destination has a usable path.
  2. Filtering: policy allows the required protocol, source, destination and port.
  3. Translation: SNAT changes source addresses for egress; DNAT maps a frontend destination to a backend. NAT is not authorization.
  4. Identity: the application or service verifies who is calling and what they may do.

AWS security groups are stateful, while network ACLs are stateless and require appropriate return rules, including ephemeral ports. Azure NSGs are stateful; do not treat them as AWS NACL equivalents. Host firewalls and network appliances can add more enforcement points.

Peering is not automatically transitive: A-to-B and B-to-C do not imply A-to-C. Private endpoints expose a service rather than merging whole networks. DNS, endpoint policy, security rules and service authorization remain necessary. Creating a private endpoint does not universally disable the public endpoint; explicitly configure and test public-access restrictions.

Dedicated connectivity is not synonymous with end-to-end encryption. Choose IPsec, supported link encryption, and/or application TLS according to the threat model. Build diverse redundant paths and exercise failover; two tunnels sharing one upstream failure domain may not satisfy the requirement.

Egress needs a budget

SNAT uses a finite pool of source addresses and ports. Many short connections to the same destination can exhaust mappings before CPU saturates. Pool connections where appropriate, monitor allocation/drop signals, and size using the actual provider's destination and timeout rules. A NAT gateway provides egress, not an inbound application frontend.

Do it by hand

A playlist service resolves a database private name correctly but cannot connect. List five checks before changing DNS.

Show answer

Check forward and return routes, effective security rules, endpoint approval/service exposure, listener port and health, and application identity/authorization. Determine first whether the failure is a network timeout, refused connection, TLS error or authenticated denial; they point to different layers.
