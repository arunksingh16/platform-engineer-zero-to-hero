Small, scoped probes

Incident replay: the SYN never gets an answer

A synthetic capture from a failing client shows repeated SYNs. Walk from observation to a narrower hypothesis; do not jump straight to “the firewall.”

  1. Name resolves to the expected addressA api.music.example = 10.30.8.7

    This proves an answer was obtained, not that a SYN can reach the destination. Confirm this is the intended DNS view.

  2. Client sends, then retransmits0s SYN seq=100; 1s SYN seq=100; 3s SYN seq=100

    Illustrative timings, not universal TCP constants. No SYN-ACK was observed here. Possibilities include forward drop, return drop, server trouble or exhausted state.

  3. Compare server-side evidenceServer sees SYN and sends SYN-ACK

    In this scenario, the forward packet arrived and the listener replied. Now investigate the return path and intermediate state rather than changing DNS.

  4. Find the first missing boundaryReturn filter drops destination port 53000

    A stateless return rule allowed destination 443 only. Correct the scoped rule, rerun the same client probe and verify transport, TLS and the actual request.

Why the small probe lies

Model: IPv4 with Don't Fragment (DF), 1500-byte underlay and a fixed 100-byte tunnel overhead. Effective inner MTU is 1400. Classic Path MTU Discovery (PMTUD) needs ICMP feedback; packetization-layer discovery can recover differently.

1500 bytes

A 1500-byte inner packet plus 100 bytes of overhead does not fit. With DF set and feedback blocked, large transfers may stall while small probes succeed.

MTU, MSS and packet evidence

MTU limits the IP packet on a link; TCP MSS describes TCP data bytes, excluding IP/TCP headers. At inner MTU 1400, plain IPv4 (20-byte header) + TCP (20-byte header) leaves 1360 data bytes before options. Tunnel overhead varies. IPv6 routers do not fragment forwarded packets; required ICMPv6 Packet Too Big messages and sender behavior matter.

A reset (RST) is different from silence: it shows a TCP-speaking host or intermediary actively rejected or reset the connection, not necessarily the intended application. An HTTP 403 means some HTTP component replied; identify which one before concluding the backend denied you. Intermediate traceroute hops can rate-limit or ignore probes while forwarding application traffic normally.

Protocol reading: IPv4 Path MTU Discovery, IPv6 Path MTU Discovery and TCP specification.

These are optional examples for systems you are authorized to test, using tools installed separately. api.music.example is a placeholder, not a working service.

dig api.music.example A
dig api.music.example AAAA
curl --connect-timeout 3 --max-time 10 -sS -o /dev/null \
  -w 'dns=%{time_namelookup} connect=%{time_connect} tls=%{time_appconnect} first_byte=%{time_starttransfer} total=%{time_total}\n' \
  https://api.music.example/ready
openssl s_client -connect api.music.example:443 \
  -servername api.music.example -verify_hostname api.music.example \
  -verify_return_error < /dev/null
ss -lnt
ip route get 10.20.1.11

ss and ip examples are Linux-specific. curl timing fields above are cumulative from request start, not separate hop durations. Subtract connect from TLS time to approximate the TLS phase for a new direct connection. Proxies and reuse change interpretation.

Use curl --resolve for an authorized known-IP test that preserves hostname/SNI; connecting to an IP URL changes those variables. ICMP ping success does not prove TCP port access, and ping failure does not prove the application is unreachable.

Cloud and VM evidence

AWS: inspect target health/reason codes, CloudWatch LB metrics, access logs, VPC Flow Logs and Reachability Analyzer for supported paths. Azure: inspect backend health, Azure Monitor metrics, access logs, Network Watcher connection troubleshooting and virtual network flow logs. Use current VNet flow logging guidance rather than building new tooling around legacy NSG flow logs.

On VMs, correlate proxy access/error logs with host sockets, interface drops and a narrowly scoped, authorized packet capture. Flow logs describe network metadata, not request payloads or proof of application success. Configuration analyzers do not replace live tests. Protect captures and logs: credentials and personal information can be present.

Incident drill

Small health responses work; large media responses stall only over a new VPN. CPU is normal. What do you test first?

Show answer

Suspect MTU/MSS and Path MTU Discovery along the tunnel. Compare packet sizes and retransmissions on both sides, check tunnel overhead and required ICMP signaling. Also rule out proxy/range/timeouts with evidence. Do not globally disable firewalls or randomly lower MTU everywhere.

Primary reading: Reachability Analyzer, Azure connection troubleshoot, VNet flow logs.
